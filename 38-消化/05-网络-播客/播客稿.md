## 板块一：K8s 网络模型的三条铁律

小K：先打地基。很多人学 K8s 网络，一上来就看 CNI 插件，越看越乱。你觉得正确的起点是什么？
小云：起点是三条铁律。第一条，所有 Pod 之间可以直接通信，不需要 NAT。第二条，节点和 Pod 之间也可以直接通信。第三条最关键，Pod 看到的自己的 IP，就是别人看到的 IP。
小K：第三条怎么理解？
小云：意思是 K8s 要的是一个扁平网络。每个 Pod 都有自己独立的、全网可路由的 IP，不搞端口映射那种替身游戏。你可以把集群想象成一个小区，每个 Pod 是一户人家，门牌号就是 IP，快递员直接按门牌送，不用去物业换牌子。
小K：那这个小区的水电煤，是谁修的？
小云：这就是 CNI 的活了。先说砖瓦：每个 Pod 住在一个叫 Network Namespace 的网络小黑屋里，veth pair 是连出小黑屋的虚拟网线，宿主机上再有一台虚拟交换机，叫 Linux Bridge。同一个节点上的两个 Pod 通信，就是走这两根网线和交换机，不用任何封装。
小K：跨节点呢？
小云：跨节点有三条主流路线。一是封装，比如 VXLAN，把包再套一层信封寄过去。二是路由，靠 BGP 让每台机器都知道路怎么走。三是 eBPF，直接在内核里高效转发。选哪条路，就是你选 CNI 插件的核心差异。

## 板块二：CNI 选型与 Terway

小K：好，那 CNI 到底怎么选？知识库里有一张五大插件的对比表，你先给大家划个重点。
小云：先记住一句大实话：CNI 是规范，不是产品。kubelet 在创建 Pod 的时候，会去调用 /opt/cni/bin 目录下的插件二进制，告诉它加网络还是删网络。真正干活的是 Flannel、Calico、Cilium 这些插件。
小K：性能上谁强谁弱？
小云：大致排序是这样：Flannel 用 VXLAN 封装，性能中等，胜在简单。Calico 用 BGP 路由或者 eBPF，吞吐高，功能全。Cilium 全程 eBPF，吞吐很高，延迟低。而在阿里云上，Terway 的 ENIIP 模式在对比表里是吞吐最高、延迟最低的那一档。
小K：为什么 Terway 能这么快？
小云：因为它是阿里云 ACK 自研的，走的是 VPC 直通路线。Pod 拿到的不是Overlay 里的虚拟身份，而是 VPC 里真实网卡 ENI 上的辅助 IP，一个包都不用封装，而且天然和 VPC 的安全组、网络策略打通。
小K：那 Terway 有没有坑？
小云：有，坑在配额。每台 ECS 实例能挂多少张 ENI、每张 ENI 能挂多少个辅助 IP，都是按实例规格写死的。Terway 文档里专门有一张实例规格配额速查表，规划 Pod 密度之前必须先看它。
小K：给大家一个选型口诀吧。
小云：通用生产选 Calico，成熟稳定。高性能加安全需求选 Cilium，它有 L7 策略和可观测。图简单选 Flannel。在阿里云上，直接 Terway。要做多集群互联，还是 Cilium，它有 ClusterMesh。

## 板块三：Service 与 DNS 的性能拐点

小K：地基讲完了，说说集群里的流量中转站，Service。很多人不知道，那个稳定的虚拟 IP 背后全是 kube-proxy 在干活。
小云：对。默认的 iptables 模式里，kube-proxy 会给每个 Service 写一串 DNAT 规则，靠概率把流量随机分给后端 Pod。问题是，iptables 匹配规则是 O(n) 的线性查找，Service 一多，规则表比整本电话簿还厚。
小K：多到什么程度该紧张？
小云：文档给的拐点是超过一千个 Service，延迟就开始明显了。大规模集群一定要切 IPVS 模式，它是 O(1) 的哈希查找，还支持轮询、最少连接这些调度算法。
小K：DNS 这边也有坑？
小云：有个隐蔽的名叫 ndots 的坑。Pod 里的 resolv.conf 是 kubelet 注入的，默认 ndots 设成 5，意味着你访问一个外部域名，会先在集群域名后缀里白白试好几圈，查询量翻着倍地涨。生产环境的建议是降到 2。
小K：还有什么省钱省力的组合拳？
小云：两招。一是上 NodeLocal DNSCache，把 DNS 缓存做到每个节点本地，别什么请求都打到 CoreDNS。二是用 topologyAwareHints，让流量优先走同一个可用区，跨 AZ 的流量又贵又慢。

## 板块四：服务网格与 API 网关

小K：接下来这个话题，我在知识库里看到一句话，说微服务的流量治理有两条战线，东西向和南北向。
小云：对，这条分界线特别重要。南北向是外部流量进集群，归 API 网关管。东西向是集群里服务和服务之间的流量，归服务网格管。
小K：服务网格这边，五大选手怎么分？
小云：Istio 功能最全，但控制平面重。Linkerd 走轻量路线。Consul Connect 和 Consul 生态绑定深。Dapr 换了个思路，做分布式运行时。Traefik Mesh 最简单。另外一个必须提的趋势是 Istio 的 Ambient Mesh，它用一个叫 ztunnel 的组件把 Sidecar 取消了，每个 Pod 的资源开销大幅下降。
小K：网关这边，大家都说 Ingress 老了，Gateway API 才是未来，为什么？
小云：Ingress 的问题是可表达的能力太少，高级功能全靠注解，换一家网关实现，注解就全变了，可移植性很差。Gateway API 把职责拆成三层：GatewayClass 定义网关的类型，由平台团队管。Gateway 是实例，由集群管理员管。HTTPRoute 才是路由规则，交还给业务开发。谁负责什么，清清楚楚。
小K：它成熟了吗？
小云：节奏是这样的：2023 年 10 月 v1.0，HTTPRoute 正式 GA。2024 年 5 月 v1.1 加入了 GRPCRoute 和 BackendTLSPolicy。同年 11 月 v1.2 开始实验性支持服务网格场景，代号 GAMMA。也就是说，这套标准正在把南北向和东西向统一起来。

## 板块五：eBPF——内核里的网络革命

小K：最后一个板块，也是整条技术线反复出现的名字，eBPF。先给没听过的朋友扫个盲。
小云：eBPF 的全称是扩展的伯克利包过滤器，但今天它早就不是过滤器了。本质一句话：不用改内核源码，也不用加载内核模块，就能在 Linux 内核里安全地运行沙箱程序。
小K：安全这两个字怎么保证？毕竟是在内核里跑别人的代码。
小云：靠验证器。你的 eBPF 程序加载前，会被内核的 verifier 逐条检查，保证没有死循环、没有越界访问，通过了才 JIT 编译执行。这就像内核门口站了个安检员。
小K：落到网络场景，Cilium 就是靠它成名的？
小云：没错。Cilium 已经是 CNCF 毕业项目了。它的架构是每节点一个 Agent DaemonSet，加一个集群级的 Operator，再加 CNI 插件本体。转发、NetworkPolicy、甚至七层策略，全部用 eBPF 实现，绕开了 iptables。知识库里给的数据是，全链路替换 iptables 之后，延迟能降百分之三十到五十。
小K：生态上还有什么配套？
小云：两个明星组件。Hubble 做网络可观测，流量图谱一目了然。Tetragon 做运行时安全，进程启动、文件访问、异常连接，都能在内核层面抓个现行。

## 总结

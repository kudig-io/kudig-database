# 事后复盘文化建立指南

## 为什么需要无责文化

```
有责文化后果:
  隐瞒问题 → 信息不透明 → 重复问题
  推卸责任 → 团队对立 → 协作困难
  惩罚文化 → 恐惧创新 → 保守发布

无责文化收益:
  透明共享 → 集体学习 → 系统改进
  心理安全 → 主动报告 → 提前预防
  持续实验 → 快速迭代 → 可靠性提升
```

## 实施步骤

### Step 1: 管理层承诺

```
管理层必须明确:
□ 事后复盘是无责的
□ 不会因问题惩罚个人
□ 奖励主动发现和报告问题
□ 将改进措施纳入绩效考核（而非问题本身）
```

### Step 2: 建立标准流程

```
问题后 24 小时内: 完成初步时间线
问题后 48 小时内: 召开复盘会议（不超过 1 小时）
问题后 1 周内: 完成复盘文档
问题后 2 周内: 开始执行改进措施
问题后 1 个月: 审查改进措施进展
```

### Step 3: 培训与赋能

```
培训内容:
- 5 Whys 根因分析方法
- 系统思维（关注流程而非个人）
- 如何撰写无责复盘文档
- 如何主持复盘会议
```

### Step 4: 持续改进

```
度量指标:
- 复盘完成率 (目标: 100%)
- 改进措施完成率 (目标: > 90%)
- 重复问题率 (目标: < 5%)
- 平均复盘时间 (目标: < 48 小时)
```

## 常见阻力与应对

| 阻力 | 应对策略 |
|------|---------|
| "这太费时间了" | 限制复盘会议 1 小时，使用模板提高效率 |
| "这没什么可学的" | 即使小问题也要复盘，积累系统知识 |
| "管理层不会真的无责" | 管理层率先分享自己的错误 |
| "我们太忙了" | 将复盘时间计入工作量，不额外加班 |

## 复盘文档模板详解

### 标准复盘文档结构

```markdown
# 事件复盘: <事件标题>

## 元信息
- 事件 ID: INC-2026-0711-001
- 严重度: Sev1
- 影响时间: 2026-07-11 14:30 - 15:45 (75 分钟)
- 影响范围: 支付服务全量用户
- 复盘日期: 2026-07-13
- 参与人员: @sre-team, @payment-team, @product

## 执行摘要
> 用 2-3 句话描述发生了什么、影响是什么、根本原因是什么。

## 时间线
| 时间 | 事件 | 操作人 |
|-----|------|-------|
| 14:30 | 监控告警触发: 支付错误率 > 5% | 自动 |
| 14:32 | IC 宣布 Sev1，开启指挥频道 | @ic |
| 14:35 | 定位到数据库连接池耗尽 | @ops |
| 14:45 | 执行回滚到上一版本 | @ops |
| 15:00 | 错误率恢复正常 | 自动 |
| 15:45 | 宣布解除，进入观察期 | @ic |

## 影响分析
- 受影响用户: ~15,000
- 失败交易: ~2,300 笔
- 收入影响: ~¥450,000
- SLA 违约: 是 (可用性 99.2% < 99.9%)

## 根因分析 (5 Whys)
1. **为什么支付失败?** → 数据库连接超时
2. **为什么连接超时?** → 连接池耗尽
3. **为什么连接池耗尽?** → 慢查询积压
4. **为什么慢查询积压?** → 缺少索引
5. **为什么缺少索引?** → 上线前未执行 SQL 审查

**根本原因**: 发布流程缺少 SQL 审查门禁

## 做得好的
- 监控告警及时 (2 分钟内触发)
- IC 响应迅速，指挥有序
- 回滚决策果断

## 待改进的
- 数据库连接池监控缺失
- 慢查询告警阈值过高
- 发布流程缺少 SQL 审查

## 改进行动
| 行动 | 负责人 | 截止日期 | 优先级 | 状态 |
|-----|-------|---------|-------|------|
| 添加连接池监控 | @sre | 07-20 | P0 | ☐ |
| 调整慢查询告警 | @dba | 07-18 | P0 | ☐ |
| 实施 SQL 审查门禁 | @dev | 07-25 | P1 | ☐ |
| 更新 Runbook | @sre | 07-22 | P1 | ☐ |

## 经验教训
- 数据库变更需要更严格的审查
- 连接池监控应纳入标准监控模板
- 回滚是最有效的止血手段
```

## 根因分析方法论

### 5 Whys 实战示例

```
问题: 用户无法登录

Why 1: 为什么用户无法登录?
  → 认证服务返回 500 错误

Why 2: 为什么认证服务返回 500?
  → Redis 连接失败

Why 3: 为什么 Redis 连接失败?
  → Redis 主节点 OOM

Why 4: 为什么 Redis 主节点 OOM?
  → 内存碎片率过高，实际使用超过 limit

Why 5: 为什么内存碎片率过高?
  → 未配置 activedefrag，且 maxmemory-policy 为 noeviction

根本原因: Redis 配置不当 + 缺少内存碎片监控
```

### 故障树分析 (FTA)

```
                    [用户无法支付]
                         │
            ┌────────────┼────────────┐
            ▼            ▼            ▼
      [API 错误]    [超时]      [前端错误]
            │            │            │
      ┌─────┴─────┐      │      ┌─────┴─────┐
      ▼           ▼      ▼      ▼           ▼
  [5xx]      [4xx]   [DB慢]  [JS错误]  [网络]
      │                    │
      ▼                    ▼
  [服务崩溃]          [连接池耗尽]
      │                    │
      ▼                    ▼
  [OOM]              [慢查询积压]
                           │
                           ▼
                      [缺少索引]
```

### 贡献因素分类

| 类别 | 示例 | 改进方向 |
|-----|------|----------|
| **代码缺陷** | Bug、逻辑错误 | 代码审查、测试覆盖 |
| **配置错误** | 参数不当、环境差异 | 配置管理、IaC |
| **容量不足** | 资源耗尽、流量突增 | 容量规划、自动扩容 |
| **依赖故障** | 第三方服务、中间件 | 降级、熔断、多活 |
| **流程缺陷** | 审查缺失、测试不足 | 流程优化、门禁 |
| **人为失误** | 操作错误、判断失误 | 自动化、培训 |

## 复盘会议主持技巧

### 会议议程模板

```
复盘会议议程 (60 分钟)

00:00-05:00  开场与规则重申
  - 感谢参与
  - 重申无责原则
  - 确认目标: 学习改进，不是追责

05:00-20:00  时间线回顾
  - Scribe 逐条朗读时间线
  - 补充遗漏信息
  - 澄清疑问

20:00-35:00  根因分析
  - 5 Whys 逐层深入
  - 识别贡献因素
  - 区分根本原因与触发因素

35:00-50:00  改进行动
  - 每条问题对应至少一条改进
  - 明确负责人和截止日期
  - 确定优先级

50:00-60:00  总结与关闭
  - 回顾做得好的
  - 确认行动项
  - 感谢参与
```

### 主持人话术指南

| 场景 | 推荐话术 | 避免话术 |
|-----|---------|----------|
| 开场 | "我们来学习这次事件，让系统更健壮" | "我们来分析这次事故" |
| 追问 | "是什么让这个问题没有被提前发现?" | "为什么你没有发现这个问题?" |
| 归因 | "流程中哪个环节可以拦截这个问题?" | "谁应该负责这个问题?" |
| 分歧 | "让我们先记录两种观点，会后再验证" | "你确定是这样吗?" |
| 情绪 | "我理解这很令人沮丧，让我们聚焦改进" | "别激动，冷静点" |

  actions.yaml: |

      - id: ACT-2026-0711-001

      - id: ACT-2026-0711-002

### 自动化提醒 CronJob

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: postmortem-action-reminder
  namespace: sre
spec:
  schedule: "0 9 * * 1"  # 每周一 9:00
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: reminder
              image: bitnami/kubectl:latest
              command:
                - /bin/sh
                - -c
                - |
                  echo "=== 复盘改进行动提醒 ==="
                  
                  # 检查逾期行动
                  OVERDUE=$(kubectl get configmap postmortem-actions -n sre -o yaml | \
                    yq '.data.actions' | \
                    yq '.actions[] | select(.due < now and .status != "done")')
                  
                  if [ -n "$OVERDUE" ]; then
                    echo "⚠️ 以下行动已逾期:"
                    echo "$OVERDUE"
                    # 发送 Slack 提醒
                    curl -X POST -H 'Content-type: application/json' \
                      --data '{"text":"⚠️ 复盘改进行动逾期提醒"}' \
                      $SLACK_WEBHOOK
                  fi
```

## 复盘成熟度模型

| 级别 | 特征 | 复盘质量 | 改进效果 |
|-----|------|---------|----------|
| **1. 无复盘** | 问题发生后无复盘 | 无 | 重复问题频发 |
| **2. 形式化** | 有复盘但流于形式 | 低 | 改进措施不落地 |
| **3. 规范化** | 有模板、有流程 | 中 | 部分改进落地 |
| **4. 数据驱动** | 基于数据分析根因 | 高 | 改进措施有效 |
| **5. 学习型** | 复盘知识沉淀共享 | 极高 | 系统性预防 |

### 成熟度评估问卷

| 问题 | 1分 | 3分 | 5分 |
|-----|-----|-----|-----|
| 复盘完成率 | < 50% | 50-90% | > 90% |
| 改进措施完成率 | < 50% | 50-80% | > 80% |
| 重复问题率 | > 20% | 10-20% | < 10% |
| 复盘文档质量 | 无模板 | 有模板 | 有模板+评审 |
| 知识共享 | 无 | 团队内 | 全公司 |

## 自动化支持

### 复盘文档自动生成

```bash
#!/bin/bash
# 🟢 低风险：复盘文档生成脚本
set -euo pipefail

INCIDENT_ID=${1:?"Usage: $0 <incident-id>"}

echo "=== 生成复盘文档: $INCIDENT_ID ==="

# 1. 收集事件数据
echo "[1] 收集事件数据..."
kubectl get events -n production --field-selector involvedObject.name=$INCIDENT_ID > /tmp/events.txt

# 2. 收集监控截图
echo "[2] 收集监控数据..."
# 从 Grafana 导出关键面板

# 3. 生成文档
echo "[3] 生成文档..."
cat > /tmp/postmortem-$INCIDENT_ID.md <<EOF
# 事件复盘: $INCIDENT_ID

## 元信息
- 事件 ID: $INCIDENT_ID
- 生成时间: $(date)

## 时间线
$(cat /tmp/events.txt)

## 待补充
- [ ] 执行摘要
- [ ] 影响分析
- [ ] 根因分析
- [ ] 改进行动
EOF

echo "=== 文档已生成: /tmp/postmortem-$INCIDENT_ID.md ==="
```

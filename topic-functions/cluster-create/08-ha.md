## 高可用架构

kubeadm 支持两种高可用模式:

```
模式 1: stacked etcd
┌─────────┐  ┌─────────┐  ┌─────────┐
│ node-1  │  │ node-2  │  │ node-3  │
│ apiserver│  │ apiserver│  │ apiserver│
│ etcd    │  │ etcd    │  │ etcd    │
└─────────┘  └─────────┘  └─────────┘

模式 2: external etcd
┌─────────┐  ┌─────────┐  ┌─────────┐
│ node-1  │  │ node-2  │  │ node-3  │
│ apiserver│  │ apiserver│  │ apiserver│
└─────────┘  └─────────┘  └─────────┘
       │           │           │
       └───────────┴───────────┘
              ┌────────┐
              │ external etcd cluster │
              └────────┘
```

## 高可用配置示例

```yaml
# init-config.yaml
apiVersion: kubeadm.k8s.io/v1beta3
kind: InitConfiguration
metadata:
  name: my-cluster
spec:
  controlPlaneEndpoint: "loadbalancer:6443"  # 负载均衡器地址
  localAPIEndpoint:
    advertiseAddress: "192.168.1.1"
    bindPort: 6443
```

---

## 核心: --control-plane-endpoint

```go
// cmd/kubeadm/app/cmd/phases/controlplane/controlplane.go
func getControlPlaneEndpoint(cfg *kubeadmapi.InitConfiguration) (string, error) {
    // 如果指定了 --control-plane-endpoint，使用它
    // 否则使用第一个 control plane 节点的 IP
    return cfg.ControlPlaneEndpoint, nil
}
```

所有节点的 `admin.conf` 和 `kubelet.conf` 中的 `server` 字段都指向负载均衡器，实现 API Server 高可用。

---

## 负载均衡器要求

| 要求 | 说明 |
|------|------|
| TCP 6443 | API Server 端口 |
| TLS Passthrough | 负载均衡器透传 TLS 到后端 API Server |
| 健康检查 | 检查后端 6443 端口是否健康 |
| 会话保持 | 可选，kubelet 支持重连 |

常用方案: kube-vip, metallb, 云厂商 CLB/ALB, nginx/haproxy

## 新增 control-plane 节点流程

```bash
# 在新节点上执行
kubeadm join control-plane-endpoint:6443 \
  --token <token> \
  --discovery-token-ca-cert-hash sha256:<hash> \
  --control-plane \
  --certificate-key <key>
```

**`--certificate-key`** 用于解密从 init 节点上传到 ConfigMap 的证书秘文:

```go
// cmd/kubeadm/app/cmd/join.go
func decryptCertificateKey(key string) ([]byte, error) {
    // 使用 AES-256-GCM 解密上传到 ConfigMap 的私钥
    // 确保新节点获得控制面证书的完整副本
}
```

## etcd 高可用

### stacked 模式 (同节点 etcd)

每个 control-plane 节点运行自己的 etcd 实例，通过 raft 协议同步。

### external etcd 模式

```bash
# 1. 先搭建独立的 3 节点 etcd 集群
# 2. kubeadm init 时指定:
kubeadm init --control-plane-endpoint=<lb> --etcd-servers=https://<etcd1>:2379,https://<etcd2>:2379,https://<etcd3>:2379
```

## API Server HA 细节

```go
// 每个 API Server 配置:
--secure-port=6443
--advertise-address=<node-ip>
// kubelet.conf 指向 loadbalancer
server: https://<loadbalancer>:6443
```

## Controller Manager / Scheduler HA

```go
// kube-controller-manager 和 kube-scheduler 都配置:
// --leader-elect=true
// 使用内置的 leader election，选择一个 active 实例
// 其他实例处于热备状态
```

Leader election 使用以下端点:

```go
// kube-controller-manager
--leader-elect-resource-name= kube-controller-manager
endpoints: /xyz/kubernetes.io/services/kube-controller-managerLeader

// kube-scheduler
--leader-elect-resource-name= kube-scheduler
endpoints: /xyz/kubernetes.io/services/kube-schedulerLeader
```

## 证书处理

新 control-plane 节点加入时:

```
1. 解密 certificate-key 获取控制面证书
2. 将证书写入 /etc/kubernetes/pki/
3. 生成各组件 kubeconfig
4. 生成静态 Pod manifests
5. 启动 API Server/Controller Manager/Scheduler
6. 向现有 etcd 集群添加成员
```

## 常见问题

| 问题 | 原因 | 解决 |
|------|------|------|
| etcd 成员添加失败 | 新节点 IP 不在证书 SAN 中 | 重新生成 etcd 证书含新 IP |
| API Server 连不上 | 负载均衡器未配置 TLS passthrough | 配置负载均衡器透传 |
| 脑裂 | 节点网络分区 | 减少 `--election-timeout` |

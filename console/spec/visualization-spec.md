# Console 可视化规范

> 本文规定六个结构视图**画什么、为什么这么画、怎么读、什么绝不能画**。每张图必须先通过"它回答哪个问题"这一关，否则不进产品。

## 0. 通则

### 0.1 图形选择原则

| 读者要做的判断 | 用 | 不用 |
|---|---|---|
| 比较若干对象在同一维度的多寡 | 条形 / 堆叠条 | 饼图（>3 项）、雷达图 |
| 找"谁在哪" | 矩阵 / 热力 | 词云 |
| 看层级拆解 | 缩进树 / 冰柱图 | 3D 饼、圈套 |
| 看邻接 | 2 跳邻域小图 | 全库力导向 |
| 看随时间变化 | 堆叠柱 / 折线 | 面积图（易夸张） |

### 0.2 颜色语义（与 `console/DESIGN.md` 一致）

| 色 | 唯一含义 | 禁止 |
|---|---|---|
| IBM 蓝 `#1E40AF` | 已落锁 / 已对齐 / 选中 | 装饰、强调无关内容 |
| 浅蓝 `#EFF3FE` + 蓝线 | 部分覆盖 | 表示"次要点" |
| 琥珀 `#B86E0A` / 文字 `#7D4A05` | 缺口 / 未覆盖 | 表示"错误"或"危险" |
| 墨 `#0D0D0D` | 结构框线、文字 | 填充大面积 |

> **一色一义**：任何图上出现第四种颜色，必须在图例中给出唯一含义；否则删除。

### 0.3 尺寸与密度

- 一个视图首屏最多 **3 个视觉块**；
- 单图元素上限：矩阵 ≤ 40×20 格、邻域 ≤ 60 节点、时间线 ≤ 36 个月；
- 超出上限一律**聚合**（按域合并）并在标题里注明"已聚合"。

### 0.4 文本等价

每张图必须提供"表格视图"切换（`aria-describedby` 指向隐藏表格），保证屏幕阅读器与复制粘贴可用。

## 1. 构成剖面 Composition

**问题**：这片知识由什么组成？核心页多还是外围页多？

**画法**：每个分区一条水平堆叠条，段 = tier（core / supporting / reference / peripheral / 未标注），段宽 ∝ 页数；条下方标注各区段的七层均值点。

```
全库        █████████ core 1,529 │ ███████████ supporting 1,947 │ ██████ peripheral 1,131
wiki        ███████ core 1,353   │ █████████ supporting 1,675   │ █████ peripheral 860
skills      ██ core 159          │ ██ supporting 191            │ ███ peripheral 230
maintaining █ core 12            │ ██ supporting 42             │ ██ peripheral 33
code        —                    │ █████ supporting 39          │ █ peripheral 8
```

**为什么不用嵌套环**：嵌套环在 86 个域时扇区过窄不可读；堆叠条可向下钻取到域级。

**读法**：左侧（core）越宽说明"高价值页"越多；若某分区 core 极少而 periphery 极多，说明该分区多为索引与参考。

**交互**：点击任一段 → 该分区/域按 tier 过滤的页列表（结构元素 → 证据抽屉）。

**禁止**：把 tier 当质量分排序；tier 是标注，不是评分。

## 2. 拆解树 Decomposition

**问题**：一页/一域到底拆成几段可执行的东西？

**画法**：横向缩进树，节点 = H2/H3，节点右侧挂"载荷徽章"（`表 2 · 码 9 · 图 1`）。层级深度 ≤ 3。

```
MySQL on Kubernetes 生产指南                      落锁 7/7
├─ 1 适用场景与范围
├─ 3 核心概念与架构
│   ├─ 3.1 高可用拓扑           码1
│   └─ 3.2 Operator 选型        表1
└─ 4 标准操作流程                码9 · 表1
    ├─ 4.1 MySQL Operator 部署
    ├─ 4.3 备份                 ▸ L226
    └─ 4.5 故障转移
```

**为什么是树而不是大纲文本**：大纲只给标题；载荷徽章把"这节值不值得读"提前暴露。

**读法**：徽章密集的枝干是可执行的；只有标题没有徽章的枝干是"有划无肉"。

**回溯**：叶子节点显示 `▸ L226`（源文件行号），点击直达阅读页对应行并高亮。

## 3. 一致性热力 Consistency Heatmap

**问题**：同一个维度，哪些域写了、哪些没写？

**画法**：行 = 域（默认按"维度覆盖数"降序），列 = 受控维度（12 个），格三态：

| 态 | 视觉 | 判定 |
|---|---|---|
| 专节（H2） | 实蓝 + 白字 + `H2` 角标 | 一级标题命中 |
| 子节（H3） | 实蓝 + 白字 + `H3` 角标 | 仅在二级标题命中 |
| 提及 | 浅蓝 + 蓝字 | 正文命中 1–2 行 |
| 无 | 琥珀虚框 + `–` | 无匹配 |

> **必须区分 H2 与 H3**：实测 `07` 域"备份"在 H2 命中 0、在 H3 命中 4/4。把两者混为"有"会让读数失去意义；混为"无"会得出错误结论。

**为什么是三态而不是二分**：语料里"提一句"与"成节写"的价值差一个数量级，二分会把两者抹平。

**读法**：
- **横向**看一个域缺哪些维度（该补什么）；
- **纵向**看一个维度在多少域被认真处理（该维度是否成熟）。

**实测参照**（`07 数据库中间件` 的产品页）：备份 4/4 · 监控 4/4 · 高可用 3/4 · 故障转移 3/4 · 连接池 3/4 · 性能调优 2/4 · 扩缩容 1/4。

**禁止**：把"未匹配"渲染成"缺失问题"红色；未匹配可能只是词表没覆盖，界面用中性措辞"未成节"。

## 4. 对比矩阵 Comparison Matrix

**问题**：同一维度下，几个对象差在哪？

**画法**：行 = 实体组（如 4 个数据库），列 = 维度组（如 备份 / 监控 / 高可用）。每格：摘要 ≤ 24 字 + 可行号锚点；空格为琥珀虚线"未写"。

```
            备份恢复          监控告警          高可用
MySQL       XtraBackup ▸L226  PMM ▸L250        InnoDB Cluster ▸L120
TiDB        BR 全量/增量 ▸L310 Prometheus ▸L330 Multi-Raft ▸L88
PostgreSQL  WAL-G PITR ▸L140   exporter ▸L150   CloudNativePG ▸L70
MongoDB     Ops Manager ▸L260  PMM ▸L280        副本集 ▸L95
```

**约束**（硬性）：

1. 同一矩阵内实体必须同 `group`（`entities.json`），否则矩阵无意义；
2. 每格内容必须来自 `triples.json` 的 `evidence`，不得由视图合成；
3. 空格的视觉必须与"有内容"区分，且不得填"无数据"之类占位文本；
4. **维度组而非单一节名**：一列可以映射多个候选小节（见下），并必须展示实际采用的映射。

### 4.1 维度组的映射问题（实测发现，必须解决）

对齐"同一维度"时，不同产品的写法并不对称。以 `07` 域实测：

| 维度组 | MySQL | PostgreSQL | TiDB | MongoDB |
|---|---|---|---|---|
| 备份恢复 | 4.3 备份 | 4.3 备份与 PITR | 6.x 备份/恢复 | 4.4 备份与恢复 |
| 监控告警 | 4.4 监控 | 4.5 监控与告警 | 7.x Monitor/告警 | **无** |
| 高可用 | 3.1 拓扑 + 4.5 故障转移 | 3.1 拓扑 + 4.6 故障转移 | **5.1 扩缩容 + 5.3 节点替换** | 3.4 高可用与拓扑 |

**若严格按节名对齐，会误判 TiDB"缺故障转移"**——实际上它的高可用路径是"扩缩容 + 节点替换"。

**规则**：每个维度组是一组**候选匹配**（`patterns[]`），格子记录 `matchedSection` 与 `mappingNote`（人类可读的一句话说明采用了哪种映射）。当映射偏离默认时，格子右上角出现 `≠` 标记，悬停显示说明。

**禁止**：在未标注映射差异的情况下，把"没匹配上"渲染成"没有能力"。

**读法**：行看一个产品的能力面，列看一个维度的成熟度。

## 5. 关系邻域 Neighborhood

**问题**：读完这篇，接下来该读哪几篇？

**画法**：以选中页为圆心，只画 2 跳；半径 = log(入链数)，颜色 = 分区，边 = 库内 wikilink。

```
            etcd(353)            Prometheus(457)
                \                     /
                 \                   /
            ─── Kubernetes(1,648) ───   ← 圆心
                 /                   \
            kubelet(314)         Automation(316)
```

**为什么只画 2 跳**：4,815 节点的全图不可读也不可交互；2 跳足以回答"下一步读什么"。

**默认中心**：全网入链最高页（当前 `Kubernetes` 1,648）。

**读法**：圆心是"锚"，外圈是"入口"；从外圈进入比从搜索进入的路径短。

**禁止**：力导向动画自动漂移（用户失去空间记忆）；边数 > 400 时不画边只画节点。

## 6. 演化时间线 Evolution

**问题**：知识怎么长出来的？哪些是"赶出来的薄页"？

**画法**：横轴月份（≤ 36），纵轴页数，堆叠按落锁层数（0–2 层 / 3–5 层 / 6–7 层）分三段；叠加一层"某域层演变"的标尺。

**实测参照**：全库只有 8 个月份有数据，`2026-05` 集中 2,410 页、`2026-07` 1,476 页——两次大搬迁的痕迹清晰可见。

**读法**：某月柱体以"0–2 层"为主 → 该批是批量导入的薄页；某月以"6–7 层"为主 → 该批是补成熟的。

**禁止**：用面积图；用累计曲线掩盖批次特征。

## 7. 视图间不重复原则

| 结论 | 只出现在 |
|---|---|
| 每层落锁多少页 | 构成剖面（不重复到热力） |
| 某域缺哪一层 | 一致性热力 |
| 某产品缺哪一维 | 对比矩阵 |
| 某页拆成几段 | 拆解树 |
| 谁引用谁 | 关系邻域 |
| 何时批量生成 | 演化时间线 |

若两个视图能回答同一问题，**删除弱的那一个**。

## 8. 图表的文字规范

数字与标签是图表的一半。以下规则对所有视图生效：

| 规则 | 正例 | 反例 |
|---|---|---|
| 每张图必须有**标题说结论**，不只说主题 | 「07 域 45% 的页面写了备份」 | 「维度覆盖」 |
| 数字带单位与口径 | `27 页（H2/H3 命中）` | `27` |
| 百分比分母必须写清 | `4/4 产品页` | `100%` |
| 未命中用词统一 | 「未成节」 | 「无」「缺失」「N/A」混用 |
| 空态要有下一步 | 「该筛选无结果 · 清除筛选」 | 「暂无数据」 |
| 悬停提示带来源 | 「来自 4.3 备份 · L226」 | 「点击查看」 |

**禁止**：在没有分母的情况下写百分比；用「+120%」这类没有基数的增长数字。

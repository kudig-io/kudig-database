# Console 路线图与实施计划

> 原则：**先让数据可信，再让视图好看**。每一期都必须独立可验收，不依赖下一期才能用。

## 1. 里程碑总览

| 期 | 主题 | 交付 | 出口标准 | 依赖 |
|----|------|------|----------|------|
| M0 | 设计冻结 | PRD、数据契约、可视化规范、交互规范、验收标准 | 文档评审通过 | — |
| M1 | 块级抽取 | `blocks.json` + 拆解树 + 构成剖面 | 86 域全部可拆；锚点 100% | M0 |
| M2 | 维度对齐 | `dimensions.json` + 一致性热力 | `07` 域热力与实测一致 | M1 |
| M3 | 实体对照 | `entities.json` + `triples.json` + 对比矩阵 | 3 个真实选型场景可完成 | M2 |
| M4 | 关系与演化 | 关系邻域 + 演化时间线 | 2 跳邻域可用；月份批次可识别 | M1 |

## 2. 分阶段细节

### M1 · 块级抽取（基础）

**要做什么**
- 生成器新增 `segment_blocks()`：在现有 `segment()` 基础上保留行号与章节边界；
- 产出 `data/blocks.json`（格式见 `data-contract.md` §3）；
- 前端新增"拆解树"与"构成剖面"两个视图，替换现有的"分层谱"（分层谱降为构成剖面的一种口径）。

**验收**
- 随机 20 页，节点的 `start/end` 行号与源文件一致；
- 任一叶子的"载荷徽章"数字与 `blocks.json` 一致；
- 86 域全部可展开，无空白树。

**风险**：行号偏移（frontmatter、`<!-- chunk -->` 注释）——处理方式：以**去除 frontmatter 后**的正文行号为基准，并在 `blocks.json` 记录 `lineBase: "body"`。

### M2 · 维度对齐

**要做什么**
- 建立 `dimensions.json`（12 个维度，见数据契约 §4.1）；
- 生成 `triples.json`（仅 `source: heading` 的强匹配先上）；
- 前端新增一致性热力。

**验收**：`07 数据库中间件` 的 4 个产品页在 7 个运维维度上的态与人工核对一致；全库热力中"专节"格数不少于 300。

**风险**：中文维度词匹配过宽（"故障"命中"容错"）——用"标题级匹配"而非正文匹配，命中率换准确率。

### M3 · 实体对照

**要做什么**
- `entities.json`（先做 database 组 5 个实体，验证机制后再扩展）；
- 扩充 `triples.json` 至 `source: table | strong`；
- 前端新增对比矩阵，支持选择实体组 × 维度组。

**验收**
- 矩阵中每格可定位到原页行号；
- 空格必须为空（断言 `data-state="absent"`）；
- S1/S2/S3 三个场景人工完成。

**风险**：实体同义词覆盖不足导致矩阵大量空白——上线前用 `07` 域 4 个产品做覆盖率验收，< 70% 则先补词表。

### M4 · 关系与演化

**要做什么**
- 复用现有 `index.json` 的 `out`/`in` 构建 2 跳邻域；
- 时间线基于 `date` 与 `layers` 聚合。

**验收**：默认中心为 `Kubernetes`；邻域 ≤ 60 节点；时间线能识别 `2026-05`（2,410 页）与 `2026-07`（1,476 页）两个批次。

## 3. 工作分解（以人日估）

| 任务 | 角色 | 人日 |
|------|------|-----:|
| M0 文档评审与冻结 | 产品 + 设计 | 1 |
| M1 `blocks.json` 生成器 | 数据 | 2 |
| M1 拆解树视图 | 前端 | 3 |
| M1 构成剖面视图 | 前端 | 2 |
| M2 维度词表 + 抽取 | 数据 | 2 |
| M2 热力视图 | 前端 | 2 |
| M3 实体词表 + 三元组 | 数据 | 3 |
| M3 对比矩阵视图 | 前端 | 3 |
| M4 邻域 + 时间线 | 前端 | 4 |
| 全程：断言脚本 + 视觉审阅 | 测试 | 3 |

> 合计约 25 人日；不含 Mermaid 渲染与现有阅读页（已建）。

## 4. 优先级判断依据

| 候选能力 | 用户价值 | 实现成本 | 决策 |
|---|---|---|---|
| 拆解树 | 高（每页都适用） | 低 | **M1 必做** |
| 一致性热力 | 高（回答"哪里薄"） | 中 | **M2 必做** |
| 对比矩阵 | 最高（选型核心） | 中高 | **M3 必做** |
| 关系邻域 | 中（导航辅助） | 低 | M4 |
| 演化时间线 | 中（治理视角） | 低 | M4 |
| 语义检索（embedding） | 高 | 高（新依赖） | **暂不做**，等结构视图稳定后再评估 |
| 全库力导向图 | 低（不可读） | 中 | **不做** |

## 5. 退出与回退条件

- 任一里程碑的验收未过 → **不进入下一期**，先补该期；
- 若 M2 词表覆盖率 < 60% → 回退到"仅按 H2 标题名精确匹配"，放弃跨页对齐，热力只做"有/无"两态；
- 若 M3 矩阵空格率 > 60% → 输出降级为"仅列出有内容的格（无矩阵）"。

## 6. 长期演进（不在本期范围）

1. **Agent 消费接口**：把 `triples.json` 作为 RAG 的结构化语料，提供"按维度检索页面"的 API；
2. **写作辅助**：给维护者一个"该域还缺哪个维度"的待办清单；
3. **跨库对齐**：与 `ai-guru` 等同源语料库做结构对照（见 `maintaining/HANDOFF.MD` 的划界记录）。

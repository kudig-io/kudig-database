# 结构视图走查：以「07 数据库中间件」为例

## 2. 拆解树：这页到底拆成几段

```
MySQL on Kubernetes 生产指南              7/7 层 · 正文 261 行 · 表 23 行 · 码 10 · ops-heavy
├─ 1 适用场景与范围              [L12 –L21 ]  0 码
├─ 2 前置条件与工具              [L22 –L41 ]  码 ?
├─ 3 核心概念与架构              [L42 –L67 ]  表 1（L48 起）
├─ 4 标准操作流程                [L68 –L215]  主体
├─ 5 关键检查点与验证命令         [L216–L226]
├─ 6 常见故障与 remediation      [L227–L238]
├─ 7 风险与注意事项              [L239–L249]
└─ 8 相关 Runbook / 推荐阅读     [L250–L261]
```

> 上表 H2 起始行号取自源文件正文（去除 frontmatter，1-based），可直接复算：
> ```bash
> python3 - <<'EOF'
> import re, pathlib
> raw = pathlib.Path('wiki/06-存储与数据/09-数据库/17-mysql-kubernetes-production-guide.md').read_text()
> body = raw.split('---', 2)[2]
> for i, line in enumerate(body.split('\n'), 1):
>     if re.match(r'^##\s+\S', line): print(i, line.strip())
> EOF
> ```
> 节内载荷（表格行数、代码块数）与 H3 子节由 `blocks.json` 给出；本文未逐一列出，避免写出未经生成器确认的数字。

**它揭示的结构事实**：8 个 H2 覆盖 261 行，正文最重的一节是第 4 节「标准操作流程」（L68–L215，约占全文 57%）。**它是一本操作手册，不是一篇综述**——这正是"页形 = ops-heavy"的含义。

## 3. 一致性热力：07 域在 12 个维度上的覆盖

| 维度 | 专节页数 / 70 | 说明 |
|---|---:|---|
| 故障排查 | 27 | 最普遍的论题 |
| 概述 | 20 | 多为"适用场景" |
| 监控告警 | 20 | |
| 最佳实践 | 19 | |
| 性能调优 | 15 | |
| 架构与核心概念 | 11 | |
| 生产部署 | 10 | |
| 运维操作 | 10 | |
| 架构设计 | 9 | |
| 核心组件配置 | 9 | |
| 备份 | *（待生成）* | **关键发现**：没有任何一页的 H2 叫"备份"——MySQL/PostgreSQL/TiDB/MongoDB 都把它放在 `4.3`/`6.x`/`4.4` 的 **H3 层**。只看 H2 会误判"07 域不写备份" |
| 扩缩容 | *（待生成）* | 同样藏在 H3（MySQL 有 `4.x`，TiDB 有 `5.1 水平扩缩容`） |

**上面这组数只统计 H2**：`07` 域 60 个非索引页中，"故障排查"作为 H2 出现在 27 页。

**由此得到两条口径**：

| 判定层 | 含义 | 例 |
|---|---|---|
| **专节**（H2 命中） | 该维度在域层面已成体系 | 故障排查 27/60 页 |
| **子节**（H3 命中） | 该维度存在但被归入别的章 | 备份：4 个产品页全部写在 H3（4.3 / 6.x / 4.4） |

> **这是本设计的第一个硬约束**：热力与矩阵不能只看 H2。备份在 07 域 H2 命中 **0**、H3 命中 **4/4**——只看 H2 会把一个成熟维度判成"缺失"。数据契约因此要求 `sections[]` 同时记录 `level: 2 | 3`，热力格必须显示命中层级（`H2` 徽章 / `H3` 徽标）。

## 4. 对比矩阵：4 个产品 × 3 个运维维度

| | 备份恢复 | 监控告警 | 高可用 / 故障转移 |
|---|---|---|---|
| **MySQL** | 4.3 备份 | 4.4 监控 | 3.1 高可用拓扑 · 4.5 故障转移 |
| **PostgreSQL** | 4.3 备份与 PITR | 4.5 监控与告警 | 3.1 高可用拓扑 · 4.6 故障转移 |
| **TiDB** | 6.1 S3 备份配置 · 6.2 定时备份 · 6.3 恢复流程 | 7.1 TiDB Monitor · 7.2 关键告警规则 | 5.1 水平扩缩容 · 5.3 TiKV 节点替换 |
| **MongoDB** | 4.4 备份与恢复 | **— 未成节** | 3.4 高可用与拓扑分布 |

> 本表的小节号与标题来自四篇原文的 H3 大纲（已核对）；**行号锚点待 `blocks.json` 生成后补齐**，在补齐前该矩阵以"图例态"呈现，不发布带行号的版本。

**空格的处理**：MongoDB 页的 H3 大纲里**没有**监控/告警小节（3.x 与 4.x 共 13 个子节，无一命中），矩阵显示为琥珀虚线 `未成节`，并附一句"该页仅在正文零散提及指标"。**不得**从 PostgreSQL 页抄一段补进去。

**同时暴露一处口径问题**：TiDB 页没有"故障转移"子节，它的高可用是"扩缩容 + 节点替换"（5.1/5.3），而 MySQL/PostgreSQL 是"拓扑 + 故障转移"（3.1/4.x）。**若矩阵强行按同一维度对齐，会得出"TiDB 缺失故障转移"的错误结论**。处置：矩阵的列必须是"维度组"，每格允许挂**多个候选小节**，并在格子下方注明实际采用的映射（`故障转移 ⇒ 5.3 TiKV 节点替换`）。

**这张表回答了 S1 场景**（"MySQL 与 TiDB 在备份和高可用上差在哪"）：不需要读 4 篇 × 250 行，看 3 列即可。

## 5. 关系邻域：从 MySQL 页出发的 2 跳

```
             etcd(353)                 Prometheus(457)
                   \                         /
              Kubernetes(1,648) ────────────┘
                   /         \
            kubelet(314)   Automation(316)

  本页 out-link 指向的页面（07 域实测：出链中位 2、均值 2.8）会落在上述任一邻居周围
```

> 图中节点与数值来自 `structure.json` 的 `hubs`（实测入链数）；本页的出边在 `index.json` 的 `out` 字段，渲染时按实际边绘制，本文不虚构边。

**视图规则**：本页的 `out` 平均只有 2–3 条（07 域实测中位 2、均值 2.8），所以它的邻域**天然稀疏**——这本身是一个可展示的事实：**操作手册类页面不承担导航职责**，导航由域入口页与中心页承担。

## 7. 这次走查暴露的设计问题（已回流到文档）

| # | 问题 | 处置 |
|---|---|---|
| 1 | "备份恢复"在 07 域从未作为 H2 出现，但实际内容存在（子节级） | 热力必须支持 **H3 级匹配**，不能只看 H2；已在数据契约补充 |
| 2 | 操作手册类页面 out-link 极少，邻域图会空 | 邻域视图对 `out < 3` 的页自动回退为"所在域的入口页邻域" |
| 3 | 代码块语言大量未标注（实测 `fence` 只有 bash/sql 各 1，其余 8 块未标注） | 拆解树不按语言分色，只给"码 N"总数 |
| 4 | 页形分类里 60 页有 49 页是 ops-heavy，分类过粗 | 拆解树不依赖页形，页形只用于构成剖面的图例 |

# 云原生演进故事——从物理机到 [[Kubernetes|Kubernetes]]

> **阅读建议**: 本文是 K8s 学习的第一课。不要急着学概念，先听故事。故事听懂了，后面每个技术点都会水到渠成。  
> **目标**: 读完能向朋友讲清楚"为什么需要 K8s"，并能画出技术演进时间线。

---

## 序幕：一个创业公司的部署之痛

2026 年，张三创业做电商网站。他的故事，就是过去 30 年 IT 基础设施演进的缩影。

---

## 第一章：物理机时代（1990s-2000s）

### 1.1 故事：张三买了 10 台服务器

张三的电商网站上线了。他买了 10 台物理服务器：

- 2 台跑 Web 服务（Nginx + 应用代码）
- 2 台跑数据库（MySQL）
- 2 台跑缓存（Redis）
- 2 台跑搜索（Elasticsearch）
- 2 台备用（怕坏）

每台服务器 2U 高，重 20 公斤，放在机房里嗡嗡作响。

### 1.2 痛点一：资源利用率极低

张三发现：**每台服务器的 CPU 利用率只有 10%-15%**。

为什么？因为每台服务器只跑一个应用，为了应对"双十一"峰值，他必须按峰值采购。但一年 365 天，峰值只有 1 天。

> **类比**：就像你为了过年请客买了 10 口锅，但平时只用 1 口炒菜，另外 9 口在橱柜里吃灰。

### 1.3 痛点二：扩容像搬家

网站流量涨了，张三需要加一台服务器。流程是：

1. 采购硬件（2-4 周）
2. 机房上架（1 天）
3. 安装操作系统（1 天）
4. 配置网络（1 天）
5. 部署应用（1 天）
6. 接入负载均衡（半天）

**扩容一次 = 一个月**。

等服务器到位，促销活动早就结束了。

### 1.4 痛点三：环境不一致

开发环境、测试环境、生产环境是三台不同的服务器。经常出现：

> "我本地跑得好好的啊！"

因为开发机的库版本是 2.1，生产机是 2.0，一个依赖不匹配就崩了。

---

## 第二章：虚拟机时代（2000s-2010s）

### 2.1 故事：VMware 来了

张三听说了**虚拟机（VM）**技术。一台物理服务器上可以跑多个虚拟机，每个虚拟机就像一台独立的服务器。

他把 10 台物理机缩减到 3 台，每台跑 5-6 个虚拟机。

### 2.2 解决的痛点

| 痛点 | 虚拟机如何解决 |
|------|--------------|
| 资源利用率低 | 一台物理机跑多个 VM，CPU 利用率提升到 50%+ |
| 扩容慢 | 克隆一个 VM 模板，5 分钟启动一台"新服务器" |
| 环境不一致 | 整个 VM（OS + 依赖 + 应用）打包成镜像，到处运行 |

### 2.3 新的痛点

#### 痛点一：虚拟机太重了

每个虚拟机都要跑一个完整的操作系统：

- Windows Server：20GB 磁盘起步
- CentOS：5GB 起步
- 内存占用：2GB-8GB 起步

10 个虚拟机 = 10 个操作系统 = 大量资源浪费在"操作系统本身"。

> **类比**：虚拟机就像每家每户都有一栋独立别墅，虽然住了人，但花园、车库、锅炉房都是重复的。

#### 痛点二：启动慢

启动一个虚拟机 = 启动一个操作系统 = **1-3 分钟**。

对于需要快速扩容的场景（比如秒杀活动），1-3 分钟太慢了。

#### 痛点三：镜像太大

一个 VM 镜像 10GB-50GB，传输一次要半小时。CI/CD 流水线每次构建都打包整个 VM？不可能。

## 第三章：容器时代（2013-2015）

### 3.1 故事：Docker 横空出世

2013 年，Docker 发布了。张三试了一下，惊呆了：

```bash
# 启动一个 Nginx 容器
docker run -d -p 80:80 nginx
```

**1 秒钟，Nginx 跑起来了。**

### 3.2 容器是什么？

容器不是虚拟机。它不需要完整的操作系统。

```
虚拟机架构：
┌─────────────────┐ ┌─────────────────┐
│   App A + Libs  │ │   App B + Libs  │
├─────────────────┤ ├─────────────────┤
│   Guest OS      │ │   Guest OS      │
├─────────────────┤ ├─────────────────┤
│   Hypervisor    │ │   Hypervisor    │
├─────────────────┴─┴─────────────────┤
│           Host OS                    │
└─────────────────────────────────────┘

容器架构：
┌─────────┐ ┌─────────┐
│ App+Libs│ │ App+Libs│
├─────────┤ ├─────────┤
│ 容器引擎 │ │ 容器引擎 │
├─────────┴─┴─────────┤
│      Host OS         │
└─────────────────────┘
```

**关键区别**：容器共享宿主机的操作系统内核，每个容器只打包应用和依赖，不打包操作系统。

### 3.3 解决的痛点

| 痛点 | 容器如何解决 |
|------|-------------|
| 虚拟机太重 | 容器镜像只有几十 MB（Alpine 基础镜像 5MB） |
| 启动慢 | 容器启动 = 进程启动 = **毫秒级** |
| 镜像大 | 镜像分层存储，共用基础层，传输快 |
| 环境不一致 | "Build Once, Run Anywhere" — 一次构建，到处运行 |

### 3.4 张三的容器化改造

张三把电商网站拆成了 6 个容器：

```
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│   Web 前端   │  │   订单服务   │  │   支付服务   │
│  (Nginx)    │  │  (Node.js)  │  │   (Java)    │
└─────────────┘  └─────────────┘  └─────────────┘
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│   MySQL     │  │    Redis    │  │ Elasticsearch│
└─────────────┘  └─────────────┘  └─────────────┘
```

每个服务独立开发、独立部署、独立扩容。

### 3.5 新的痛点：容器多了怎么管？

容器化半年后，张三有 50 个容器运行在 5 台服务器上。新问题出现了：

#### 痛点一：容器该放哪台服务器？

```
服务器 A：10 个容器（CPU 90%）
服务器 B：5 个容器  （CPU 30%）
服务器 C：15 个容器（CPU 95%，快崩了）
服务器 D：8 个容器  （CPU 50%）
服务器 E：12 个容器（内存不足，OOM）
```

**手动分配容器到服务器？太累了。**

#### 痛点二：容器挂了怎么办？

凌晨 3 点，支付服务容器崩溃。用户无法付款，订单流失。

张三被报警叫醒，手动登录服务器，重启容器。等他重启完，已经损失了 100 单。

**能不能容器挂了自动重启？**

#### 痛点三：流量怎么分发？

3 个 Web 前端容器跑在不同的服务器上，用户访问哪个？

张三手动在 Nginx 里配置 upstream，每次扩容/缩容都要改配置、重载 Nginx。

**能不能自动发现新容器并分配流量？**

#### 痛点四：配置怎么管理？

50 个容器，每个都有数据库密码、API Key。密码要定期更换。

张三把密码写在代码里，每次改密码都要重新构建镜像、重新部署 50 个容器。

**能不能配置外置化，不改镜像就能换密码？**

#### 痛点五：存储怎么办？

容器是无状态的，重启后数据丢失。但 MySQL 的数据必须持久化。

张三把 MySQL 数据挂载到宿主机目录。但容器漂移到另一台服务器时，数据就不在了。

**能不能存储也跟着容器走？**

## 第四章：编排时代（2015-至今）

### 4.1 故事：Kubernetes 登场

Google 说："我们内部叫 Borg，运行了 10 年管理几十亿容器。现在我们把它开源了，叫 Kubernetes（希腊语'舵手'）。"

2015 年，K8s 1.0 发布。CNCF（云原生计算基金会）成立。

张三把 50 个容器交给了 K8s。

### 4.2 K8s 如何解决五大痛点

#### 痛点一：容器该放哪台服务器？

**K8s 方案：调度器（Scheduler）**

```yaml
apiVersion: v1
kind: Pod
spec:
  containers:
  - name: payment-service
    image: payment:v2
  resources:
    requests:
      memory: "512Mi"
      cpu: "500m"
```

你告诉 K8s："这个容器需要 512MB 内存、0.5 核 CPU。" K8s 自动找一台资源够的服务器放进去。

> **类比**：就像你去餐厅，服务员（Scheduler）根据每桌人数自动安排座位，你不用自己找桌子。

#### 痛点二：容器挂了怎么办？

**K8s 方案：控制器（Controller）—— 自我修复**

```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  replicas: 3  # 始终保持 3 个副本
```

你告诉 K8s："这个服务我要 3 个副本。" K8s 保证永远有 3 个在运行。挂一个，自动启动一个新的。

> **类比**：就像你雇了 3 个收银员，有人请假了，HR 自动招一个临时工顶上。

#### 痛点三：流量怎么分发？

**K8s 方案：Service —— 服务发现与负载均衡**

```yaml
apiVersion: v1
kind: Service
spec:
  selector:
    app: web-frontend  # 自动找到所有标签匹配的 Pod
  ports:
  - port: 80
```

你创建一个 Service，K8s 自动把所有标签匹配的 Pod 挂到负载均衡后面。扩容新 Pod，自动加入；缩容旧 Pod，自动移除。

> **类比**：就像餐厅的总机号（Service IP），顾客打总机，自动转接到空闲的分机（Pod），你不用记每个分机的号码。

#### 痛点四：配置怎么管理？

**K8s 方案：ConfigMap / Secret —— 配置外置化**

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-password
data:
  password: c2VjcmV0MTIz  # base64 编码
```

密码存在 K8s 里，容器通过环境变量或挂载文件读取。换密码？改 Secret，不用重新构建镜像。

> **类比**：就像员工卡（Secret）统一由 HR 管理，员工（容器）入职时领卡，离职时回收。换门禁密码，不用重新装修办公室。

#### 痛点五：存储怎么办？

**K8s 方案：PV / PVC —— 存储抽象**

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 10Gi
```

你告诉 K8s："我要 10GB 的存储。" K8s 自动从存储池里分配一块，挂给容器。容器漂移到哪台服务器，存储跟着走。

> **类比**：就像云盘（PV），你在公司电脑（Pod A）编辑的文件，回家在笔记本（Pod B）上打开，文件是一样的。

## 第五章：K8s 全景图

听完故事，现在看 K8s 的每个组件，你都能知道它解决什么问题：

```
┌─────────────────────────────────────────────────────────────┐
│                         用户 / 开发者                          │
├─────────────────────────────────────────────────────────────┤
│  kubectl apply -f app.yaml    ← 声明式配置（告诉 K8s 我要什么） │
├─────────────────────────────────────────────────────────────┤
│                     Kubernetes 控制平面                        │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────┐  │
│  │ API Server  │  │   etcd      │  │  Scheduler          │  │
│  │ (统一入口)   │  │ (配置数据库) │  │  (调度器：放哪台机器？)│  │
│  └─────────────┘  └─────────────┘  └─────────────────────┘  │
│  ┌─────────────────────────────────────────────────────────┐│
│  │ Controller Manager（控制器：保持状态一致）                  ││
│  │  - Deployment Controller：保持 3 个副本                   ││
│  │  - Node Controller：节点挂了要处理                         ││
│  │  - Endpoint Controller：Service 后端列表维护               ││
│  └─────────────────────────────────────────────────────────┘│
├─────────────────────────────────────────────────────────────┤
│                      Kubernetes 工作节点                       │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────┐  │
│  │   kubelet   │  │ kube-proxy  │  │   Container Runtime │  │
│  │ (节点管家)   │  │ (网络代理)   │  │   (docker/containerd)│  │
│  └─────────────┘  └─────────────┘  └─────────────────────┘  │
├─────────────────────────────────────────────────────────────┤
│                         基础设施                               │
│           物理机 / 虚拟机 / 云服务器（EC2/ECS）                  │
└─────────────────────────────────────────────────────────────┘
```

## 第六章：演进时间线

| 年代 | 技术 | 核心问题 | 解决方式 |
|------|------|---------|---------|
| 1990s | 物理机 | 资源利用率低、扩容慢 | 买更多机器 |
| 2000s | 虚拟机 | 物理机资源浪费、环境不一致 | 一台机器切多份 |
| 2013 | Docker | VM 太重、启动慢 | 共享操作系统内核 |
| 2015 | Kubernetes | 容器多了怎么管 | 自动调度、自愈、服务发现 |
| 2018 | Service Mesh | 微服务间通信复杂 | Sidecar 代理（[[Istio|Istio]]） |
| 2020 | GitOps | 部署流程不规范 | Git 作为单一事实来源 |
| 2024 | AI + K8s | AI 训练任务调度 | KubeFlow、Kueue |

## 总结：三个核心思想

### 思想一：分层抽象

每一层都在隐藏下一层的复杂性：

```
应用开发者 ← 只看 Pod/Deployment/Service
     ↑
平台工程师 ← 看 K8s 架构/调度/网络
     ↑
基础设施    ← 看服务器/网络/存储
```

**你不需要懂所有层，但要清楚自己处在哪一层。**

### 思想二：声明式而非命令式

传统方式（命令式）："去服务器 A 上启动一个容器"

K8s 方式（声明式）："我要 3 个副本，你来保证"

**你描述" desired state "（期望状态），系统负责达到并维持这个状态。**

### 思想三：一切皆资源

K8s 中，一切都是可以用 YAML 描述的资源对象：

- Pod、Deployment、Service → 应用资源
- ConfigMap、Secret → 配置资源
- PV、PVC → 存储资源
- Node → 计算资源
- Namespace → 隔离资源

**学习 K8s = 学习这些资源对象的属性、关系和生命周期。**

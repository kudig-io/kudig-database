## Q1. 容器和虚拟机的本质区别？（容器基础）

**一句话**｜容器是共享宿主内核的进程，隔离靠 namespace（视图）+ cgroup（限额）+ capabilities/seccomp（削权）；VM 靠 hypervisor 虚拟硬件、每个带独立内核——容器省掉"每份一个内核"，代价是隔离性。

**30 秒答**｜四维对比：①启动——容器 fork 进程级毫秒起，VM 引导内核分钟级；②镜像——MB 级分层共享 vs GB 级整盘；③密度——单机数百容器 vs 数十 VM；④隔离——VM 内核漏洞不穿透 hypervisor，容器共享内核：内核 panic 全体陪葬、内核漏洞全量暴露。判断线：多租户强隔离/异构 OS → VM；高密度微服务 → 容器；既要容器体验又要 VM 隔离 → 沙箱容器（Kata = 每 Pod 一个 microVM；gVisor = 用户态内核拦 syscall）。

**弹药**
- `ls -l /proc/$$/ns/` — 当前 shell 的 namespace 视图
- Kata Containers：对接 CRI/OCI 生态的 microVM runtime；gVisor runsc：用户态内核（Sentry）实现 syscall 代理
- 阿里云 ACK 安全沙箱容器：基于神龙 + Kata 的强隔离节点池
- 深挖：[[wiki/14-容器运行时/00-总览/03-container-internals-deep-dive.md|容器本体深挖]] §1.1

**红线**｜❌ "容器就是轻量级虚拟机"——轻在共享内核，不是"缩小版 VM"，面试官会顺势追问轻在哪；❌ 说容器隔离性和 VM 一个级别。

## Q2. Namespace 和 cgroup 各管什么？cgroup v1/v2 差在哪？（内核机制）

**一句话**｜namespace 管"看得见什么"（视图隔离八种），cgroup 管"用得了多少"（资源配额）；v1 每个子系统一棵树、v2 统一单树 + 叶子挂进程 + PSI 压力信号。

**30 秒答**｜八种 namespace：pid（进程号）、net（网络栈）、mnt（挂载点/rootfs）、uts（hostname）、ipc、user（UID/GID 映射，**rootless 基石**）、cgroup（cgroup 根视图）、time（5.6+）。报全八种并说出 user ns 的地位，是 expert 和熟手分界。cgroup v1：cpu/memory/blkio 各一棵树，配置割裂、子系统间易不一致；v2：统一单棵层级树、进程只挂叶子、内存/IO 统一账本（memory.stat 打通）、新增 PSI（`cpu.pressure`/`memory.pressure`/`io.pressure`）供驱逐和监控用。K8s 1.25 起 cgroup v2 GA。判断线：新系统上答 v1 路径（`memory.limit_in_bytes`）是过时信号，v2 是 `memory.max`/`cpu.max`。

**弹药**
- `lsns` — 列出系统所有 namespace 及进程；`readlink /proc/<pid>/ns/pid` 比对两个进程是否同 ns
- v2 核心文件：`cpu.max`（"quota period"，如 200000 100000 = 2 核）、`memory.max`、`memory.current`、`memory.events`（oom_kill 计数）
- kubelet 与 containerd 的 cgroup driver 必须一致（`K8s·Q15`）

**红线**｜❌ 说反——namespace 做限额、cgroup 做隔离；❌ 只报 pid/net/mnt 三种就停。

## Q3. OverlayFS 怎么实现镜像分层？为什么容器里删文件不省空间？（镜像/存储）

**一句话**｜镜像只读层 = lowerdir、容器可写层 = upperdir 联合挂载；首次写触发 copy-up、删除写 whiteout 遮蔽——lower 层原文件纹丝不动，所以 rm 不省磁盘、镜像不变小。

**30 秒答**｜三动作：**读**自上而下逐层找；**写**命中 lower 层就整文件 copy-up 到 upper 再改（改 1 字节也整拷几百 MB 文件），新文件直接进 upper；**删**在 upper 放 whiteout（字符设备 0:0）遮住 lower 层文件。容器 `rm` 大文件只是"遮住"，磁盘不回收，真正回收靠运行时 GC 或重新构建。为什么选 overlay2：内核原生（4.0+）、页粒度 COW、支持约 128 层 lower，淘汰了 aufs/devicemapper。

**深挖：容器内三步验证**
```bash
# 容器内
echo hi > /usr/bin/testfile && rm /usr/bin/testfile
cat /proc/mounts | grep overlay        # 看到自己的 lowerdir/upperdir
# 宿主机按 upperdir 路径查看：
ls <upperdir>/usr/bin/                 # testfile 变成 c 0,0 的 whiteout 设备文件
```
containerd 侧快照在 `/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/`，内容寻址 sha256。

**弹药**
- `ctr snapshots ls` — containerd 快照全量视图
- `dmesg | grep overlay` — 磁盘满时 copy-up Enospc 报错
- 深挖：[[wiki/14-容器运行时/04-镜像构建/06-image-layer-optimization.md|镜像层优化]]

**红线**｜❌ "容器删除文件后磁盘会释放/镜像变小"；❌ 把镜像层和容器可写层混为一谈——image 层多容器共享只读，写时各自 COW 到自己的 upper。

## Q4. `docker run` 背后的完整链路？为什么 dockerd 重启容器不死？（运行时架构）

**一句话**｜CLI → dockerd → containerd → 每容器一个 containerd-shim → runc；runc 建好 namespace/cgroup 并 exec 用户进程后**立即退出**，shim 常驻接管——容器进程的父是 shim 不是 dockerd，生命周期解耦。

**30 秒答**｜逐跳：①CLI 经 `/var/run/docker.sock`（REST over unix socket）调 dockerd；②dockerd 管镜像/认证/网络/卷，向 containerd 发 gRPC；③containerd 是常驻"容器管家"（CNCF 毕业）：镜像存储/快照/元数据，为每容器 fork 一个 **containerd-shim-runc-v2**；④shim 调 runc：设 namespace → 写 cgroup → rootfs + pivot_root → exec 用户进程，**runc 完成即退**；⑤shim 常驻：转发 stdio、收集 exit code、上报事件。判断线："dockerd 重启容器不死"的原因就是 shim——父进程解耦 + exit code 由 shim 保存，这是 shim 存在的全部意义。K8s 链路：kubelet → CRI → containerd → shim，1.24 起 dockershim 移除、不再经过 docker（`K8s·Q18`）。

**弹药**
- `ps -ef --forest | grep -A2 containerd-shim` — 进程树：containerd → shim → 应用
- `crictl ps` — 直连 containerd 跳过 docker；`ctr -n moby containers ls` 看 dockerd 的 containerd namespace
- `runc spec && runc run mybox` — 最小容器 = 一个 spec.json
- 深挖：[[wiki/14-容器运行时/03-containerd-CRI-O/11-cri-interface-internals.md|CRI 接口内幕]] · [[wiki/14-容器运行时/03-containerd-CRI-O/04-oci-runtimes-comparison.md|OCI 运行时对比]]

**红线**｜❌ "dockerd 挂了容器也挂"（shim 解耦后不会；docker v1 时代 dockerd 直管时确实会，老八股注意区分年代）；❌ 说 kubelet → docker → containerd（1.24+ 已删 dockershim）；❌ 分不清 runc（OCI runtime，一次性）和 containerd（常驻管理面）。

## Q5. `docker exec` 进容器的原理？exec 起的进程是谁的儿子？（运行时/ns 操作）

**一句话**｜拿容器主进程的 `/proc/<pid>/ns/*` 句柄，setns() 依次加入各 namespace 再 fork-exec 目标命令——进程活在宿主机进程树上，父进程是 shim、与容器 PID 1 平级。

**30 秒答**｜步骤：①找到容器主进程宿主机 PID；②open `/proc/<pid>/ns/{mnt,net,pid,ipc,uts}`；③依次 setns()——**user ns 必须最先**，pid ns 要 setns 后再 fork 才对子进程生效；④exec 命令，stdio 经 shim 管道接回终端。证据：宿主机 `ps -ef` 能看到 exec 起的进程。两个推论：exec 不是"再起一个容器"；exec 进程不是 PID 1 的子进程——它自己退出由 shim 收尸，它产生的孤儿才 reparent 给 PID 1。docker daemon 挂了还能进：`nsenter -t <主进程PID> -m -n -p -i -u bash`。

**弹药**
- `nsenter` — 不依赖 docker 的 ns 进入工具，排障救命招
- `lsns` — 全系统 namespace 清单；`readlink /proc/<pid>/ns/pid` 验证进入前后变化
- 深挖：[[wiki/14-容器运行时/00-总览/03-container-internals-deep-dive.md|容器本体深挖]] §3.2

**红线**｜❌ 说 exec 是"ssh 进容器"；❌ 说 exec 进程是容器 PID 1 的子进程（平级，父是 shim）。

## Q6. 容器里 PID 1 特殊在哪？`docker stop` 为什么要等满 10 秒？（进程模型）

**一句话**｜内核给 PID 1 两个特权：未注册 handler 的信号直接丢弃（shell 当 1 号位 kill 不掉）+ 收养孤儿但必须 wait（不收尸就僵尸堆积）——解法是 exec 直启入口或 tini。

**30 秒答**｜两个坑：①**信号**——普通进程未注册 SIGTERM handler 走默认动作（杀），PID 1 未注册的信号被内核丢弃（假设 init 有自己的清理逻辑）；shell 当 1 号位不转发 SIGTERM 给子进程 → `docker stop` 宽限期默认 10s 耗尽被 SIGKILL——这就是"stop 总要等满 10 秒"的经典根因。②**僵尸**——父进程先死的进程被 PID 1 收养，PID 1 不循环 wait 就堆积 Z 状态（Nginx master 不收 worker 僵尸是真实事故）。解法：入口脚本 `exec java -jar ...` 让主进程顶替 shell 当 1 号位；或 `docker run --init`（内置 tini：转发 SIGTERM + 循环 wait）。K8s：`shareProcessNamespace: true` 后 Pod 级 PID 1 是 pause，统一收尸（`K8s·Q18`）。

**弹药**
- 验证信号坑：`docker run -d --name t bash -c 'sleep 1000' && time docker stop t` → 必等满 10s
- 容器内 `ps -ef` 找 Z 状态；K8s 里 pause 当 PID 1 收尸的机制见 `K8s·Q18`
- 深挖：[[wiki/14-容器运行时/01-Docker/03-docker-container-lifecycle.md|容器生命周期]]

**红线**｜❌ "SIGTERM 杀不掉就调大 terminationGracePeriodSeconds"——掩盖问题，正确解法是让 PID 1 转发信号（或对照 `K8s·Q34` 的摘流竞态区分两种"杀不掉"）；❌ 把 stop 慢归因于"应用退出慢"（多数是信号根本没送达）。

## Q7. CPU limit 底层怎么实现？"limit 不高但 P99 抖"的根因？（资源/CPU）

**一句话**｜CFS bandwidth control：每 period（默认 100ms）窗口只给 quota 额度，用满整个 cgroup 被 throttle 到下一窗口——多线程应用同窗口烧光额度会集体挂起，产生百毫秒级毛刺。

**30 秒答**｜机制：v2 `cpu.max = "<quota> <period>"`（如 200000 100000 = 2 核；v1 是 cfs_quota_us/cfs_period_us），request 对应 `cpu.weight` 只影响调度权重不硬限。**数字推演**（面试必会）：96 核宿主机跑 Go 服务，没设 automaxprocs → GOMAXPROCS=96，0.2 核 quota 在窗口前几毫秒被烧光 → 每窗口剩余 ~80ms 全组挂起 → CPU 利用率 5%、P99 却是 100ms 台阶。缓解次序：①并发度对齐 quota（根治）：`go.uber.org/automaxprocs`，Go 1.25 起 GOMAXPROCS 默认感知 cgroup，JVM `-XX:ActiveProcessorCount`；②period 调小到 20ms 细化 throttle 粒度；③低延迟场景 CPU Manager static policy 绑核独占（`K8s·Q40`）。

**弹药**
- `cat /sys/fs/cgroup/cpu.max`；`cat /sys/fs/cgroup/cpu.stat | grep throttled` — **nr_throttled 是毛刺第一证据**
- 判断线：CPU 利用率再低也可能 throttle——判据是 throttled 计数，不是 CPU%
- 深挖：[[wiki/14-容器运行时/00-总览/03-container-internals-deep-dive.md|容器本体深挖]] §4.1

**红线**｜❌ "CPU 打满才 throttle"——是 quota 打满，利用率可以只有 10%；❌ 只会调大 limit（能缓解不根治，并发度对齐才是根治）；❌ 分不清 request（权重）和 limit（硬顶）。

## Q8. 内存超过 limit 会发生什么？和节点 OOM 怎么区分？（资源/内存）

**一句话**｜容器超 limit 是 cgroup memory 子系统直接 OOM kill（exit 137）；节点内存不足是 kubelet 驱逐（Evicted）或内核全局 OOM——三层账本，别混。

**30 秒答**｜cgroup 层触发链：memory.current（anon + file + kernel）撞 memory.max → 内核先 reclaim 踢 page cache → 踢不动（涨的是 anon）→ cgroup OOM killer 杀该 cgroup 内 oom_score_adj 最大者 → 容器 137 OOMKilled。节点层：MemAvailable 破阈值 → kubelet 按 QoS+超 request 比例驱逐（Evicted）；内核全局 OOM（dmesg 有 Killed process）是最后兜底。**page cache 计入 memory limit**——纯读写大文件/写日志就能顶满 limit，RSS 却很低（`K8s·Q2` 深挖的同源根因）。判断线：describe pod 看 `lastState.reason=OOMKilled`（cgroup 层）vs events `reason=Evicted`（节点层）。

**弹药**
- `cat /sys/fs/cgroup/memory.current` vs `memory.max`；`memory.stat` 拆 anon/file/kernel
- `cat /sys/fs/cgroup/memory.events` — **oom_kill 计数器，监控直接告警它**
- `dmesg -T | grep -i "killed process"` — 节点层铁证
- swap：v2 `memory.swap.max`；K8s 1.28+ NodeSwap beta

**红线**｜❌ "RSS 没到 limit 不可能 OOM"（file/kernel 两本账在 RSS 之外）；❌ 只会调大 limit 不拆 memory.stat（file 大就治理日志/缓存）；❌ 把 cgroup OOM 和 kubelet Evicted 说成一回事。

## Q9. 容器里 free/top 显示的是谁的内存？老 JVM 为什么因此被 OOM？（可观测/兼容性）

**一句话**｜`/proc/meminfo`、`/proc/cpuinfo` 是内核按整机信息生成的全局视图，namespace 不隔离内容——按"机器 128G"配堆的老 JVM，实际 cgroup 只有 4G，直接被 OOM。

**30 秒答**｜根因：procfs 内容由内核全局生成，mnt ns 只隔离挂载点视图。受害链：8u131- 的 JVM 按物理内存默认 heap = 机器内存 1/4 → 128G 节点上默认 32G 堆撞 4G limit 必死；`nproc`/`Runtime.availableProcessors()` 同理返回宿主机核数，GC/JIT 线程按 96 核开。解法三招：①JDK 8u191+/10+ `UseContainerSupport` 默认开，按 cgroup 算核数内存；②显式：`-Xmx` ≤ 0.5~0.75×limit 且给堆外（metaspace/direct buffer/线程栈）留份，或 `MaxRAMPercentage=75`；③系统级 **lxcfs**：FUSE 把容器 cgroup 值回写成它自己的 /proc 视图（阿里云容器服务老版标配）。Go 同理：GOMAXPROCS 用 automaxprocs，Go 1.25 起默认感知。

**弹药**
- 容器内 `free -g`、`nproc` 对比宿主机——不一致即未做 cgroup 感知
- `java -XX:+PrintFlagsFinal -version | grep -E "MaxHeapSize|UseContainerSupport"`；`-XX:ActiveProcessorCount=N`
- `mount | grep lxcfs` 验证视图回写
- 深挖：[[wiki/14-容器运行时/01-Docker/12-java-containerization-guide.md|Java 容器化指南]]

**红线**｜❌ "free 显示宿主机内存是 bug"——是设计；❌ JVM 只调 -Xmx 不留堆外余量（metaspace + direct buffer + 线程栈分分钟顶穿，`K8s·Q2` 弹药已有）。

## Q10. 镜像瘦身的五板斧？为什么 layer 顺序影响构建缓存？（镜像工程）

**一句话**｜多阶段构建砍编译链 + distroless/scratch 基底 + 合并 RUN 同层清缓存 + .dockerignore + 依赖清单前置保缓存——层是"只增改不回收"的账本，所有手段都是在少留账。

**30 秒答**｜五板斧：①**多阶段构建**——`FROM golang AS build` 编译，`FROM gcr.io/distroless/static` 只 COPY 二进制，gcc/源码全留在 build stage；②**小基底**——scratch（纯静态）< distroless < alpine（musl 注意 glibc 兼容与 Go DNS re-resolve 坑）< slim；③**同层清理**——`apt-get ... && rm -rf /var/lib/apt/lists/*` 必须同一条 RUN，分开写删除只是 whiteout、层还在（Q3 的直接应用）；④**缓存顺序**——层按指令序失效：`COPY go.mod` + `go mod download` 放前，`COPY . .` 放后，改一行代码不至于重拉依赖；⑤**.dockerignore**——.git/构建产物不进 context（context 先 tar 上传给 daemon）。数字感：Go 服务 golang 基底 1.2G → distroless 静态二进制 80M；Java 用 jlink 裁 JRE + AppCDS/CRaC 加速启动。

**深挖：缓存失效链与"删不掉的 500M 层"**
```dockerfile
COPY go.mod go.sum /app/
RUN go mod download        # 改代码不失效
COPY . .                   # 改代码只从这层起失效
RUN go build -o /app/server
```
追问标配——镜像里有个 500M 的层删不掉：层一旦被 push 或被下游镜像引用就在 registry 永久存在；修法 = 改 Dockerfile 重建出新 digest + 清旧 tag + registry GC（Harbor garbage collect）。BuildKit 缓存挂载 `RUN --mount=type=cache,...` 让缓存放镜像外。

**弹药**
- `docker history <img>` 逐层看大小与指令；`dive` 可视化逐层浪费
- 深挖：[[wiki/14-容器运行时/04-镜像构建/06-image-layer-optimization.md|镜像层优化]] · [[wiki/14-容器运行时/02-镜像管理/09-image-distribution-acceleration.md|镜像分发加速]]

**红线**｜❌ 在后面的 RUN 里删上层文件指望变小（whiteout 不回收）；❌ alpine 跑 glibc 依赖/cgo 服务不测就上生产（musl 坑）；❌ "镜像小=启动快"只对一半——拉取快是真的，JVM 预热等初始化耗时与镜像大小无关。

**下一问**｜镜像拉取慢除了瘦身还能怎么办？（→ P2P 分发/镜像预热/按需加载，见 [[wiki/14-容器运行时/02-镜像管理/09-image-distribution-acceleration.md|镜像分发加速]]）

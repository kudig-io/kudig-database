# 高可用控制面搭建 — 源码分析

## 概述

高可用（High Availability, HA）是生产环境 Kubernetes 集群的基本要求。单控制面节点的集群存在单点问题风险——一旦控制面节点宕机，集群将无法创建新的 Pod、处理 API 请求或进行调度决策。高可用控制面通过部署多个控制面节点和负载均衡器来消除单点问题，确保集群在部分节点问题时仍能正常提供服务。

kubeadm 支持两种高可用 etcd 拓扑：

- **Stacked etcd（堆叠模式）**：etcd 运行在控制面节点上，与 API Server 等组件共享同一台机器。这是 kubeadm 推荐的方式，部署简单，但 etcd 和控制面组件共享资源。
- **External etcd（外部模式）**：etcd 运行在独立的节点上，与控制面节点分离。这种方式性能更好，隔离性更强，但需要额外的机器和维护成本。

两种模式都使用负载均衡器来分发 API Server 的流量。`--control-plane-endpoint` 参数是 HA 配置的核心，所有组件的 kubeconfig 文件都通过它连接到负载均衡器而非单个 API Server。

本文档详细分析 kubeadm HA 的架构设计、配置方法、新增控制面节点的流程、etcd 高可用机制以及 Controller Manager 和 Scheduler 的 Leader Election。

## 一、高可用架构

### 1.1 Stacked etcd 模式

```
Stacked etcd (推荐):
  ┌─────────────────────────────────────────────────────────────┐
  │  负载均衡器 (HAProxy/Nginx/kube-vip/云厂商 CLB)             │
  │  control-plane-endpoint:6443                                │
  └──────┬──────────────────┬──────────────────┬────────────────┘
         │                  │                  │
  ┌──────▼──────┐   ┌──────▼──────┐   ┌──────▼──────┐
  │  CP Node 1  │   │  CP Node 2  │   │  CP Node 3  │
  │  apiserver  │   │  apiserver  │   │  apiserver  │
  │  scheduler  │   │  scheduler  │   │  scheduler  │
  │  ctrl-mgr   │   │  ctrl-mgr   │   │  ctrl-mgr   │
  │  etcd       │◄──►  etcd       │◄──►  etcd       │
  └─────────────┘   └─────────────┘   └─────────────┘

  特点:
  - etcd 与控制面组件运行在同一节点
  - 部署简单，kubeadm 原生支持
  - 需要 3 个或 5 个控制面节点 (奇数，保证 etcd 仲裁)
  - etcd 和控制面共享资源
```

### 1.2 External etcd 模式

```
External etcd:
  ┌─────────────────────────────────────────────────────────────┐
  │  负载均衡器                                                  │
  └──────┬──────────────────┬──────────────────┬────────────────┘
         │                  │                  │
  ┌──────▼──────┐   ┌──────▼──────┐   ┌──────▼──────┐
  │  CP Node 1  │   │  CP Node 2  │   │  CP Node 3  │
  │  apiserver  │   │  apiserver  │   │  apiserver  │
  │  scheduler  │   │  scheduler  │   │  scheduler  │
  │  ctrl-mgr   │   │  ctrl-mgr   │   │  ctrl-mgr   │
  └──────┬──────┘   └──────┬──────┘   └──────┬──────┘
         │                  │                  │
         └──────────────────┴──────────────────┘
                            │
                ┌───────────▼───────────────┐
                │   External etcd Cluster   │
                │  ┌──────┐ ┌──────┐ ┌──────┐
                │  │etcd-1│ │etcd-2│ │etcd-3│
                │  └──────┘ └──────┘ └──────┘
                └───────────────────────────┘

  特点:
  - etcd 运行在独立节点
  - 性能更好，隔离性更强
  - 需要额外机器和维护
  - 适用于大规模生产环境
```

## 二、高可用配置

### 2.1 Init 配置

```yaml
# init-config.yaml
apiVersion: kubeadm.k8s.io/v1beta3
kind: InitConfiguration
metadata:
  name: my-cluster
nodeRegistration:
  name: node-1
  criSocket: unix:///var/run/containerd/containerd.sock
localAPIEndpoint:
  advertiseAddress: "192.168.1.1"
  bindPort: 6443
---
apiVersion: kubeadm.k8s.io/v1beta3
kind: ClusterConfiguration
metadata:
  name: my-cluster
controlPlaneEndpoint: "loadbalancer.example.com:6443"  # 核心: 负载均衡器地址
etcd:
  local:
    dataDir: /var/lib/etcd
networking:
  podSubnet: "10.244.0.0/16"
  serviceSubnet: "10.96.0.0/12"
kubernetesVersion: "v1.28.0"
```

### 2.2 --control-plane-endpoint 源码分析

```go
// cmd/kubeadm/app/cmd/phases/kubeconfig/kubeconfig.go
func BuildKubeconfig(kubeconfigFile string, endpoint string, ...) error {
    config := &clientcmdapi.Config{
        Clusters: map[string]*clientcmdapi.Cluster{
            "kubernetes": {
                Server: endpoint,  // 使用 controlPlaneEndpoint
                CertificateAuthorityData: caCert,
            },
        },
    }
    // 所有组件的 kubeconfig 都指向负载均衡器
}
```

**关键点**：所有 kubeconfig 文件中的 `server` 字段都指向 `controlPlaneEndpoint`（负载均衡器地址），而非单个 API Server 的地址。这确保了当某个 API Server 问题时，请求会自动路由到健康的 API Server。

### 2.3 负载均衡器要求

| 要求 | 说明 | 原因 |
|------|------|------|
| TCP 6443 负载均衡 | 四层负载均衡 | API Server 使用 HTTPS |
| TLS Passthrough | 透传 TLS 到后端 | 不解密 TLS，保持端到端加密 |
| 健康检查 | TCP 或 HTTPS 检查 | 自动剔除不健康的后端 |
| 无需会话保持 | 无状态 API | API Server 是无状态的 |

常用负载均衡器方案：

``` bash
# 🟢 低风险：只读/信息收集，通常无副作用
# 方案 1: kube-vip (推荐，Cloud Native)
# 以静态 Pod 运行在控制面节点上
# 提供 Virtual IP + 负载均衡

# 方案 2: HAProxy + Keepalived
# 传统方案，可靠性高

# 方案 3: 云厂商负载均衡器
# AWS: NLB/ALB
# GCP: TCP Proxy Load Balancer
# Azure: Azure Load Balancer

# 方案 4: nginx (简单测试)
# TCP stream proxy
```

## 三、新增控制面节点流程

### 3.1 证书分发

新增控制面节点需要获取现有集群的控制面证书。kubeadm 使用 `upload-certs` 机制来分发证书：

```bash
# 在第一个控制面节点上上传证书
kubeadm init phase upload-certs --upload-certs
# 输出 certificate-key: xxxxxxxx

# 或在 init 时上传
kubeadm init --upload-certs
```

```go
// cmd/kubeadm/app/phases/uploadconfig/uploadcerts.go
func UploadCerts(cfg *kubeadmapi.InitConfiguration) error {
    // 1. 读取所有控制面证书
    // 2. 使用 AES-256-GCM 加密证书
    // 3. 上传加密后的证书到 ConfigMap (kubeadm-certs)
    // 4. 返回 certificate-key (用于解密)
}
```

### 3.2 新节点 Join 流程

```bash
# 在新控制面节点上执行
kubeadm join control-plane-endpoint:6443 \
  --token <token> \
  --discovery-token-ca-cert-hash sha256:<hash> \
  --control-plane \
  --certificate-key <key>

# 完整流程:
# 1. 使用 Bootstrap Token 向 API Server 认证
# 2. 下载加密证书 (从 ConfigMap)
# 3. 使用 certificate-key 解密证书
# 4. 将证书写入 /etc/kubernetes/pki/
# 5. 生成各组件 kubeconfig
# 6. 生成静态 Pod manifests (API Server/CM/Scheduler)
# 7. 向 etcd 集群添加新成员
# 8. 启动静态 Pod
# 9. 等待新 API Server 健康
```

```go
// cmd/kubeadm/app/cmd/join.go
func (j *Join) Run(cmd *cobra.Command, args []string) error {
    // 1. Preflight 预检
    // 2. 如果是控制面节点 (--control-plane):
    //    a. 下载并解密证书
    //    b. 生成 kubeconfig
    //    c. 生成静态 Pod manifests
    //    d. 添加 etcd 成员
    // 3. 如果是工作节点:
    //    a. 使用 Bootstrap Token 认证
    //    b. 写入 kubelet 配置
    //    c. 启动 kubelet
}
```

## 四、etcd 高可用

### 4.1 Stacked 模式 etcd

``` bash
# 🟢 低风险：只读/信息收集，通常无副作用
# 每个 CP 节点运行自己的 etcd 实例
# etcd 通过 Raft 协议保证数据一致性

# 查看 etcd 成员
ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/peer.crt \
  --key=/etc/kubernetes/pki/etcd/peer.key \
  member list

# 查看 etcd 集群健康
ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/peer.crt \
  --key=/etc/kubernetes/pki/etcd/peer.key \
  endpoint health --cluster

# etcd 仲裁要求:
# 3 节点集群: 容忍 1 节点问题
# 5 节点集群: 容忍 2 节点问题
# (N/2 + 1) 个节点必须存活
```
### 4.2 External etcd 模式

```bash
# kubeadm init 时指定外部 etcd
kubeadm init \
  --control-plane-endpoint=lb:6443 \
  --etcd-servers=https://etcd1:2379,https://etcd2:2379,https://etcd3:2379 \
  --etcd-ca-file=/etc/kubernetes/pki/etcd/ca.crt \
  --etcd-cert-file=/etc/kubernetes/pki/etcd/client.crt \
  --etcd-key-file=/etc/kubernetes/pki/etcd/client.key
```

## 五、Controller Manager / Scheduler HA

### 5.1 Leader Election

Controller Manager 和 Scheduler 都通过内置的 Leader Election 机制实现 HA：

```go
// 多个实例同时运行，但只有一个 active（leader）
// Leader 通过 Lease 对象选举产生
// 其他实例处于热备状态
// Leader 问题时，其他实例自动接管

// 启动参数:
--leader-elect=true                    // 启用选主
--leader-elect-lease-duration=15s      // 租约时长
--leader-elect-renew-deadline=10s      // 续约超时
--leader-elect-retry-period=2s         // 重试间隔
```

### 5.2 Leader Election 源码

```go
// staging/src/k8s.io/client-go/tools/leaderelection/leaderelection.go
type LeaderElector struct {
    config LeaderElectionConfig
}

func (le *LeaderElector) Run(ctx context.Context) {
    // 1. 尝试获取 Lease 对象
    // 2. 如果成功，成为 leader，启动 OnStartedLeading 回调
    // 3. 定期续约 Lease
    // 4. 如果续约失败或 Lease 被抢占，触发 OnStoppedLeading
}

// Lease 对象:
// kube-system/kube-controller-manager
// kube-system/kube-scheduler
```

### 5.3 查看当前 Leader

``` bash
# 🟢 低风险：只读/信息收集，通常无副作用

kubectl get endpoints kube-controller-manager -n kube-system -o yaml
```

## 六、证书处理

### 6.1 证书复制流程

```
新控制面节点加入时的证书处理:
  ┌─────────────────────────────────────────────────────────────┐
  │  1. 从 ConfigMap 下载加密证书 (kubeadm-certs)               │
  └─────────────────────────────────────────────────────────────┘
                            │
                            ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  2. 使用 certificate-key (AES-256-GCM) 解密证书             │
  └─────────────────────────────────────────────────────────────┘
                            │
                            ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  3. 写入 /etc/kubernetes/pki/                               │
  │     ├── ca.crt, ca.key                                      │
  │     ├── etcd/ca.crt, etcd/ca.key                            │
  │     ├── front-proxy-ca.crt, front-proxy-ca.key              │
  │     ├── sa.key, sa.pub                                      │
  │     └── ...                                                 │
  └─────────────────────────────────────────────────────────────┘
                            │
                            ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  4. 生成该节点特有的证书                                     │
  │     ├── apiserver.crt (含本节点 IP 的 SAN)                  │
  │     ├── etcd/server.crt (含本节点 IP)                       │
  │     ├── etcd/peer.crt (含本节点 IP)                         │
  │     └── kubelet 证书 (通过 CSR)                              │
  └─────────────────────────────────────────────────────────────┘
```

## 七、常见错误与排查

| 错误 | 原因 | 排查命令 | 解决方案 |
|------|------|---------|---------|
| etcd 成员添加失败 | 新节点 IP 不在证书 SAN 中 | `openssl x509 -in /etc/kubernetes/pki/etcd/peer.crt -noout -text | grep SAN` | 重新生成 etcd 证书包含新 IP |
| API Server 连不上 | 负载均衡器未配置 TLS passthrough | `curl -k https://<lb>:6443/healthz` | 配置负载均衡器透传 |
| 脑裂 | 节点网络分区 | `etcdctl endpoint health --cluster` | 减少选举超时，检查网络 |
| 证书解密失败 | certificate-key 错误 | `kubeadm init phase upload-certs` | 重新上传证书 |
| etcd 仲裁丢失 | 超过半数节点问题 | `etcdctl endpoint health` | 恢复问题节点或重建集群 |
| join 超时 | API Server 未就绪 | `curl -k https://<lb>:6443/healthz` | 等待 API Server 启动 |

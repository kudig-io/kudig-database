# 控制器模式 × 可观测性


## 连接点

[[concepts/controller-pattern.md|controller pattern]] 是 [[domain-17-system-foundation/topic-cheat-sheet/k8s.md|K8s]] 的自动化核心，[[entities/prometheus.md|prometheus]]-grafana]] 是监控栈。wiki 将前者视为设计模式、后者视为运维工具，但控制器的可观测性与应用的可观测性有本质不同：**应用监控关注用户体验，控制器监控关注系统存亡**。控制器的 Reconcile 延迟、Workqueue 深度、错误率直接反映了集群控制平面的健康状态。

## 共现场景

- **workqueue_depth**：当 API Server 或 [[entities/etcd.md|etcd]] 性能退化时，所有控制器的 Workqueue 都会堆积。这是集群级瓶颈的早期信号，比应用级告警更早出现
- **reconcile_errors_total**：[[entities/deployment.md|Deployment]] Controller 的协调错误通常意味着 etcd 写入失败或 API Server 不可用。这些错误是控制平面问题的直接指标
- **reconcile_duration_seconds**：协调延迟突增通常意味着：Watch 事件丢失（需要全量 List）、网络分区导致 API Server 超时、或控制器自身逻辑出现死锁
- **leader_election**：需要 Leader Election 的控制器（如 kube-controller-manager）在 Prometheus 中暴露 leader 状态。Leader 频繁变更意味着网络不稳定或节点资源不足

## 交叉洞察

**核心洞察：控制器是可观测性的"元指标"——它们不仅生成指标，其自身的健康状态就是集群最深层的诊断信号。**

传统可观测性关注应用层：请求延迟、错误率、吞吐量。但应用层的问题往往是控制平面问题的**症状**，而非**根因**：

```
应用层告警：Pod 启动缓慢
    └── 控制器层根因：Scheduler 协调延迟增加
            └── 基础设施根因：etcd 写入延迟退化
```

**控制器的可观测性三层模型：**

| 层级 | 指标 | 含义 | 紧急程度 |
|------|------|------|---------|
| **基础设施层** | etcd_disk_wal_fsync_duration_seconds | 控制平面存储性能 | 最高 |
| **控制器层** | reconcile_duration_seconds, workqueue_depth | 协调循环效率 | 高 |
| **应用层** | apiserver_request_duration_seconds | API 服务质量 | 中 |

**关键发现：控制器层的告警应该优先于应用层。** 当 workqueue_depth 持续增长时，即使所有应用 Pod 都健康，集群也处于雪崩边缘——因为新的调度请求、扩缩容请求、配置更新都无法及时处理。

## 张力与权衡

| 张力 | 详情 |
|------|------|
| **指标采集开销** | 每个控制器的 /metrics 端点增加 Prometheus 的 scrape 负担。在 100+ 自定义 Operator 的集群中，仅 scrape 控制器指标就可能消耗显著资源 |
| **告警噪音** | 控制器在滚动更新、节点驱逐、API Server 重启期间会自然产生大量协调错误。过于敏感的告警导致运维疲劳 |
| **跨控制器关联** | 一个控制器的延迟可能由另一个控制器引起（如 HPA 修改 Deployment 的 replicas，触发 Deployment Controller 的协调）。单一控制器的指标无法揭示这种跨控制器依赖 |

## 开放问题

- **控制器可观测性标准**：不同 Operator SDK 生成的指标命名和标签不统一。是否应该有一个跨框架的控制器可观测性标准（类似 OpenTelemetry 的语义约定）？
- **控制器级联故障检测**：当多个控制器的 workqueue 同时堆积时，如何快速定位根因是 etcd、API Server、还是网络问题？当前缺乏自动化的根因关联分析工具

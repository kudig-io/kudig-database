# 阿里云专有云架构概述

本文档面向部署在客户数据中心的阿里云专有云K8s运维团队，系统梳理专有云产品矩阵、[[Kubernetes|K8s]]部署模式、与公有云ACK的差异，以及专有云特有的运维限制。智能体部署在客户环境之外时，需通过工单群远程指导客户执行操作。

---

## 1. 阿里云专有云产品矩阵

阿里云提供三种私有云部署形态，适用于不同规模和合规要求的客户场景。

| 产品 | 定位 | 部署规模 | 核心组件 | 适用场景 |
|------|------|----------|----------|----------|
| **ZStack** | 轻量级私有云 | 数十台物理机 | 自研IaaS引擎、简化管控面 | 中小企业、边缘节点、POC验证 |
| **Apsara Stack 企业版** | 企业级专有云 | 数百至数千节点 | 完整飞天底座、ACK、OSS、RDS | 大型政企、金融、运营商 |
| **Apsara Stack 敏捷版** | 容器化专有云 | 数十至数百节点 | Kubernetes原生、轻量管控 | DevOps平台、云原生转型 |
| **飞天平台** | 公有云底座 | 超大规模 | 盘古存储、伏羲调度、洛神网络 | 公有云Region、超大规模专有云 |

### 1.1 ZStack 架构要点

```
┌─────────────────────────────────────┐
│           ZStack 管理平台            │
│  ┌─────────┐ ┌─────────┐ ┌────────┐ │
│  │ 计算节点 │ │ 存储节点 │ │ 网络节点│ │
│  │ (KVM)   │ │ (Ceph)  │ │ (SDN)  │ │
│  └─────────┘ └─────────┘ └────────┘ │
└─────────────────────────────────────┘
              ↓
        ┌─────────────┐
        │  ZStack K8s │  ← 可选部署
        │  (KubeSpray)│
        └─────────────┘
```

ZStack 提供基于 KVM 的虚拟化层，存储可选本地存储或 Ceph。K8s 集群可通过 ZStack 云平台的「容器服务」插件一键部署，底层使用 KubeSpray 或 ZStack 自研编排器。

**远程顾问注意**：ZStack 环境通常缺少阿里云公有云的标准 OpenAPI，诊断需依赖客户提供的 ZStack 管理台截图或导出的资源清单。

### 1.2 Apsara Stack 企业版架构

```
┌─────────────────────────────────────────────────────────┐
│                    Apsara Stack 企业版                   │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────┐  │
│  │  飞天底座    │  │  产品控制台  │  │   运维管控中心    │  │
│  │ (盘古/伏羲)  │  │  (ASO/天基)  │  │   (ASCM/ASO)    │  │
│  └─────────────┘  └─────────────┘  └─────────────────┘  │
│         ↓                  ↓                  ↓          │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────┐  │
│  │  ACK 集群   │  │  OSS/NAS    │  │   SLB/VPC/RAM   │  │
│  │  (专有版)   │  │  (盘古存储)  │  │   (洛神网络)    │  │
│  └─────────────┘  └─────────────┘  └─────────────────┘  │
└─────────────────────────────────────────────────────────┘
```

Apsara Stack 企业版复刻公有云核心产品，通过**天基（ASO）**进行底层资源编排，通过**ASCM**提供租户级控制台。ACK 专有版集群运行在此底座之上，与公有云 ACK 共享核心代码基线，但在网络、存储、安全组件上存在差异。

### 1.3 飞天平台与专有云的关系

飞天平台（Apsara）是阿里云所有云服务的底层分布式操作系统：

| 飞天组件 | 公有云实现 | 专有云实现 | 差异说明 |
|----------|------------|------------|----------|
| **盘古** | 分布式存储 | Ceph/商业存储兼容层 | 专有云存储后端可替换 |
| **伏羲** | 统一调度 | 专有云调度器 | 规模较小，调度策略简化 |
| **洛神** | 虚拟网络 | VPC/VXLAN | 专有云网络设备需预集成 |
| **女娲** | 一致性服务 | [[entities/etcd.md|Etcd]] | 专有云元数据服务降级 |
| **钟馗** | 安全/风控 | 客户自有安全体系 | 需对接客户IAM/KMS |

## 2. 专有云 K8s 部署模式

### 2.1 ACK on 专有云（推荐）

阿里云 ACK 专有版（Dedicated Edition）是专有云场景的标准 K8s 交付形态：

```yaml
# ACK 专有版集群典型配置示例
apiVersion: cs.alibaba-cloud.com/v1
kind: ClusterConfig
metadata:
  name: apsara-ack-prod
spec:
  region: "cn-apsara-local"      # 专有云Region标识
  clusterType: "Dedicated"       # 专有版（非托管版）
  kubernetesVersion: "1.28.3-aliyun.1"
  vpcId: "vpc-apsara-xxxxx"      # 专有云VPC
  vswitchIds:
    - "vsw-apsara-az1"
    - "vsw-apsara-az2"
  masterInstanceTypes:
    - "ecs.g7.xlarge"            # 管控节点规格
  workerInstanceTypes:
    - "ecs.g7.2xlarge"           # 工作节点规格
  numOfNodes: 6                  # 初始节点数
  containerCidr: "172.20.0.0/16"
  serviceCidr: "172.21.0.0/20"
  keyPair: "apsara-k8s-key"
  addons:
    - name: terway-eniip          # 专有云推荐CNI
    - name: csi-plugin            # 存储插件
    - name: logtail-ds            # 日志采集
```

**部署流程（远程顾问指导客户执行）**：

1. **前置检查**：确认天基/ASO管控面就绪、VPC/VSwitch已创建、ECS库存充足
2. **创建集群**：通过 ASCM 控制台或调用专有云 OpenAPI `CreateCluster`
3. **配置节点池**：创建系统节点池（`system`）和业务节点池（`worker`）
4. **部署插件**：安装 Terway、CSI、日志、监控插件
5. **接入客户体系**：对接客户内部 DNS、镜像仓库、LDAP/AD

### 2.2 自建 K8s on 专有云 ECS

部分客户选择基于专有云 ECS/裸金属自建 K8s：

| 部署方式 | 工具链 | 适用场景 | 运维复杂度 |
|----------|--------|----------|------------|
| Kubeadm | kubeadm + 手动配置 | 小规模测试 | 高 |
| KubeSpray | Ansible + 容器化部署 | 中规模生产 | 中 |
| ACK Distro | 阿里云开源 K8s 发行版 | 边缘/IoT | 中 |
| 二进制手动 | systemd + 静态Pod | 金融合规 | 极高 |

``` bash
# 🟢 低风险：只读/信息收集，通常无副作用
# 远程顾问常用：检查客户自建K8s版本和组件健康状态
kubectl version --short
kubectl get nodes -o wide
kubectl get pods -n kube-system

# 检查 kubeadm 集群的证书有效期（自建集群常见问题）
kubeadm certs check-expiration

# 检查 etcd 成员健康（自管 etcd 场景）
ETCDCTL_API=3 etcdctl endpoint health \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key
```

## 3. 与公有云 ACK 的差异

专有云 ACK 与公有云 ACK 在以下维度存在显著差异，远程顾问需特别注意。

### 3.1 网络差异

| 维度 | 公有云 ACK | 专有云 ACK | 远程诊断影响 |
|------|------------|------------|--------------|
| **CNI 模式** | Terway/Flannel | Terway 为主 | 专有云Flannel功能受限 |
| **VPC 互通** | 云企业网/CEN | 客户自建专线/VPN | 跨VPC需客户网络团队配合 |
| **公网访问** | EIP/NAT网关 | 通常无公网 | Pod拉取公网镜像需代理 |
| **SLB** | 标准SLB/NLB/ALB | 专有云SLB/金属LB | 健康检查机制可能不同 |
| **DNS** | 云解析DNS/PrivateZone | 客户内部DNS | CoreDNS需配置上游转发 |

```yaml
# 专有云 CoreDNS 配置：对接客户内部DNS示例
apiVersion: v1
kind: ConfigMap
metadata:
  name: coredns
  namespace: kube-system
data:
  Corefile: |
    .:53 {
        errors
        health
        kubernetes cluster.local in-addr.arpa ip6.arpa {
           pods insecure
           fallthrough in-addr.arpa ip6.arpa
        }
        # 专有云：转发到客户内部DNS
        forward . 10.0.1.10 10.0.1.11 {
           max_concurrent 1000
        }
        cache 30
        loop
        reload
        loadbalance
    }
    # 客户内部域解析
    corp.internal:53 {
        forward . 10.0.1.10
    }
```

### 3.2 存储差异

| 存储类型 | 公有云 | 专有云 | 备注 |
|----------|--------|--------|------|
| 云盘 | ESSD/SSD/高效 | 兼容块存储 | 专有云底层可能为商业存储 |
| NAS | 阿里云文件存储 | 盘古/商业NAS | 需确认NFS版本兼容性 |
| OSS | 标准OSS | 专有云对象存储 | API兼容，endpoint不同 |
| 本地盘 | D1/D2本地SSD | 物理机本地盘 | 需配置LVM/RAID |

``` bash
# 🟢 低风险：只读/信息收集，通常无副作用
# 远程诊断：检查专有云存储后端状态
# 1. 查看CSI插件运行状态
kubectl get pods -n kube-system | grep csi

# 2. 检查StorageClass
kubectl get sc

# 3. 检查节点上存储插件日志（客户执行）
kubectl logs -n kube-system csi-plugin-xxxx -c csi-plugin

# 4. 验证盘古存储健康（Apsara Stack场景）
curl -s http://localhost:5266/storage/status | jq .
```
### 3.3 安全差异

| 安全维度 | 公有云 ACK | 专有云 ACK | 远程处理方案 |
|----------|------------|------------|--------------|
| **身份认证** | RAM + OIDC | 客户IAM/AD + RAM | 需配置IDaaS联邦认证 |
| **密钥管理** | KMS云密钥 | 客户HSM/内部KMS | 使用BYOK或客户KMS |
| **镜像安全** | 容器镜像服务ACR | 客户内部Harbor | 对接客户镜像扫描流程 |
| **网络隔离** | 安全组 + 网络ACL | 客户防火墙 + 安全组 | 需客户开放白名单端口 |
| **审计合规** | ActionTrail | 客户SIEM/审计系统 | 导出审计日志对接 |

## 4. 专有云特有的限制

### 4.1 无公网访问

专有云通常部署在客户内网，无公网出口。影响及应对方案：

| 场景 | 问题 | 解决方案 |
|------|------|----------|
| 镜像拉取 | 无法访问 Docker Hub/ACR 公网 | 配置内部Harbor、使用imagePullSecrets |
| [[entities/helm.md|Helm]] Chart | 无法访问 Helm Hub | 部署本地 Chart Museum |
| 软件包安装 | 节点无法访问公网yum/apt | 配置内部镜像源/Nexus代理 |
| 日志上报 | 无法上报阿里云SLS公网 | 部署专有云内SLS网关或本地ELK |

```yaml
# 配置内部镜像仓库的 Secret
apiVersion: v1
kind: Secret
metadata:
  name: internal-registry-secret
  namespace: default
type: kubernetes.io/dockerconfigjson
data:
  .dockerconfigjson: <base64-encoded-auth>
---
# Pod 引用内部镜像
apiVersion: v1
kind: Pod
metadata:
  name: internal-app
spec:
  imagePullSecrets:
    - name: internal-registry-secret
  containers:
    - name: app
      image: harbor.corp.internal:5000/myapp:v1.0.0
```

### 4.2 依赖内部 DNS

专有云需对接客户内部 DNS 基础设施：

``` bash
# 🟡 中风险：会修改集群/资源状态，执行前请确认目标、影响范围与授权
# 远程诊断 DNS 问题流程
# Step 1: 检查 Pod 内 DNS 解析
kubectl run -it --rm debug --image=busybox:1.36 --restart=Never -- nslookup kubernetes.default

# Step 2: 检查 CoreDNS Pod 状态
kubectl get pods -n kube-system -l k8s-app=kube-dns
kubectl logs -n kube-system -l k8s-app=kube-dns --tail=100

# Step 3: 检查 CoreDNS ConfigMap
kubectl get cm coredns -n kube-system -o yaml

# Step 4: 测试上游 DNS 可达性
kubectl run -it --rm debug --image=busybox:1.36 --restart=Never -- \
  nc -vz 10.0.1.10 53

# Step 5: 验证内部域名解析
kubectl run -it --rm debug --image=busybox:1.36 --restart=Never -- \
  nslookup gitlab.corp.internal 10.0.1.10
```
### 4.3 内部镜像仓库

专有云场景下，镜像构建和分发流程：

```
开发者本地 → CI/CD流水线 → 内部Harbor → 专有云节点拉取
                  ↑              ↑
            安全扫描      签名/准入控制 (OPA/Kyverno)
```

远程顾问需确认的镜像仓库配置项：

| 配置项 | 检查命令/方法 |
|--------|---------------|
| 仓库地址 | `kubectl get cm -n kube-system | grep registry` |
| 仓库证书 | 检查节点 `/etc/docker/certs.d/` |
| 仓库配额 | Harbor UI 或 API 查询 |
| 镜像签名 | 检查 Notary/Cosign 配置 |
| 准入策略 | `kubectl get clusterpolicies.kyverno.io` |

### 4.4 管控面可达性限制

远程顾问无法直接访问客户环境，需通过以下途径指导：

```
┌─────────────────┐     工单/企微/钉钉      ┌─────────────────┐
│   远程顾问       │ ←──────────────────→ │   客户运维人员    │
│  (无环境访问)    │                      │  (有堡垒机权限)   │
└─────────────────┘                      └────────┬────────┘
                                                  │
                         ┌──────────────────────┘
                         ↓
                  ┌─────────────┐
                  │  客户堡垒机  │
                  │  (JumpServer)│
                  └──────┬──────┘
                         │
            ┌────────────┼────────────┐
            ↓            ↓            ↓
       ┌────────┐  ┌────────┐  ┌────────┐
       │ACK管控面│  │ 节点   │  │ 日志平台│
       │(ASCM/API)│ │ (SSH)  │  │ (SLS)  │
       └────────┘  └────────┘  └────────┘
```

**远程诊断沟通模板**：

```markdown
【阿里云远程顾问-诊断指令】

请客户运维同学在堡垒机上执行以下命令，并将完整输出复制回复：

1. 集群基础信息：
   kubectl cluster-info
   kubectl get nodes -o wide
   kubectl get pods -A --field-selector status.phase!=Running

2. 事件检查（最近1小时）：
   kubectl get events --sort-by='.lastTimestamp' | tail -50

3. 特定组件日志（如问题指向Terway）：
   kubectl logs -n kube-system -l app=terway-eniip --tail=200

4. 节点资源：
   kubectl top nodes
   kubectl describe node <node-name>
```

## 5. 远程顾问快速参考

| 诊断目标 | 客户侧命令 | 顾问分析要点 |
|----------|------------|--------------|
| 集群健康 | `kubectl get --raw='/healthz'` | 管控面组件状态 |
| 网络连通 | `kubectl run test --image=busybox -- ping <target>` | CNI/安全组策略 |
| 存储挂载 | `kubectl describe pv,pvc` | CSI事件、后端存储状态 |
| 镜像拉取 | `kubectl describe pod <pod>` + `crictl pull` | 仓库认证、网络代理 |
| DNS解析 | `nslookup` in debug pod | CoreDNS配置、上游DNS |
| 资源水位 | `kubectl top nodes,pods` | 容量规划、伸缩策略 |

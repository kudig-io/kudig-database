## 1.1.1 什么是 FEBM

法医鉴定循证方法论（Forensic Evidence-Based Methodology, FEBM）是一套源于传统法医学、适配数字环境的系统化调查方法。它将物理世界中积累了数百年的法医学原理、证据科学和刑事侦查方法论，迁移并重构为适用于数字系统——特别是云原生基础设施——的工程化实践框架。

FEBM 不是一个单一的工具或技术，而是一套完整的**认识论体系（Epistemological Framework）**，回答的核心问题是：

- 在高度动态、短暂且分布式的云原生环境中，**如何建立关于系统状态和事件的可靠知识？**
- 如何确保这些知识的**可验证性、可审计性和可辩护性？**
- 如何将分散在多源异构数据中的碎片信息**重建为完整的因果叙事？**

## 1.1.2 洛卡德交换原理：FEBM 的哲学基石

FEBM 的核心哲学可追溯至 **洛卡德交换原理（Locard's Exchange Principle）**：

> "Every contact leaves a trace."  
> "每次接触都会留下痕迹。"

这一原理由 20 世纪法国犯罪学家埃德蒙·洛卡德（Edmond Locard, 1877-1966）提出。洛卡德被誉为"现代法医学之父"，他在里昂建立了世界上第一个专门的犯罪实验室。他的核心洞见是：犯罪行为不可能不留下物理痕迹——犯罪者总会在现场留下某些东西（指纹、纤维、DNA），也总会从现场带走某些东西。

这一原理在数字世界中的映射关系极为深刻：

```
物理世界 (Physical Forensics)          数字世界 (Digital Forensics)
──────────────────────────────────────────────────────────────────────
犯罪现场保护                           证据采集与保全 (Chain of Custody)
指纹、DNA、纤维                        日志记录、审计事件、进程痕迹
现场脚印                              系统调用序列 (syscall trace)
弹道痕迹                              网络流量模式 (flow patterns)
目击证词                              指标数据 (Metrics/Telemetry)
监控录像                              分布式追踪 (Distributed Traces)
物证保管链                            证据哈希 + Chain of Custody 文档
法庭呈堂证据标准                       合规审计可辩护性 (Defensibility)
尸检报告                              内存取证报告 (Memory Forensics)
弹道分析                              恶意代码逆向分析
时间线重建                            多源事件关联时间线 (Timeline)
犯罪心理画像                          攻击者行为模式分析 (TTPs)
```

**在 Kubernetes 环境中的具体体现：**

- 每次 API 调用都会在审计日志中留下痕迹
- 每次容器启动都会产生 cgroup 和 namespace 记录
- 每次网络连接都会在 conntrack 表中留下条目
- 每次文件操作都会更新 inode 的时间戳
- 每次 Pod 调度都会在 scheduler 日志和 etcd 中记录决策
- 每次配置变更都会在 GitOps 仓库和审计日志中留下完整历史
- 每次 eBPF 程序触发都会捕获内核级事件

洛卡德原理的力量在于其**普遍性**——它不依赖于对具体故障模式的预知，只依赖于一个基本事实：交互必然产生痕迹。这使得 FEBM 天然适应动态、未知、复杂的系统环境。

**数字取证科学（Digital Forensics）的贡献：**

数字取证科学作为法医学的分支，经过三十余年的发展已形成完善的学科体系。它为 FEBM 贡献了：

- **证据分类学**：将数字证据按类型（磁盘、内存、网络、日志）、易失性（极高到极低）、可靠性（直接证据/间接证据/推定证据）进行系统分类
- **采集规范**：ISO/IEC 27037 定义了数字证据的识别、收集、获取和保存的标准化程序
- **分析框架**：从静态分析（磁盘取证）到动态分析（行为分析），从时间线分析到关联分析的完整方法体系
- **工具验证标准**：NIST CFTT（Computer Forensic Tool Testing）程序确保取证工具的可靠性

**循证方法论（Evidence-Based Methodology）的贡献：**

循证方法论起源于循证医学（Evidence-Based Medicine），由大卫·萨科特（David Sackett）在 1990 年代系统化。其核心原则"将当前最佳证据与临床专长和患者价值观整合"，被 FEBM 迁移为"将当前最佳数字证据与运维专长和业务上下文整合"。它贡献了：

- **证据等级体系**：从最强的直接观测证据（如 eBPF 捕获的系统调用序列）到最弱的专家意见，建立了证据强度的评估框架
- **假设-验证循环**：系统化的假设生成、证据收集、假设检验、结论修正的迭代过程
- **交叉验证要求**：多个独立证据源指向同一结论才能提高可信度
- **认知偏差防范**：明确识别并防范确认偏误（Confirmation Bias）、锚定效应（Anchoring）等认知陷阱

**事件响应工程（Incident Response Engineering）的贡献：**

NIST SP 800-61（计算机安全事件处理指南）定义的四阶段响应框架——准备、检测与分析、遏制/根除/恢复、事后活动——为 FEBM 提供了面向实际运维场景的工程化骨架。它贡献了：

- **响应流程模型**：标准化的事件分级、升级、协调机制
- **遏制策略**：在保全证据的前提下控制事件影响范围
- **自动化能力**：SOAR（Security Orchestration, Automation and Response）平台的编排能力
- **持续改进循环**：Lessons Learned → 检测规则更新 → 响应手册优化

FEBM 的发展经历了四个历史阶段：

这一演进的核心驱动力是**目标环境的根本性变化**：

| 维度 | 传统环境 | 云原生/K8s 环境 |
|------|---------|---------------|
| 主机生命周期 | 年级 | 秒-分钟级（容器） |
| 存储模型 | 持久化本地磁盘 | Ephemeral + 外挂 PV |

| 调查访问权限 | 物理接触或远程登录 | API 驱动，RBAC 约束 |
| 证据易失性 | 低（磁盘持久化） | 极高（内存驻留数据秒级丢失） |
| 隔离粒度 | 物理主机级 | Namespace/Pod/Container 级 |

## 1.2.1 支柱一：证据中心性（Evidence Centricity）

**核心原则：** FEBM 拒绝一切无证据支撑的推断。每一个分析结论都必须能够追溯到具体的、可验证的数字证据。

这一原则直接对抗运维实践中常见的认知陷阱：

```
常见的"无证据推断"陷阱:

❌ "上次也是这个问题，肯定还是 DNS"
   → 过度依赖经验，忽略当前证据

❌ "刚部署了新版本，肯定是新版本的 bug"
   → 时间相关性 ≠ 因果关系

❌ "内存使用率很高，肯定是内存泄漏"
   → 表象与根因混淆

❌ "网络延迟变高了，肯定是网络问题"
   → 症状可能由多层原因导致

✓ FEBM 方法: 先采集证据，再构建假设，用证据验证假设
```

**证据的分类体系：**

FEBM 将 Kubernetes 环境中的证据按多个维度进行系统分类：

**按易失性分级（RFC 3227 参考）：**

| 易失性等级 | 证据类型 | 生命周期 | 采集优先级 | Kubernetes 示例 |
|-----------|---------|---------|-----------|----------------|
| Level 0 | 寄存器/缓存 | 纳秒级 | 极高 | CPU 寄存器状态（CRIU 检查点） |
| Level 1 | 内存 | 秒级 | 极高 | 进程内存映射、网络连接状态 |
| Level 2 | 运行时状态 | 分钟级 | 高 | 系统调用序列、文件描述符 |
| Level 3 | 临时存储 | Pod 生命周期 | 高 | emptyDir、容器层文件系统 |
| Level 4 | 日志缓冲 | 小时级 | 中 | 未转发的 stdout/stderr |
| Level 5 | 事件 | 默认 1h TTL | 中 | Kubernetes Events |
| Level 6 | 持久化日志 | 天-月级 | 低 | 已转发到 Loki/ES 的日志 |
| Level 7 | 审计记录 | 月-年级 | 低 | API Server 审计日志 |
| Level 8 | 配置历史 | 永久 | 低 | GitOps 仓库、etcd 快照 |

**按证据强度分级：**

| 强度等级 | 描述 | Kubernetes 示例 | 可信度 |
|---------|------|----------------|-------|
| 直接证据 | 直接观测到的事实 | eBPF 捕获的 syscall 序列 | 最高 |
| 实物证据 | 系统产生的原始数据 | 容器检查点、内存转储 | 高 |
| 记录证据 | 系统自动记录 | 审计日志、应用日志 | 中高 |
| 间接证据 | 需要推理的关联 | 指标趋势、时间关联 | 中 |
| 传闻证据 | 二手描述 | 用户工单描述、口头报告 | 低 |

**按来源层级分类：**

```
Kubernetes 证据来源层级模型:

┌─────────────────────────────────────────────────────────┐
│ Layer 7: 业务层证据                                       │
│   业务指标、用户行为数据、A/B 测试结果                      │
├─────────────────────────────────────────────────────────┤
│ Layer 6: 应用层证据                                       │
│   应用日志、分布式追踪 Spans、自定义 Metrics                │
├─────────────────────────────────────────────────────────┤
│ Layer 5: Service Mesh 层证据                              │
│   Istio/Linkerd 遥测、mTLS 证书日志、流量策略日志           │
├─────────────────────────────────────────────────────────┤
│ Layer 4: Kubernetes 控制平面层证据                         │
│   API Server 审计日志、etcd 操作、Scheduler 决策日志        │
│   Controller Manager 日志、Admission Webhook 日志          │
├─────────────────────────────────────────────────────────┤
│ Layer 3: Pod/容器层证据                                    │
│   容器日志(stdout/stderr)、cAdvisor 指标                  │
│   容器检查点(CRIU)、容器运行时(containerd/CRI-O)日志       │
├─────────────────────────────────────────────────────────┤
│ Layer 2: 节点层证据                                       │
│   kubelet 日志、内核日志(dmesg/journal)                    │
│   节点指标(node_exporter)、eBPF 事件                      │
├─────────────────────────────────────────────────────────┤
│ Layer 1: 基础设施层证据                                    │
│   物理/虚拟资源指标、网络设备日志                           │
│   存储后端日志、云服务商 API 日志                           │
└─────────────────────────────────────────────────────────┘
```

## 1.2.2 支柱二：程序规范性（Procedural Rigor）

**核心原则：** 证据的价值不仅取决于内容本身，更取决于其采集、处理和存储过程的规范性。未经规范程序处理的证据，即使内容真实，也可能在合规审计或法律程序中被质疑。

FEBM 遵循的核心标准体系：

| 标准 | 全称 | 核心内容 | FEBM 应用 |
|------|------|---------|----------|
| NIST SP 800-61 Rev.2 | Computer Security Incident Handling Guide | 事件响应四阶段框架 | FEBM 响应流程骨架 |
| NIST IR 8006 | NIST Cloud Computing Forensic Science Challenges | 云环境取证挑战分析 | K8s 取证特殊考量 |
| ISO/IEC 27037:2012 | Digital Evidence Identification, Collection, Acquisition and Preservation | 数字证据处理标准 | 证据采集 SOP |
| ISO/IEC 27041:2015 | Guidance on Assuring Suitability and Adequacy of Incident Investigation Methods | 调查方法的适宜性保证 | 方法验证 |
| ISO/IEC 27042:2015 | Guidelines for the Analysis and Interpretation of Digital Evidence | 数字证据分析和解释指南 | 分析流程规范 |
| ISO/IEC 27043:2015 | Incident Investigation Principles and Processes | 事件调查原则和流程 | 调查流程框架 |
| RFC 3227 | Guidelines for Evidence Collection and Archiving | 证据收集和归档指南 | 易失性排序采集 |

**链式监管（Chain of Custody）的实施：**

链式监管是确保证据完整性和可信度的核心机制。在 Kubernetes 环境中，其实施方式如下：

```
Chain of Custody 文档记录要素:

┌─────────────────────────────────────────────────────────┐
│ 证据项: container-checkpoint-abc123.tar                  │
│ 证据 ID: EV-2026-0225-001                               │
│ 原始 SHA-256: a3f2b8c9d1e4f5a6b7c8d9e0f1a2b3c4...      │
├─────────────────────────────────────────────────────────┤
│ 编号 │ 时间戳        │ 操作者    │ 操作         │ 位置   │
├──────┼───────────────┼──────────┼──────────────┼────────┤
│ 001  │ 2026-02-25    │ falco-   │ 检查点创建   │ node-  │
│      │ 10:32:15 UTC  │ webhook  │ 自动触发     │ 03     │
├──────┼───────────────┼──────────┼──────────────┼────────┤
│ 002  │ 2026-02-25    │ evidence-│ 传输至云存储 │ S3:    │
│      │ 10:32:45 UTC  │ collector│ SHA-256 验证 │ bucket │
├──────┼───────────────┼──────────┼──────────────┼────────┤
│ 003  │ 2026-02-25    │ analyst- │ 分析环境恢复 │ 隔离   │
│      │ 11:15:00 UTC  │ jdoe     │ SHA-256 验证 │ 集群   │
├──────┼───────────────┼──────────┼──────────────┼────────┤
│ 004  │ 2026-02-25    │ analyst- │ Volatility   │ 分析   │
│      │ 11:30:00 UTC  │ jdoe     │ 内存分析     │ 工作站 │
└─────────────────────────────────────────────────────────┘

每次转移:
  → 发送方签名 + 接收方签名
  → 传输前后 SHA-256 一致性验证
  → 存储介质/位置变更记录
  → 分析工具名称和版本记录
```

## 1.2.3 支柱三：时效敏感性（Time Sensitivity）

**核心原则：** 数字证据的易失性决定了 FEBM 的响应时效要求。在 Kubernetes 环境中，证据消失的速度远快于传统环境。

**Kubernetes 环境中的证据易失性时间线：**

```
证据易失性时间线 (Kubernetes 环境):

T+0s     容器内存状态 ──────┐
T+0s     运行时系统调用 ────┤ 容器终止后立即丢失
T+0s     网络连接状态 ──────┤ (不可恢复)
T+0s     进程树结构 ────────┘

T+5s     容器层文件系统 ──── containerd 清理 overlay 层

T+30s    容器日志缓冲 ────── stdout/stderr 需实时转发
                             未转发的部分可能随容器消失

T+1min   Pod Sandbox 状态 ── CRI 运行时清理 Pod 残留

T+5min   Pod 事件 ─────────── Kubernetes Events 默认 1h TTL
                              但高频事件可能被提前驱逐

T+1h     Kubernetes Events ── 默认 TTL 过期清除
         节点级日志 ─────────── 取决于日志轮转配置 (logrotate)

T+24h    审计日志 ───────────── 取决于审计后端配置
         conntrack 表项 ────── 内核连接跟踪过期清理

T+7d     Prometheus 原始指标 ─ 取决于 retention 配置
         分布式追踪 Spans ──── 取决于后端存储策略

T+30d    长期指标存储 ────────── Thanos/Cortex 降采样数据
         历史日志 ────────────── 取决于保留策略

T+∞      GitOps 仓库 ────────── 永久保存（如果不被强制推送覆盖）
         etcd 快照 ─────────── 定期备份保存
```

**时效敏感性在实践中的影响：**

```
场景: 容器被检测到异常出站连接

如果 T+0s 响应 (eBPF 实时检测):
  ✓ 捕获完整的内存状态
  ✓ 记录精确的网络连接四元组和缓冲区
  ✓ 保留进程树和系统调用上下文
  ✓ 获取容器内临时文件
  → 可进行完整的恶意行为分析和攻击路径重建

如果 T+5min 响应 (告警触发后人工介入):
  ✗ 内存状态已丢失 (容器可能已重启)
  ✗ 网络连接已断开
  ✗ 进程树已改变
  ✓ 日志可能还在
  ✓ 审计记录仍然完整
  → 只能基于日志做有限的事后分析

如果 T+1h 响应 (下一个值班周期):
  ✗ 所有运行时证据已丢失
  ✗ Kubernetes Events 可能已过期
  ✗ 容器日志可能已被轮转
  ✓ 审计日志仍在
  ✓ 指标数据仍在
  → 只能做粗粒度的趋势分析，无法进行深度取证
```

这就是为什么 FEBM 强调**持续取证（Continuous Forensics）**——不是等到事件发生后才开始采集，而是始终在线采集并持久化关键证据。

## 1.2.4 支柱四：结论可辩护性（Defensible Conclusions）

**核心原则：** FEBM 的分析结论必须能够经受技术审查、合规审计甚至法律程序的挑战。

结论可辩护性要求：

```
可辩护结论的要素清单:

1. 方法可靠性
   ☐ 使用的分析方法有已发表的理论基础
   ☐ 使用的工具经过验证 (NIST CFTT 或同等标准)
   ☐ 分析流程符合行业标准 (ISO/IEC 27042)

2. 证据完整性
   ☐ 证据的 Chain of Custody 完整无缺
   ☐ 证据的哈希值在采集后未发生变化
   ☐ 证据的采集时间和方式有详细记录

3. 推理透明性
   ☐ 从证据到结论的每一步推理都有明确记录
   ☐ 使用的假设和前提条件被明确说明
   ☐ 推理过程可被独立第三方复现

4. 替代假设考量
   ☐ 主要的替代解释已被列举
   ☐ 每个替代假设被排除的理由有证据支撑
   ☐ 无法排除的替代假设被明确标注

5. 局限性声明
   ☐ 分析的时间范围和数据覆盖度明确说明
   ☐ 已知的证据缺失被记录
   ☐ 结论的置信度被量化标注
   ☐ 可能影响结论的已知偏差被列举
```

**可辩护性在不同场景中的要求差异：**

| 场景 | 可辩护性要求 | 关键考量 |
|------|------------|---------|
| 内部故障诊断 | 中等 | 技术准确性，团队可理解 |
| SLA 违约分析 | 高 | 证据的客观性，时间戳精度 |
| 安全事件调查 | 很高 | 证据完整性，分析可复现 |
| 合规审计 (SOC2/等保) | 很高 | 流程符合性，记录完整性 |
| 法律诉讼/执法协助 | 最高 | 司法鉴定标准，专家证人 |

## 1.3.1 思维范式对比

理解 FEBM 必须将其与传统的故障树分析（FTA）进行认识论层面的对比。两者的差异不仅是技术手段的不同，而是**思维范式的根本分歧**：

```
认识论定位:

FTA  → 理性主义 (Rationalism)
       知识主要来自理性推演
       从公理/假设出发，通过逻辑推导得到结论
       强调模型的数学严谨性

FEBM → 经验主义 (Empiricism)
       知识主要来自经验观察
       从观察到的事实出发，通过归纳推理得到结论
       强调证据的客观性和可验证性
```

**推理范式的详细对比：**

| 维度 | FTA（演绎法） | FEBM（归纳法） |
|------|:---:|:---:|
| **推理方向** | 自上而下：从假设到验证 | 自下而上：从证据到结论 |
| **起点** | 预定义的顶事件和故障树模型 | 实际观察到的数字证据 |
| **对未知的态度** | 无法处理模型外的问题 | 天然适应未预期的事件 |
| **数学基础** | 布尔代数、概率论、最小割集 | 归纳逻辑、统计推断、贝叶斯推理 |
| **动态适应性** | 弱：静态模型需人工维护 | 强：证据驱动，自适应 |
| **核心假设** | 系统架构稳定、故障模式可枚举 | 每次接触留下痕迹（洛卡德原理） |
| **最佳场景** | 架构稳定、故障模式已知 | 动态环境、未知威胁 |
| **形式化程度** | 高：可数学验证 | 中：依赖专家解释框架 |
| **完备性保障** | 最小割集/径集算法 | 证据覆盖度评估 |
| **结果确定性** | 高：模型固定则结果确定 | 中：受证据时效和分析师经验影响 |

```
FTA 思维模型:
  "系统应该是这样的" → "如果出问题，可能是这些原因" → "检查这些原因"
  (预设 Model)      → (演绎 Deduction)               → (验证 Verification)

  具体流程:
  ①定义顶事件 → ②分解为中间事件 → ③追溯到基本事件
  → ④计算最小割集 → ⑤量化概率 → ⑥识别关键路径

FEBM 思维模型:
  "系统现在实际是什么状态？" → "证据表明发生了什么？" → "最可能的解释是什么？"
  (观察 Observation)          → (归纳 Induction)        → (推断 Inference)

  具体流程:
  ①采集多源证据 → ②重建时间线 → ③识别异常模式
  → ④生成候选假设 → ⑤证据验证假设 → ⑥排除替代解释 → ⑦确认根因
```

## 1.3.2 在 Kubernetes 环境中的适配性分析

Kubernetes 环境的五大特征决定了 FEBM 相对于 FTA 的适配性优势：

**特征一：极端动态性（Extreme Dynamism）**

容器的平均生命周期低于 15 分钟。HPA/VPA 自动伸缩、滚动更新、CronJob、批处理 Job 等机制使得系统的组件数量和拓扑结构持续变化。

```
FTA 的困境:
  为 Deployment-A (3 replicas) 构建的故障树
  → HPA 扩容至 12 replicas → 故障树中的资源竞争模型失效
  → 滚动更新替换 Pod → 故障树中的组件标识失效
  → 节点调度变化 → 故障树中的物理拓扑映射失效

FEBM 的适应:
  不依赖预定义的组件模型
  → 实时采集当前状态的证据
  → 通过 Pod UID / Container ID 追踪动态实体
  → 通过时间线重建还原变化过程
```

**特征二：多层级信号分散（Multi-Layer Signal Dispersion）**

从基础设施层到应用层的 7+ 层级中，每一层都产生独立的可观测性数据。一个应用层的错误可能源于容器层的资源限制、节点层的 CPU 节流、或基础设施层的网络拥塞。

```
FTA 的困境:
  将各层信号抽象为"基本事件"通过逻辑门组合
  → 损失跨层关联的细微模式
  → 无法表达跨层因果循环
  (例: 节点网络延迟 ← 某 Pod 异常流量 ← 配置错误导致调度至过载节点)

FEBM 的适应:
  通过关联标识符跨层连接证据
  → Pod UID 连接控制平面和数据平面
  → Trace ID 连接请求链路上的所有服务
  → 时间窗口匹配连接无标识符的事件
  → 自然支持跨层因果链的发现
```

**特征三：声明式管理范式（Declarative Management）**

Kubernetes 的声明式管理和控制器调和机制确保了自愈能力，但也意味着系统实际状态处于持续变化中。

```
FTA 的困境:
  静态快照可能迅速过时
  → 控制器不断调和期望状态和实际状态
  → 问题可能在自愈过程中被掩盖
  → 模型无法反映"自愈失败"的复杂场景

FEBM 的机遇:
  声明式本质提供了强大的审计能力
  → 所有 API 操作被审计日志完整记录
  → 期望状态 (YAML) 作为偏差检测的基准
  → "意图-实际"偏差本身就是关键证据
  → GitOps 仓库提供完整的配置变更历史
```

**特征四：共享基础设施（Shared Infrastructure）**

多租户架构和共享内核带来的"吵闹邻居"问题和容器逃逸风险。

**特征五：软件故障模式的不稳定性**

与硬件不同，软件组件的失效模式缺乏稳定的统计规律——同一个 Bug 可能在特定条件组合下才触发，而这些条件组合在生产环境中不断变化。

## 1.4.1 OODA 循环的 FEBM 映射

FEBM 的运行时推理过程可以映射到 John Boyd 的 OODA（Observe-Orient-Decide-Act）循环：

```
FEBM-OODA 循环:

  ┌─────────────────────────────────────────────────────┐
  │                                                     │
  │  Observe (观察)          Orient (定向)               │
  │  ┌──────────────┐       ┌──────────────┐           │
  │  │ 多源证据采集 │──────►│ 时间线重建   │           │
  │  │ eBPF/日志/   │       │ 模式识别     │           │
  │  │ 指标/追踪    │       │ 上下文关联   │           │
  │  └──────────────┘       └──────┬───────┘           │
  │         ▲                      │                    │
  │         │                      ▼                    │
  │  Act (行动)             Decide (决策)               │
  │  ┌──────────────┐       ┌──────────────┐           │
  │  │ 遏制/修复/   │◄──────│ 假设生成     │           │
  │  │ 恢复/沉淀    │       │ 假设验证     │           │
  │  │              │       │ 根因确认     │           │
  │  └──────────────┘       └──────────────┘           │
  │                                                     │
  │  循环速度: 秒-分钟级 (自动化) / 分钟-小时级 (人工)   │
  └─────────────────────────────────────────────────────┘
```

## 1.4.2 认知偏差防范

FEBM 方法论明确识别并防范运维分析中常见的认知偏差：

| 认知偏差 | 描述 | FEBM 对策 |
|---------|------|----------|
| 确认偏误 | 倾向于寻找支持已有假设的证据 | 强制列举和验证替代假设 |
| 锚定效应 | 过度依赖首先获得的信息 | 多源证据交叉验证 |
| 可得性偏差 | 基于最容易回忆的案例判断 | 系统化证据采集，不依赖记忆 |
| 近因效应 | 将原因归于最近的变更 | 时间线重建覆盖完整时间窗口 |
| 叙事偏差 | 倾向于构建简单的因果故事 | 要求多条独立证据链 |
| 权威偏差 | 过度信任资深工程师的判断 | 证据优先于经验判断 |

# 升级与交接协议（阿里云/专有云版）

> **适用版本**：Kubernetes v1.28 - v1.32 | **最后更新**：2026-06-26
> **文档定位**：定义工单智能体在无法独立处理或触及红线时的升级标准、交接内容与沟通话术。

---

## 1. 升级标准

升级分为三类：立即升级、建议升级、可能升级。

### 1.1 立即升级

满足以下任一条件，智能体必须立即停止自动修复并升级：

| 条件 | 说明 |
|:---|:---|
| 生产服务完全不可用 | 核心业务中断，影响外部用户 |
| 超过 30% 节点或全部控制平面异常 | 爆炸半径大，风险不可控 |
| 涉及数据丢失或数据损坏 | 任何可能丢失数据的操作 |
| 触及安全红线 | 越权访问、证书泄露、攻击事件 |
| 需要执行高危写操作 | 删除命名空间、修改 etcd、重启控制平面 |
| 连续三次修复失败 | 根因不明，继续尝试可能扩大影响 |
| 客户明确要求升级 | 客户不满意或要求人工介入 |

### 1.2 建议升级

满足以下任一条件，智能体应建议升级，由值班工程师确认：

| 条件 | 说明 |
|:---|:---|
| 涉及跨多个技术栈 | 网络 + 存储 + 安全同时异常 |
| 需要协调第三方团队 | 云平台、网络、安全、DBA |
| 非标准场景，无历史案例 | 缺乏可执行 SOP |
| 修复窗口要求严格 | 必须在 15 分钟内完成且风险较高 |
| 影响金融/政务等敏感行业 | 合规要求需要人工审批 |

### 1.3 可能升级

以下情况可在继续诊断的同时准备升级材料：

| 条件 | 说明 |
|:---|:---|
| 信息严重不足 | 客户无法提供日志或命令输出 |
| 环境受限 | 无 kubectl/SSH 权限，无法执行验证 |
| 症状反复 | 修复后问题反复出现 |
| 涉及专有云底座 | 怀疑 ASO/天基/专有云组件异常 |

### 1.4 升级权限矩阵

| 角色 | 可决定升级 | 可执行修复 | 说明 |
|:---|:---:|:---:|:---|
| 工单智能体 | 立即升级 / 建议升级 | 低风险只读/修复 | 触及红线必须停止 |
| L1 技术支持 | P1 及以下 | 标准修复 | P0 需上报 |
| L2 SRE | P0/P1 | 高级修复 | 可协调跨团队 |
| 值班经理 | 全部 | 指挥 | 启动战争室 |

## 2. 交接信息模板

### 2.1 结构化交接单

```yaml
incident_id: INC-20260626-001
priority: P0
customer: 阿里云专有云客户 A
cluster_id: ack-prod-hangzhou-01
region: cn-hangzhou
reported_at: "2026-06-26T14:32:00+08:00"
escalated_at: "2026-06-26T14:35:00+08:00"

symptoms:
  - 生产命名空间 production 全部 Pod 处于 Pending
  - kubectl get nodes 显示 60% 节点 NotReady
  - 外部用户无法访问核心业务

impact:
  - 影响范围: production 命名空间，约 120 个 Pod
  - 业务中断: 是
  - 数据丢失风险: 暂不明确

diagnosis_steps:
  - step: 1
    command: kubectl get nodes
    result: 60% NotReady
    timestamp: "2026-06-26T14:33:00+08:00"
  - step: 2
    command: kubectl get events -n production --sort-by='.lastTimestamp'
    result: 大量 NodeNotReady 事件
    timestamp: "2026-06-26T14:34:00+08:00"

root_cause_hypothesis:
  - 控制平面或网络组件异常导致节点失联
  - 专有云底座/ASO 可能触发变更或告警
  confidence: 中

attempted_fixes: []

risk_assessment:
  - 继续自动修复可能导致更多 Pod 被驱逐
  - 建议人工介入确认控制平面状态

recommended_next_steps:
  - 检查 apiserver/etcd 状态
  - 检查 ASO/天基告警
  - 评估是否需要回滚最近变更

attachments:
  - /tmp/incident-20260626-001.log
  - /tmp/node-status.txt
```

### 2.2 简要交接模板（用于 IM / 电话）

```
# 🟢 低风险：只读/信息收集，通常无副作用
【升级通知】
工单号：INC-20260626-001
优先级：P0
客户：阿里云专有云客户 A
现象：production 命名空间 120 个 Pod 全部 Pending，60% 节点 NotReady
影响：业务中断
已执行：kubectl get nodes / describe events
根因假设：控制平面/网络异常，ASO/天基可能有关
建议：立即人工介入，检查 apiserver/etcd/ASO 告警
联系人：值班 SRE / 专有云底座值班
```
### 2.3 交接时间线要求

| 优先级 | 交接单生成时间 | 人工确认接手时间 |
|:---:|:---:|:---:|
| P0 | 5 分钟内 | 15 分钟内 |
| P1 | 10 分钟内 | 30 分钟内 |
| P2 | 30 分钟内 | 2 小时内 |
| P3 | 按队列 | 按队列 |

## 3. 升级话术

### 3.1 开场确认

> “您好，我是 KUDIG 工单智能体。当前问题已触发升级条件，我将为您转接值班工程师。在转接前，我会整理已收集的信息，请稍等。”

### 3.2 说明升级原因

> “由于当前问题涉及 [生产服务中断/大量节点异常/数据丢失风险/需要执行高危操作]，已超出自动处理范围，需要人工专家介入。”

### 3.3 交接时

> “已为您升级到值班工程师 [姓名]，升级单号 [INC-xxx]。我已将诊断过程、已执行命令和当前状态整理成交接单，工程师会继续跟进。”

### 3.4 安抚客户

> “请您放心，升级后会有专人持续跟进。在工程师接手前，请不要对集群执行未经确认的写操作，以免扩大影响。”

### 3.5 升级后跟进

> “值班工程师已接手，当前正在 [检查 apiserver/联系底座团队/排查网络]。我会持续同步进展，预计 [时间] 内给出下一步反馈。”

## 4. 阿里云专有云升级路径

### 4.1 问题分层

| 问题层级 | 责任方 | 接入方式 | 典型问题 |
|:---|:---|:---|:---|
| K8s 应用层 | 客户 SRE / KUDIG 智能体 | 工单系统/IM | Pod 异常、配置错误 |
| ACK 集群层 | 阿里云 ACK 支持团队 | 阿里云工单 / 钉钉群 | 集群组件异常、升级失败 |
| 专有云底座 | 专有云底座 SRE | 天基值班 / ASO 工单 | ECS、VPC、SLB、OSS 异常 |
| ASO 运维平台 | ASO 运维团队 | ASO 运维工单 | ASO 页面报错、任务失败 |
| 天基 | 天基运维团队 | 天基值班热线 | 产品部署、底座变更 |

### 4.2 常见专有云问题升级路径

#### 节点大量 NotReady

```
KUDIG 智能体
  │
  ▼
值班 SRE（确认是否为客户侧问题）
  │
  ├─ 是：修复 kubelet/containerd/网络
  │
  └─ 否 / 涉及底座
      ▼
  提交天基/ASO 值班工单
      ▼
  专有云底座 SRE 排查 ECS/VPC/网络设备
```

#### 证书过期导致控制平面异常

```
KUDIG 智能体
  │
  ▼
值班 SRE 确认证书类型
  │
  ├─ K8s 组件证书：按 SOP 轮转
  │
  └─ 专有云底座证书：提交 ASO 证书续期工单
```

#### SLB / Terway 网络异常

```
KUDIG 智能体
  │
  ▼
检查 Service/Ingress/NetworkPolicy
  │
  ├─ 配置问题：修复配置
  │
  └─ SLB/Terway 异常：提交阿里云 SLB/Terway 工单
```

### 4.3 升级联系方式示例

| 团队 | 值班通道 | 备注 |
|:---|:---|:---|
| 阿里云 ACK 支持 | 阿里云控制台工单 | 提供 ClusterID |
| 专有云底座 SRE | 天基值班热线 / 钉钉群 | 提供 Region、产品实例 |
| ASO 运维团队 | ASO 运维工单系统 | 提供任务 ID、报错截图 |
| 安全响应中心 | 安全工单 / 电话 | 涉及安全事件时使用 |

## 5. 升级后智能体行为

| 阶段 | 行为 |
|:---|:---|
| 升级中 | 停止自动写操作，持续收集日志和事件 |
| 交接后 | 输出标准化交接单，发送给值班工程师和客户 |
| 跟进 | 在工程师授权下，可辅助执行只读验证命令 |
| 闭环 | 修复完成后，更新工单状态并记录经验 |

### 5.1 升级后跟进检查清单

- [ ] 值班工程师已确认接手
- [ ] 客户已收到升级通知
- [ ] 持续收集事件和日志，补充到交接单
- [ ] 不向客户承诺未确认的时间点
- [ ] 修复后协助验证并输出闭环话术

## 6. 战争室与重大事件

对于 P0 级别且影响多个客户的事件，应启动战争室（War Room）机制：

1. 值班经理召集相关团队（ACK、底座、网络、安全）
2. 建立统一沟通频道（钉钉/飞书/腾讯会议）
3. 每 15 分钟同步一次进展
4. 记录关键决策和操作时间线
5. 事件结束后 24 小时内输出 Postmortem

---

## 7. 特殊升级路径

| 场景 | 升级路径 |
|:---|:---|
| 安全事件 | 立即升级安全响应中心，保留证据 |
| 数据泄露 | 升级法务、安全、客户成功团队 |
| 合规审计要求 | 升级合规负责人，暂停自动修复 |
| 媒体/监管关注 | 升级 PR 与高管，统一对外口径 |

## 8. 生产检查清单

- [ ] 升级条件判断是否有明确依据
- [ ] 交接单包含 incident_id、优先级、影响范围、已执行命令
- [ ] 已向客户说明升级原因和下一步安排
- [ ] 已通知对应值班团队/支持渠道
- [ ] 未在升级前执行未经确认的高危写操作
- [ ] 升级后持续跟踪，直至人工确认接手
- [ ] 闭环后将关键信息写入 memory/
- [ ] P0 事件已启动战争室并记录时间线

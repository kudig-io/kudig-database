# 事后复盘模板与主持指南

## 1. Blameless Postmortem 原则

### 1.1 核心理念

```
Blameless ≠ 无责任

核心观点:
  - 人会犯错，系统应该容错
  - 关注"为什么会犯错"而非"谁犯了错"
  - 改进系统和流程，而非惩罚个人
  - 鼓励主动报告和透明分享

禁止行为:
  ✗ "XXX 应该更仔细"
  ✗ "这是 XXX 的责任"
  ✗ "为什么 XXX 会犯这种低级错误"

提倡表达:
  ✓ "系统没有阻止这个操作"
  ✓ "流程中缺少验证步骤"
  ✓ "监控没有覆盖这个场景"
```

### 1.2 复盘触发条件

```
必须进行复盘的事件:

强制复盘:
  - 所有 P0 事件
  - 所有 P1 事件
  - P2 事件中数据丢失或安全相关的
  - 同一根因 7 天内重复发生的 P2

建议复盘:
  - P2 事件（非重复）
  - 有重要经验教训的 P3 事件
  - 接近 P1 的 P2 事件

时间要求:
  - P0: 事件恢复后 24-48 小时内
  - P1: 事件恢复后 48-72 小时内
  - P2: 事件恢复后 1 周内
```

### 5-Why 分析

```
Why 1: 为什么服务不可用？
  → 因为 Pod 被 OOMKilled 后未自动恢复

Why 2: 为什么 Pod 被 OOMKilled？
  → 因为内存使用超过 Limit，触发内核 OOM Killer

Why 3: 为什么内存使用超过 Limit？
  → 因为新版本引入的内存泄漏，在高并发下快速膨胀

Why 4: 为什么新版本没有发现内存泄漏？
  → 因为性能测试只覆盖了正常负载，未覆盖峰值场景

Why 5: 为什么性能测试未覆盖峰值场景？
  → 因为没有定义峰值负载的 SLO，测试用例中缺失
```

## 3. 5-Why 根因分析指南

### 3.1 方法论

```
5-Why 分析步骤:

Step 1: 定义问题
  - 明确描述事件的直接现象
  - 用数据量化影响

Step 2: 问第一个 Why
  - 问: 为什么这个问题会发生？
  - 回答必须基于事实和证据

Step 3: 继续追问
  - 对每个回答继续问 Why
  - 通常 3-5 层可到达根本原因
  - 不要跳过中间层次

Step 4: 验证因果链
  - 反向检查: 修复根因是否能防止事件？
  - 检查是否有多个并行原因

Step 5: 确定根本原因
  - 根本原因是可以通过行动改变的
  - 不要把"人为失误"当作根本原因
```

### 3.2 常见根因模式

```
系统设计类:
  - 缺少容错机制
  - 单点故障
  - 资源未设限
  - 缺少降级策略

流程类:
  - 变更审批不充分
  - 缺少灰度发布
  - 监控覆盖不全
  - 文档不完整

代码类:
  - 未处理异常路径
  - 资源泄漏
  - 并发竞态
  - 边界条件未覆盖

运维类:
  - 配置管理缺陷
  - 备份策略不足
  - 容量规划不足
  - 证书/密钥管理疏忽
```

### 3.3 分析示例

```
事件: API 响应时间飙升至 10 秒

Why 1: 为什么 API 响应变慢？
  → 数据库查询从 50ms 变为 8s

Why 2: 为什么数据库查询变慢？
  → 查询走了全表扫描，未使用索引

Why 3: 为什么索引未被使用？
  → 昨晚的 DDL 变更删除了旧索引，新索引创建失败

Why 4: 为什么新索引创建失败？
  → 磁盘空间不足，ALTER TABLE 操作被取消

Why 5: 为什么磁盘空间不足？
  → 没有自动清理 binlog 的策略，binlog 占满了磁盘

根因: 缺少 binlog 自动清理策略 + DDL 变更流程未验证前置条件
改进:
  1. 配置 binlog 自动过期（7 天）
  2. DDL 变更前检查磁盘空间
  3. 索引变更作为变更审批检查项
```

## 4. 复盘会议主持指南

### 4.1 会议准备

```
会前准备 Checklist:

□ 完成复盘文档初稿
□ 收集所有参与者的时间线补充
□ 准备好相关 Dashboard 和日志
□ 确认所有关键参与者可出席
□ 预定会议室 / 线上会议链接
□ 提前 24 小时发送文档供预读
□ 准备白板/共享文档用于讨论
```

### 4.2 会议议程

```
复盘会议议程（建议 60-90 分钟）:

1. 开场（5 min）
   - 重申 Blameless 原则
   - 确认议程和时间安排
   - 指定记录员

2. 事件回顾（10 min）
   - IC 概述事件经过
   - 确认时间线完整性
   - 补充遗漏信息

3. 影响确认（5 min）
   - 确认影响数据
   - 确认 SLA/SLO 影响

4. 根因讨论（20 min）
   - 5-Why 分析走读
   - 挑战假设，要求证据
   - 确认根本原因

5. 检测与响应评估（10 min）
   - TTD/TTA/TTR 回顾
   - 流程改进讨论

6. 改进项讨论（20 min）
   - 逐项讨论改进措施
   - 确认 Owner 和截止日期
   - 评估优先级

7. 经验教训（10 min）
   - 做得好的方面
   - 需要改进的方面

8. 收尾（5 min）
   - 确认 Action Items
   - 确认文档发布计划
   - 感谢参与者
```

### 4.3 主持技巧

```
主持要点:

引导讨论:
  - 用"是什么导致了..."代替"谁做了..."
  - 鼓励沉默者发言
  - 打断指责性言论，重定向到系统层面

聚焦根因:
  - 当讨论偏离时，拉回到 5-Why 链
  - 要求每个结论都有数据支撑
  - 区分"相关"和"因果"

控制节奏:
  - 每个环节设定时间限制
  - 争议问题先记录，会后讨论
  - 避免在某个点上过度深入

确保产出:
  - 每个改进项都有明确 Owner
  - 截止日期具体到日
  - 会后 24 小时内发布文档
```

### 4.4 常见陷阱

```
避免的陷阱:

✗ 追责导向
  → 转向: "系统如何能防止这个错误？"

✗ 流于表面
  → 转向: 继续追问 Why，直到系统层面

✗ 改进项太笼统
  → "加强监控" → "为 XX 服务添加内存使用率告警，阈值 80%"

✗ 没有 Owner
  → 每个改进项必须有且仅有一个 Owner

✗ 没有截止日期
  → 没有期限的改进项永远不会完成

✗ 只关注技术
  → 也要讨论流程和组织层面的改进
```

      - "Prometheus 告警规则已部署"

### 5.3 完成标准

```
改进项完成标准:

技术改进:
  □ 代码变更已合并
  □ 变更已部署到生产
  □ 相关测试已通过
  □ 文档已更新
  □ 验证改进效果

流程改进:
  □ 文档已更新
  □ 相关人员已培训
  □ 新流程已试运行
  □ 反馈已收集

监控改进:
  □ 告警规则已部署
  □ 告警已验证触发
  □ 告警已接入通知链路
  □ Runbook 已更新
```

## 6. 复盘文档管理

### 6.1 存储结构

```
postmortems/
├── 2026/
│   ├── Q1/
│   │   ├── INC-20260115-001-redis-failover.md
│   │   └── INC-20260201-002-cert-expiry.md
│   ├── Q2/
│   │   └── INC-20260401-003-oom-incident.md
│   └── Q3/
│       └── INC-20260701-004-ddl-incident.md
└── README.md
```

### 6.2 文档状态流转

```
草稿 → 审核中 → 已发布

草稿: IC 或 Scribe 创建
审核中: 分发给参与者审核（24 小时）
已发布: 审核通过后归档
```

### 6.3 知识提取

```
从复盘中提取知识:

高频根因模式:
  - 统计过去 12 个月的根因分类
  - 识别系统性问题
  - 优先投入改进资源

改进项效果:
  - 跟踪改进项完成率
  - 验证改进是否真的减少了类似事件
  - 调整改进优先级

团队能力:
  - 分析 TTD/TTA/TTR 趋势
  - 识别需要加强培训的领域
  - 优化 On-Call 排班
```

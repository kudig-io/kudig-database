# 对外沟通模板与利益相关方通知

## 1. 沟通原则

### 1.1 核心原则

```
事件沟通五原则:

1. 及时性: 宁可早发（哪怕信息不完整），不要晚发
2. 准确性: 只陈述已确认的事实，不猜测根因
3. 一致性: 所有渠道使用相同口径
4. 透明性: 承认问题存在，不隐瞒影响范围
5. 行动导向: 每次更新都说明"我们正在做什么"
```

### 1.2 沟通节奏

| 级别 | 初始通知 | 进展更新 | 恢复通知 | 事后摘要 |
|------|---------|---------|---------|---------|
| P0 | ≤ 15 min | 每 30 min | 恢复后 15 min | 24 hr 内 |
| P1 | ≤ 30 min | 每 1 hr | 恢复后 30 min | 48 hr 内 |
| P2 | ≤ 2 hr | 每日 | 恢复后 2 hr | 按需 |
| P3 | 不通知 | 不通知 | 不通知 | 不通知 |

## 2. 内部状态更新模板

### 2.1 War Room 状态更新

```markdown
## [HH:MM] 状态更新 #N

**事件 ID**: INC-YYYYMMDD-NNN
**级别**: P0/P1
**开始时间**: YYYY-MM-DD HH:MM UTC+8
**持续时间**: X 小时 Y 分钟
**当前状态**: 🔴 排查中 / 🟡 已定位 / 🔵 修复中 / 🟢 已恢复

**影响范围**:
- 受影响服务: <服务列表>
- 受影响用户比例: X%
- 错误类型: 5xx / 超时 / 功能不可用
- 业务影响: 支付受阻 / 登录失败 / 数据延迟

**当前进展**:
- [已完成] <排查动作 1> → <结论>
- [进行中] <排查动作 2>
- [待开始] <计划动作>

**根因分析**:
- 假设: <当前最可能的根因>
- 置信度: 高/中/低
- 证据: <支撑数据>

**下一步行动**:
1. <行动 1> — Owner: <人名> — ETA: <时间>
2. <行动 2> — Owner: <人名> — ETA: <时间>

**需要支持**:
- <如有需求>
```

```

ETA: 预计 20 分钟内恢复
```

## 3. 客户通知模板

### 3.1 初始通知

```
主题: [Investigating] 服务异常通知 — <受影响功能>

尊敬的用户,

我们检测到 <受影响功能/服务> 出现异常，部分用户可能遇到 <具体现象>。

我们的工程团队正在积极排查和修复中。

影响范围:
- 受影响功能: <功能列表>
- 受影响用户: <范围描述>
- 预计影响时间: 评估中

我们将在 30 分钟内提供下一次更新。

如有紧急问题，请联系 support@example.com。

— <公司名> 运维团队
```

### 3.2 进展通知

```
主题: [Update] 服务异常通知 — INC-YYYYMMDD-NNN

尊敬的用户,

关于 <受影响功能> 的异常，以下是最新进展:

当前状态: <已定位 / 修复中>
根因: <简要说明（如已确认）>
已采取措施:
- <措施 1>
- <措施 2>

临时解决方案:
- <如有 Workaround，请提供步骤>

预计恢复时间: <时间>

我们将在 <时间> 或有重大进展时提供下一次更新。

— <公司名> 运维团队
```

### 3.3 恢复通知

```
主题: [Resolved] 服务已恢复正常 — INC-YYYYMMDD-NNN

尊敬的用户,

我们很高兴地通知您，<受影响功能> 已完全恢复正常。

事件摘要:
- 开始时间: YYYY-MM-DD HH:MM UTC+8
- 恢复时间: YYYY-MM-DD HH:MM UTC+8
- 持续时间: X 小时 Y 分钟
- 影响范围: <概述>

根因: <简要说明>

已采取措施:
- <修复措施>
- <预防措施>

如有任何问题或仍遇到异常，请联系 support@example.com。

我们对此次服务中断深表歉意，并将持续改进以避免类似事件。

— <公司名> 运维团队
```

### 3.4 简短版本（适用于社交媒体/StatusPage）

```
[Investigating]
我们正在调查 <功能> 的性能问题。部分用户可能受到影响。团队正在积极处理中。

问题已定位：<简要说明>。团队正在实施修复。

[Monitoring]

```

## 5. StatusPage 更新规范

### 5.1 组件状态定义

| 状态 | 含义 | 使用场景 |
|------|------|---------|
| Operational | 正常运行 | 默认状态 |
| Degraded Performance | 性能降级 | 功能可用但变慢 |
| Partial Outage | 部分中断 | 部分用户/功能受影响 |
| Major Outage | 严重中断 | 大规模不可用 |
| Under Maintenance | 维护中 | 计划维护窗口 |

### 5.2 StatusPage 更新模板

```yaml
# statuspage-updates.yaml

investigating:
  title: "[Investigating] <受影响功能>"
  body: |
    我们正在调查 <功能> 的异常情况。
    部分用户可能遇到 <具体现象>。
    我们正在积极排查，将在 30 分钟内提供更新。
    components:
      - name: "<组件名>"
        status: "partial_outage"

identified:
  title: "[Identified] <受影响功能>"
  body: |
    问题已定位：根因为 <简要说明>。
    我们正在实施修复方案，预计 <时间> 恢复。
  components:
    - name: "<组件名>"
      status: "partial_outage"

monitoring:
  title: "[Monitoring] <受影响功能>"
  body: |
    修复已部署，服务正在恢复中。
    我们正在监控各项指标，确认完全恢复后将更新状态。
  components:
    - name: "<组件名>"
      status: "degraded_performance"

resolved:
  title: "[Resolved] <受影响功能>"
  body: |
    服务已完全恢复正常运行。
    此次事件持续 X 小时 Y 分钟，我们将在 48 小时内发布事后分析报告。
    对此次中断给您带来的不便，我们深表歉意。
  components:
    - name: "<组件名>"
      status: "operational"
```

### 5.3 StatusPage 更新流程

```
StatusPage 更新 Checklist:

初始通知:
  □ 确认受影响组件列表
  □ 设置组件状态
  □ 发布 Investigating 更新
  □ 确认订阅用户收到通知

进展更新:
  □ 更新组件状态（如有变化）
  □ 发布进展更新
  □ 保持与内部状态一致

恢复通知:
  □ 将所有组件设为 Operational
  □ 发布 Resolved 更新
  □ 注明事后报告发布时间

注意事项:
  - 不要在 StatusPage 上讨论根因细节
  - 不要承诺具体的恢复时间（除非高度确定）
  - 保持措辞专业、简洁
  - 避免技术术语，面向普通用户
```

## 6. 客服团队支持

### 6.1 客服话术模板

```
初始话术（客户询问时）:
"感谢您的反馈。我们已注意到 <功能> 存在异常，
工程团队正在全力排查和修复中。
我们会在恢复后第一时间通知您。
给您带来的不便深表歉意。"

进展话术（客户追问时）:
"感谢您的耐心。目前问题已定位，团队正在修复中。
预计 <时间> 恢复。如有紧急需求，
建议您 <临时解决方案>。"

恢复话术:
"很高兴通知您，<功能> 已恢复正常。
如您仍遇到问题，请尝试清除缓存后重试，
或联系我们获取进一步帮助。"
```

### 6.2 FAQ 模板

```
Q: 什么时候能恢复？
A: 我们预计在 <时间> 恢复，如有变化会及时通知。

Q: 我的数据安全吗？
A: 是的，此次事件不影响数据安全和完整性。

Q: 是否有补偿措施？
A: 我们会在事件结束后评估影响并公布补偿方案。

Q: 如何避免再次发生？
A: 我们将在事后报告中详细说明根因和改进措施。
```

## 7. 沟通审批流程

```
沟通审批链:

内部状态更新:
  - War Room 内: IC 直接批准
  - 公司范围: IC + Manager 批准

客户通知:
  - 初始通知: IC + Comms + Manager
  - 进展通知: IC + Comms
  - 恢复通知: IC + Comms + Manager
  - 事后报告: IC + Manager + VP

管理层汇报:
  - P0 简报: IC 直接发送
  - P1 简报: Manager 审核后发送

社交媒体:
  - 所有发布: Comms + PR 团队审核
```

## 8. 多语言支持

```
通知语言策略:

默认: 中文
用户群体以外企为主时: 中英双语
社交媒体: 根据平台选择语言

翻译流程:
  - Comms 撰写原稿
  - 指定人员翻译（或使用翻译服务）
  - 翻译后由母语人士审核
  - 确认后同步发布
```

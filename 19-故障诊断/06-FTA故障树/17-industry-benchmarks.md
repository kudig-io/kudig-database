## 17.1 Google SRE 的故障分析实践

Google 是 FTA 思想在 IT 运维领域应用的先驱。其核心实践体现在以下方面：

```
Google SRE 的 FTA 相关实践:

1. Error Budget (错误预算)
   ← FTA 概率计算的直接应用
   → SLO = 99.95% → Error Budget = 0.05%
   → 当 Error Budget 耗尽 → 冻结变更、全力修复
   → FTA 用于分析哪些底事件消耗了最多 Error Budget

2. Postmortem Culture (事后分析文化)
   ← FTA 问题回溯验证的制度化
   → 每次 P0/P1 事故后编写 Postmortem
   → Postmortem 中包含问题传播路径分析
   → 分析结果反馈到故障分析体系中

3. Borgmon → Monarch → [[23-实体/07-可观测性/prometheus|prometheus]]
   ← FTA 底事件可观测性的技术支撑
   → Google 内部监控系统的演进
   → 每个 FTA 底事件都有对应的监控指标
   → 告警规则与故障树路径直接关联

关键成果:
  - P0 问题 MTTR < 10 分钟
  - 全球基础设施可用性 > 99.99%
  - 自动化处理覆盖 > 80% 的已知问题
```

## 17.2 Netflix 的混沌工程 + FTA

```
Netflix 的实践模型:

1. Chaos Engineering 验证 FTA:
   ┌─────────────┐
   │ 设计 FTA    │
   │ (故障树)    │
   └──────┬──────┘
          │
          ▼
   ┌─────────────┐
   │ Chaos Monkey│ ── 随机杀死实例
   │ Chaos Kong  │ ── 区域问题
   │ Latency     │ ── 注入延迟
   │ Monkey      │
   └──────┬──────┘
          │
          ▼
   ┌─────────────┐
   │ FTA 验证    │
   │ 路径是否正确 │
   └──────┬──────┘
          │
       ┌──┴──┐
       │ Yes │ → FTA 有效
       │ No  │ → 更新 FTA，新增遗漏路径
       └─────┘

2. 关键实践:
   - 在生产环境执行混沌实验 (而非仅在测试环境)
   - 每个实验都对应 FTA 中的一个或多个底事件
   - 实验结果自动更新 FTA 概率数据
   - "Chaos Engineering 是 FTA 的动态测试"

3. 成效:
   - 服务可用性: 99.99%+
   - 区域故障恢复: < 7 分钟
   - 每年发现并修复 200+ 个弹性问题
```

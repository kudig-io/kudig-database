# 发布工程与变更管理最佳实践

> 统计显示，生产事故的最大诱因是**变更本身**。大规模集群的发布工程目标：让每次变更**小步、可观测、自动回滚**，让变更管理从"人盯人"变成"系统守门"。

## 1. 发布策略选型矩阵

| 策略 | 原理 | 适用 | 风险点 |
|---|---|---|---|
| RollingUpdate | 分批替换 Pod | 大多数无状态服务（默认） | 新旧版本短暂共存，接口需兼容 |
| Recreate | 全停再启 | 开发环境、单副本有状态 | 有停机窗口，生产慎用 |
| 蓝绿 | 双环境整体切换 | 数据库 schema 变更等重大版本 | 双倍资源、状态同步难 |
| 金丝雀 | 小比例流量验证后逐步放大 | 核心服务每次发布 | 需流量调度能力（Ingress/网关/网格） |

无状态服务滚动参数基线：`maxSurge: 25%`、`maxUnavailable: 0`（宁可慢不能断），大促前核心服务临时调 `maxSurge: 10%` 更稳。

## 2. 渐进式交付（金丝雀的工程化）

手工金丝雀的问题在于"放量靠拍、回滚靠盯"。标准做法：**Argo Rollouts / Flagger + 指标自动分析**。

```yaml
# Argo Rollouts 金丝雀策略示例（核心片段）
strategy:
  canary:
    steps:
    - setWeight: 10        # 10% 流量
    - pause: {duration: 5m}
    - setWeight: 30
    - pause: {duration: 5m}
    - setWeight: 60
    - pause: {duration: 5m}
    # 每一步由 AnalysisTemplate 自动判定：
    # 错误率 < 阈值 且 P99 < 基线×1.5 才进入下一步，否则自动回滚
```

**自动分析的指标选择：**

- 必选：新版本 Pod 错误率（5xx 占比）、P99 时延 vs 基线
- 推荐：业务核心指标（下单成功率、消息消费 lag）
- 与 SLO 联动：发布烧错误预算的速度超阈值即熔断（[[15-slo-chaos-engineering#2. 错误预算驱动运营]]）

**落地要求：**

- 核心服务（P0/P1）100% 走自动分析金丝雀；普通服务至少滚动发布 + 发布后指标观察
- 回滚演练：每季度实测一次"金丝雀自动回滚"真实触发
- 金丝雀期间 HPA 与 Rollouts 的副本数关系要评估（HPA 会干扰权重计算，按官方模式配置）

## 3. 变更分类分级与窗口制度

| 级别 | 定义 | 审批 | 窗口 |
|---|---|---|---|
| C0 紧急 | 故障修复、安全应急 | 事后补审 | 随时（值班长批准） |
| C1 常规 | 日常业务发布 | 流水线自动 + 代码评审 | 工作日业务低峰 |
| C2 重大 | 架构变更、集群升级、中间件大版本 | 变更评审会 | 预约窗口 + 值班加强 |
| C3 高危 | 数据迁移、网络割接、证书轮换 | 评审会 + 业务方确认 | 深夜窗口 + 回滚演练先行 |

**冻结日历（制度化的变更禁令）：**

- 大促/重大活动前 T-1 天至活动结束：冻结 C1+ 变更（C0 除外）
- 护网/重保期间：全面冻结（[[08-security-defense-checklist#8. 护网期间运行机制]]）
- 每月集群升级窗口、每季度证书轮换窗口：提前预约公示
- 错误预算耗尽 → 自动进入冻结（SLO 驱动的客观标准，见 [[15-slo-chaos-engineering]]）

## 4. 配置变更治理

配置变更（ConfigMap/Secret/限流阈值/特性开关）与代码发布**同等风险**，但常被当作"小事"：

1. 配置全部进 Git，与代码同评审、同流水线、可回滚——禁止 kubectl edit 改生产
2. 配置变更与代码发布解耦：可独立发布、独立回滚
3. 大配置（>100KB）进 ConfigMap 前评审——过大的配置既伤 etcd 又难 diff
4. Secret 变更额外管控：敏感配置变更走双人复核
5. 特性开关（Feature Flag）：新功能默认开关关闭上线，逐步放开——把"发布"和"上线"解耦，是降低发布风险性价比最高的工程实践

## 5. GitOps 多环境晋级

```text
feature 分支 → 合并 main → CI（构建/扫描/签名）
     │
     ▼
dev 环境自动同步 ──冒烟通过──▶ staging 晋级 PR ──评审──▶ prod 晋级 PR
                                                              │
                                            审批 + 窗口校验 + 同步 + 金丝雀分析
```

- 晋级以 PR 为载体：每次环境晋级有评审记录、有 diff、可回滚（revert PR）
- 配置漂移检测：GitOps 控制器持续对比集群实际态与 Git 期望态，漂移自动告警/纠正（ArgoCD sync policy / Flux drift detection）
- 多集群分发见 [[10-multi-cluster#2.2 应用与资源分发]]

## 6. 发布可观测性与质量度量

- 每次发布自动生成"发布单"：变更内容、影响服务、金丝雀分析结果、操作人——进事件时间线系统，故障定位时先查"最近 30 分钟有没有变更"
- 发布质量度量（纳入团队效能看板）：
  - 变更失败率（引发事故的发布占比）——目标 < 5%
  - 回滚率与平均回滚耗时
  - 发布频率与 lead time（DORA 指标）
- 高频小步发布优于低频大批量：批量越大，故障定位变量越多

## 7. 常见反模式

| 反模式 | 后果 |
|---|---|
| 滚动发布 maxUnavailable > 0 在高峰期执行 | 发布中容量下降叠加流量高峰，自我制造事故 |
| 金丝雀只看"Pod 不挂" | 业务级故障（逻辑错误、数据错误）全部漏网 |
| 配置不走 Git 直接改 | 漂移累积，故障时无人能回答"改了什么" |
| 回滚方案 = "重新发旧版本" | CI 构建 10 分钟，故障多烧 10 分钟预算；回滚必须是秒级（保留旧副本/镜像） |
| 冻结期走"特批"变常态 | 冻结制度名存实亡 |
| 大版本一把梭（半年憋大招） | 变更变量过多，出问题无法归因 |

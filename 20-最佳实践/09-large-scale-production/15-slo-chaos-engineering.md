# SLO 体系与混沌工程

> "没挂过"不等于"可靠"。大规模集群的可靠性工程需要两把尺子：**SLO 度量现实**，**混沌工程探索边界**。两者结合才能回答"我们到底能承受什么"。

## 1. 双层 SLO 体系

### 1.1 平台 SLO（集群层，面向业务方的承诺）

参考 Kubernetes 官方可伸缩性 SLO 建立平台层基线：

| SLI | SLO 参考 | 说明 |
|---|---|---|
| API 响应性 | 99% API 调用 < 1s（P99） | 官方大规模集群 SLO 基线 |
| Pod 启动时延 | 99% Pod（镜像已预热）启动 < 5s | 官方 SLO；生产建议补充"镜像未预热"场景指标 |
| 集群可用性 | 99.95%（APIServer 可服务时间） | 含计划内维护则另算 |
| 调度时延 | P99 调度决策 < 100ms | 大集群调度健康信号 |
| 节点恢复 | 故障节点替换 < 15min | 弹性能力承诺 |

### 1.2 业务 SLO（服务层）

- 从用户体验倒推 SLI：可用性（成功请求率）、时延（P95/P99）、新鲜度（数据类）
- SLO 设定原则：比现状好一点、比用户期望低一点（100% 是错误目标——成本无限大且剥夺变更空间）
- 典型起步值：核心服务 99.95%，普通服务 99.9%，内部工具 99.5%

## 2. 错误预算驱动运营

错误预算 = 1 − SLO（如 99.95% → 月度预算约 21.6 分钟不可用）。

**预算消耗告警（burn rate alerting）双窗口：**

| 窗口 | 燃烧率阈值 | 级别 | 含义 |
|---|---|---|---|
| 1h（快烧） | > 14.4× 基准 | P1 | 2 天内烧完月度预算，立即处理 |
| 6h（中烧） | > 6× | P2 | 5 天内烧完 |
| 3d（慢烧） | > 1× | P3 | 按当前速率本月预算耗尽，排期处理 |

**预算治理动作：**

- 预算充足 → 允许激进变更（升级、混沌演练、新功能快速发布）
- 预算消耗 > 50% → 变更评审收紧
- 预算耗尽 → **变更冻结**，全力恢复可靠性，直到预算回正
- 这套机制把"什么时候能上变更"从争论变成算术

## 3. 混沌工程演练矩阵

按故障域分层设计演练，每格都应有标准剧本（稳态假设 → 注入 → 观察 → 恢复 → 结论）：

| 层 | 演练场景 | 验证目标 |
|---|---|---|
| 节点 | 随机杀业务节点、节点网络分区、磁盘写满、CPU 打满 | 驱逐与重调度、PDB 有效性、驱逐风暴防护 |
| AZ | 单 AZ 网络隔离/节点全失 | 跨 AZ 分布有效性、容量冗余 |
| 控制面 | 杀 1 台 Master、杀 1 个 etcd 节点、APIServer 限流注入 | HA 有效性、APF 行为 |
| 网络 | CoreDNS 故障、Pod 间时延注入、丢包注入 | DNS 缓存兜底、超时与重试配置合理性 |
| 存储 | 卷 IO 时延注入、CSI 故障 | 应用降级能力、告警有效性 |
| 依赖 | DB/MQ/下游服务不可用或慢 | 超时/熔断/降级配置，**防雪崩** |
| 应用 | 杀 Pod、注入 5xx、流量突增 | HPA 行为、优雅上下线、限流 |

**工具选型：** Chaos Mesh（K8s 原生 CRD、场景全）、Litmus（GitOps 友好）、云厂商 FIS（EKS FIS 等）。

**安全护栏（大规模必须）：**

- 演练从预发开始，生产演练必须：小爆炸半径先行（1 个节点 → 1 个 AZ）+ 熔断条件预定义 + 一键停止 + 值班全员知情
- 高峰期、大促、护网期间禁止演练
- 每次演练记录"预期 vs 实际"，偏差即缺陷，录入改进 backlog

## 4. GameDay 制度化

| 频率 | 内容 |
|---|---|
| 每月 | 单场景演练（从演练矩阵轮选） |
| 每季 | 综合演练：复合故障（如 AZ 故障 + 流量高峰）、全链路压测叠加故障注入 |
| 每半年 | 容灾切换演练：整集群/整地域不可用的切换与回切（见 [[10-multi-cluster#5. 跨集群容灾与多活]]） |
| 每年 | 灾难恢复大考：假设主集群数据全损，从备份重建到恢复服务，实测 RTO/RPO |

**GameDay 标准流程：**

1. 剧本评审（稳态假设、观测点、熔断条件、回滚方案）
2. 执行与观察（专人盯 Dashboard、记录时间线）
3. 复盘（30 分钟内出时间线，48 小时内出报告）
4. 改进项跟踪到人、到期复查——**演练不复盘等于白演**

## 5. 与告警和发布的联动

- SLO 告警上线后逐步替代资源阈值告警（CPU 高不等于用户受损）
- 发布系统接入 SLO：发布后 SLI 异常自动回滚（Argo Rollouts Analysis / Flagger）
- 混沌演练期间关联告警静默（避免演练制造告警疲劳），但保留记录

## 6. 常见反模式

| 反模式 | 后果 |
|---|---|
| SLO 定 100% | 永远违规，预算机制失效，团队对告警麻木 |
| 只有阈值告警 | 告警多而无意义，真问题被淹没 |
| 演练只在预发做 | 生产环境的真实依赖（容量、数据量）永远没验证过 |
| 演练无熔断条件 | 演练本身演变成生产事故 |
| 演练发现的问题不进 backlog | 同样的坑每次演练都重新发现一次 |

# 多集群与联邦管理最佳实践

> 当单集群逼近上限（拆分信号见 [[01-overview#1.3 单集群 vs 多集群的决策点]]），架构重心从"集群内治理"转向"集群间治理"。多集群的核心挑战：**一致性（配置不漂移）、可控性（爆炸半径）、连通性（网络与发现）**。

## 1. 多集群架构模式

| 模式 | 特征 | 适用 |
|---|---|---|
| 集群复制（Stamp） | 每个集群是同构的"邮票"，配置模板化批量复制 | 大规模 SaaS、按租户/区域分片 |
| 功能分层 | 按职能拆分：生产/灾备/大数据/AI 各自成集群 | 大多数企业的自然形态 |
| 主备/多活 | 同业务跨集群双活或主备 | 高容灾要求核心业务 |
| 云边协同 | 中心集群 + 边缘集群（KubeEdge/OpenYurt） | 边缘计算场景 |

**集群划分维度优先级**：故障域（地域/AZ）> 合规边界 > 业务域 > 环境（生产/预发）。避免按"部门"随意建集群——集群数量膨胀本身就是运维灾难。

## 2. 管理平面选型

### 2.1 集群生命周期（建、升、删）

- **Cluster API（CAPI）**：声明式管理集群生命周期，社区标准，适合自建/多云
- 云厂商托管：EKS/GKE/AKS/ACK API + Terraform/eksctl 模板化
- 原则：**集群即代码**——任何集群都能从 Git 仓库完整重建，禁止控制台手工建生产集群

### 2.2 应用与资源分发

| 方案 | 特点 | 适用 |
|---|---|---|
| Karmada | 控制面集中，资源模板 + OverridePolicy 分发到成员集群，支持多集群调度与故障转移 | 需要跨集群调度/容灾编排 |
| Argo CD（fleet 模式） | GitOps 拉模型，每集群一个 ApplicationSet | 以发布为中心的团队 |
| Flux | 同 GitOps 拉模型，轻量 | 同上 |
| 云厂商舰队（ACK One Fleet、GKE Fleet/Anthos、Azure Fleet） | 托管托管控制面 + 托管 ArgoCD，跨云/边/IDC 统一治理 | 云上为主的企业 |

### 2.3 选型建议

- 已有 GitOps 体系 → ArgoCD/Flux ApplicationSet 起步最轻
- 需要"一次定义、多集群自适应分发 + 跨集群容灾调度" → Karmada
- 混合云/边缘且采购了云厂商体系 → 用厂商舰队，避免重复造轮子

## 3. 统一治理（防漂移）

多集群最大的隐性风险是**配置漂移**：几十个集群各自被手工改过，半年后谁也说不清差异。对策：

1. **基线分发**：把"每个集群都必须有"的东西（PSS 标签、默认 NetworkPolicy、LimitRange、监控 Agent、安全策略）做成基线包，通过 GitOps/舰队统一分发，漂移自动纠正
2. **策略即代码**：OPA/Kyverno 策略集中管理、统一下发、统一审计（见 [[12-security-hardening-baseline]]）
3. **身份联邦**：统一 OIDC 接 IdP，集群 RBAC 模板化；杜绝每集群独立维护本地账号
4. **镜像仓库**：统一私有仓库 + 各集群就近 mirror/proxy，杜绝公网直拉
5. **巡检**：定期跨集群 diff（配置、版本、策略覆盖度），输出漂移报告

## 4. 多集群网络

- **IP 规划是地基**：全局唯一 IPAM 表，任何新集群入网段必须先登记；Pod/Service CIDR 集群间不重叠（重叠将永久堵死互联可能）
- 跨集群服务发现与互联：
  - 轻量：东西向网关 + DNS 联邦
  - 标准：MCS API（Multi-Cluster Services）、Submariner、Cilium ClusterMesh
  - 云厂商：云企业网/VPC Peering + 厂商多集群方案
- 跨集群流量必须过统一网关或网格，便于熔断、限流与审计（零信任原则不因跨集群而放松）

## 5. 跨集群容灾与多活

- **数据决定形态**：有无状态服务多活容易；有状态服务（DB/中间件）以主备 + 数据层复制为主，不要盲目追求双活
- 流量调度：GTM/全局负载做跨集群入口调度，健康检查与摘除自动化
- 容灾演练：每半年执行一次"整集群不可用 → 流量切换到备份集群 → 数据校验"的全流程演练，记录 RTO/RPO 实测值
- GitOps 是容灾的隐藏支柱：集群状态可随时在空集群上重建，RTO 从"天"级降到"小时"级

## 6. 多集群可观测性

- 每集群本地 Prometheus 采集 + 中心化查询/告警层（Thanos/Mimir/厂商方案）
- 告警必须带 `cluster` 标签并在统一视图聚合；值班不能靠切十几个 Grafana
- 容量视图：全局资源水位（各集群 allocatable 使用率）一屏呈现，支撑跨集群调度决策

## 7. 常见反模式

| 反模式 | 后果 |
|---|---|
| 集群无模板手工建 | 配置漂移、无法重建、升级各自为政 |
| 按部门随意开集群 | 集群数量失控，治理成本指数上升 |
| 网段不登记就建集群 | IP 重叠后跨集群互联永久无解 |
| 多活但无数据层方案 | 流量切过去数据不一致，灾难放大 |
| 各集群独立账号体系 | 权限审计无法做，离职回收漏成筛子 |

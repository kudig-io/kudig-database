# Paralus 访问控制（Paralus）

## 概述

Paralus 是 CNCF Sandbox 项目，为 Kubernetes 提供集中式的访问控制和审计平台，支持 SSO、RBAC 和 kubectl 访问代理，是多集群权限管理的统一方案。

## 核心概念/原理

- **集中访问控制**：统一管理多集群的 K8s 访问权限
- **SSO 集成**：支持 OIDC/SAML/LDAP 身份源
- **CNCF Sandbox**：Rafay 主导
- **审计追踪**：完整的 kubectl 命令审计日志

## 关键机制或特性

- Zero Trust Access 代理（无需 VPN）
- 基于角色的 kubectl 访问控制
- 多集群的 RBAC 统一管理
- SSO 和 MFA 集成
- 命令审计和回放
- JIT（Just-in-Time）临时权限
- 用户/组/项目层次管理

## 使用场景与最佳实践

- 多集群的 K8s 权限集中管理
- 开发团队的 kubectl 安全访问
- 合规要求下的访问审计
- SSO 集成的统一认证
- 临时权限的安全分发

## 架构深度解析

### Paralus 多集群访问架构

```
┌──────────────────────────────────────────────────────────────┐
│  用户（kubectl / 浏览器）                                      │
│   │  ① SSO 认证（OIDC + MFA）                                 │
│   ▼                                                          │
│  ┌─────────────────────────────────────────────────────────┐  │
│  │ Paralus（控制面）                                        │  │
│  │ ├─ 认证：SSO/MFA/JIT 临时权限                            │  │
│  │ ├─ 授权：用户/组/项目 → 集群 RBAC 映射                  │  │
│  │ ├─ 审计：命令记录与回放                                  │  │
│  │ └─ 签发：短生命周期 kubeconfig/证书                      │  │
│  └──────────────────────────┬──────────────────────────────┘  │
│                             │ 转发请求                       │
│                             ▼                                │
│  ┌─────────────────────────────────────────────────────────┐  │
│  │ Zero Trust Proxy（ztka 代理）                            │  │
│  │ ├─ 与各集群 kube-apiserver 建立反向隧道                  │  │
│  │ └─ 无需 VPN/公网暴露，安全转发 kubectl 请求              │  │
│  └──────────────────────────┬──────────────────────────────┘  │
│                             │ 隧道                          │
│                             ▼                                │
│  ┌─────────────────────────────────────────────────────────┐  │
│  │ 目标集群 K8s API Server                                  │  │
│  │ └─ 校验 Paralus 签发证书 → RBAC 授权执行                 │  │
│  └─────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────┘
```

### 源码关键路径（paralus/paralus）

| 模块 | 路径 | 关键职责 |
|---|---|---|
| 控制面 API | pkg/ | 认证/授权/集群管理 |
| 代理 | ztka/ | 反向代理与隧道 |
| 认证 | pkg/authenticators/ | OIDC/MFA 处理 |
| 审计 | pkg/audit/ | 命令审计与回放 |
| 前端 | web/ | 管理控制台 |

### 流程步骤

1. 用户通过 SSO（OIDC+MFA）登录 Paralus，按用户/组映射到项目与集群。
2. 授权检查通过后，Paralus 签发短期 kubeconfig/证书（JIT 可限时）。
3. kubectl 请求经 Zero Trust Proxy 隧道转发到目标集群 API Server。
4. API Server 校验证书身份并按集群内 RBAC 授权执行。
5. 全部命令记录审计（用户/时间/集群/命令），支持回放取证。

## 生产案例

### 案例 1：代理隧道故障导致多集群访问中断（2023 年事件）

| 时间 | 事件 |
|---|---|
| T+0 | 某集群网络变更后代理隧道断开，所有 kubectl 请求超时 |
| T+20min | 定位为代理与 API Server 间 TLS 证书未随集群升级轮换 |
| T+1h | 重新建立隧道并轮换证书；补加隧道健康监控与自动重建 |
| T+2h | 多集群巡检确认全部隧道恢复 |

- **根因**：隧道单点 + 证书轮换缺失 + 无健康监控。
- **修复命令**（诊断 + 重建）：
```bash
# 🟢 查看代理隧道状态与日志
kubectl -n paralus logs deploy/ztka --tail=50 | grep -i tunnel
# 🔴 重建隧道（重新部署代理或刷新证书）
kubectl -n paralus rollout restart deploy/ztka
```

### 案例 2：JIT 临时权限被滥用

- **现象**：审计发现某 JIT 授权窗口被反复延长，远超申请时长。
- **诊断**：JIT 权限审批流缺失（自助申请即批准）；时长上限未配置。
- **修复**：JIT 申请走审批流（管理员批准）；时长上限（如 4h）强制；权限到期自动吊销并审计。

## 对比评测

| 维度 | Paralus | Teleport | 传统 VPN+kubeconfig |
|---|---|---|---|
| 认证 | SSO/MFA/JIT | SSO/MFA 丰富 | 无/弱 |
| 网络模型 | Zero Trust 隧道 | 代理/隧道 | 全网络暴露 |
| 审计 | 命令审计+回放 | 会话审计 | 无 |
| 多集群 | 项目级统一管理 | 集群接入 | 手动 |
| 适用 | K8s 多集群访问 | 混合基础设施 | 简单场景 |

- **选型建议**：多集群 K8s 集中访问选 Paralus；混合基础设施选 Teleport；简单场景直接 kubeconfig（配 IP 白名单）。

## 故障排查速查

| 症状 | 可能原因 | 排查命令 |
|---|---|---|
| 登录失败 | SSO/OIDC 配置错误 | 查看认证日志与 IdP 连通性 |
| kubectl 超时 | 隧道断开/代理故障 | 检查 ztka 状态与隧道健康 |
| 权限不足 | RBAC 映射缺失 | 核对项目-集群-用户映射 |
| JIT 不生效 | 审批流/时长配置 | 检查 JIT 策略与审批记录 |
| 审计缺失 | 审计管道故障 | 检查审计存储与导出 |

## 生产部署清单

- [ ] Paralus 控制面高可用（多副本+数据库），代理多实例容灾
- [ ] SSO 集成（OIDC+MFA），禁用本地密码认证
- [ ] JIT 权限走审批流，时长上限强制，到期自动吊销

## 面试要点

> 以下 Q&A 覆盖 Paralus 面试高频考点，按"概念 → 原理 → 实战"递进。

1. **Q：Paralus 的 Zero Trust 访问模型与传统 VPN 有何本质区别？**
   A：VPN 先建立网络层信任（用户进入内网即拥有网络可达性），暴露面大；Paralus 是应用层零信任：不依赖网络可达（kubectl 请求经代理隧道转发），每次访问都要身份认证（SSO+MFA）+ 授权（项目/集群/RBAC 映射）+ 审计（命令记录），集群 API Server 无需公网暴露，最小化攻击面。

2. **Q：Paralus 如何实现多集群的统一权限管理？**
   A：通过"用户/组 → 项目 → 集群"模型：项目定义一组集群与角色的映射关系，用户按组加入项目即获得对应集群 RBAC 权限；Paralus 统一签发短期证书，免去为每个集群手工维护 kubeconfig。配合 JIT 临时权限，实现"集中管理、最小权限、可审计"的多集群访问治理。

3. **Q：JIT（Just-in-Time）临时权限在生产中的设计要点？**
   A：① 申请必须走审批流（不能自助即批）；② 时长上限强制（如 4h）且到期自动吊销；③ 权限范围最小化（限定集群+命名空间+动作）；④ 全流程审计（申请/批准/使用/吊销）；⑤ 定期回顾 JIT 使用报告，识别滥用模式（频繁申请同一权限应转为长期最小权限）。

## 运维要点

- 高可用：控制面多副本 + 数据库高可用；代理多实例 + 隧道自动重建。
- 认证治理：SSO 为唯一认证源，MFA 强制，本地账号禁用。
- 权限治理：项目-集群映射季度审计；JIT 报告月度回顾。
- 审计：命令审计全量归档，回放功能定期演练（取证能力验证）。
- 告警：隧道健康、登录失败率、JIT 异常使用、审计管道延迟。

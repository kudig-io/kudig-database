> **生产环境安全提示**
>
> 本文档包含可直接执行的运维命令。执行前请确认：当前目标集群与 Namespace 是否正确；是否具备足够的 RBAC 权限；是否已在非生产环境验证。命令风险等级标注：🔴 高风险（可能造成数据丢失或服务中断）、🟡 中风险（会修改集群状态，但通常可回滚）、🟢 低风险/只读（信息收集，无副作用）。




# 工单回复话术：请求信息

> **适用版本**: 阿里云 / 专有云 K8s 运维工单 | **最后更新**: 2026-06-29
> **文档定位**: 为工单智能体提供标准化的“请求信息”话术变体，帮助高效收集诊断所需信息。

---

## 变量说明

| 变量 | 含义 |
|:---|:---|
| `{{user_name}}` | 用户称呼 |
| `{{incident_id}}` | 工单编号 |
| `{{issue_summary}}` | 问题摘要 |
| `{{affected_resource}}` | 受影响资源 |
| `{{command}}` | 建议执行的命令 |
| `{{log_source}}` | 日志来源/路径 |

---

## 模板 1：通用信息请求

```
{{user_name}} 您好，

为更准确地定位【{{issue_summary}}】问题，请您协助提供以下信息：

1. 受影响资源的名称与命名空间（如 Pod、Service、Node 名称）
2. 问题首次出现的时间
3. 是否最近有变更（发布、扩缩容、配置变更）
4. 相关错误截图或关键日志片段

收到后我们会立即进行下一步分析，感谢您的配合。
```

**适用场景**：首次诊断信息不足，需要通用信息补充。

---

## 模板 2：请求执行诊断命令

```
{{user_name}} 您好，

请协助在集群中执行以下命令，并将输出结果贴回：

```bash
{{command}}
```

这些命令均为只读操作，不会修改您的集群配置。
如您无法直接执行，请告知原因，我们会提供替代方案。
```
# 🟢 低风险：只读/信息收集，通常无副作用
**适用场景**：需要用户执行 kubectl 等只读命令获取现场数据。

---

## 模板 3：请求权限或访问方式

```
{{user_name}} 您好，

当前排查需要访问【{{affected_resource}}】，请您确认是否可以提供：

1. 只读 kubeconfig 或临时运维账号
2. 集群管理控制台截图
3. 日志系统查询权限

我们会严格遵循最小权限原则，仅在授权范围内操作。
```

**适用场景**：需要登录用户集群或查看专有云平台信息。

---

## 模板 4：信息不足时的回复

```
{{user_name}} 您好，

根据目前提供的信息，尚不足以判断【{{issue_summary}}】的根因。
为避免误操作，建议您先补充以下任一信息：

- 具体的错误信息或告警内容
- 受影响资源的名称
- 问题发生的时间范围

信息越完整，我们的判断会越准确，谢谢。
```

**适用场景**：用户只提供了模糊描述，无法定位。

---

## 模板 5：请求变更记录

```
{{user_name}} 您好，

为排查【{{issue_summary}}】，请协助提供最近 24 小时内的变更记录：

1. 是否有应用发布、配置变更或扩缩容？
2. 是否有集群组件、节点、网络或存储的变更？
3. 是否有证书、密钥或权限的更新？

变更记录越完整，定位速度越快，感谢您的配合。
```

**适用场景**：问题可能与近期变更相关。

---

## 模板 6：请求日志与事件

```
{{user_name}} 您好，

为分析【{{issue_summary}}】，请提供以下日志或事件信息：

1. 受影响 Pod 的最近日志：`kubectl logs <pod-name> -n <namespace> --tail=200`
2. Pod 事件：`kubectl describe pod <pod-name> -n <namespace>`
3. 集群事件：`kubectl get events -n <namespace> --sort-by='.lastTimestamp' | tail -50`
4. 如接入日志系统，请提供 {{log_source}} 中相关时间段的日志

谢谢。
```

**适用场景**：需要详细日志定位根因。

---

## 模板 7：请求截图与录屏

```
{{user_name}} 您好，

为更直观理解【{{issue_summary}}】，请您提供：

1. 错误页面或控制台的完整截图
2. 告警通知的截图
3. 如涉及操作步骤，可提供简短录屏

这些信息有助于我们快速复现问题，感谢您的配合。
```

**适用场景**：前端或控制台类问题。

---

## 模板 8：请求业务影响说明

```
{{user_name}} 您好，

为评估【{{issue_summary}}】的紧急程度并制定处理方案，请协助确认：

1. 该问题影响的业务模块或功能
2. 受影响的用户数量或范围
3. 是否有交易、支付等关键流程受阻
4. 业务方可接受的恢复时间

收到后我们会据此调整优先级与处理策略，谢谢。
```

**适用场景**：需要评估业务影响以确定优先级。

---

## 使用提示

1. 每次请求信息尽量具体，避免一次性要求过多。
2. 提供的命令应为只读，并说明安全性。
3. 如用户无法提供某些信息，及时给出替代方案。

---

## 信息请求优先级

1. **先请求最关键信息**：资源名称、命名空间、错误现象。
2. **再请求变更记录**：是否有发布、扩缩容、配置变更。
3. **最后请求权限与日志**：在确认需要进一步排查时申请。

## 组合示例

```
Step 2（请求信息）:
请协助执行以下命令并提供输出：

kubectl get pods -n production -l app=order-service
kubectl describe pod <pod-name> -n production
kubectl logs <pod-name> -n production --previous
```

{{user_name}} = 李女士

kubectl get svc -n production
```
这些命令均为只读操作，不会修改您的集群配置。
如您无法直接执行，请告知原因，我们会提供替代方案。
```

## 模板 8：请求监控截图

```
{{user_name}} 您好，

为快速判断【{{issue_summary}}】的影响范围，请提供以下截图：

1. Prometheus/Grafana 相关指标面板
2. ACK 控制台中受影响资源的状态
3. 告警通知详情

截图越清晰，定位速度越快，谢谢。
```

## 模板 9：请求复现步骤

```
{{user_name}} 您好，

为定位【{{issue_summary}}】，请协助提供稳定复现步骤：

1. 触发条件（请求参数、操作路径）
2. 复现频率（必现/偶发）
3. 受影响用户或环境
4. 已知的规避方法

我们将根据复现步骤在测试环境进一步验证。
```

## 模板使用注意事项

1. 请求信息时一次不要索要过多内容，分批次请求。
2. 提供的命令应为只读，若涉及写操作需特别说明。
3. 对关键信息应设定回复时限，避免工单挂起。
4. 收到信息后应立即确认并进入下一步分析。

## 模板 10：请求业务方协助定位

```
{{user_name}} 您好，

【{{issue_summary}}】涉及业务逻辑，为缩小排查范围，请协助确认：

1. 该问题是否仅在特定功能/页面出现？
2. 是否特定用户群体或地域受影响？
3. 最近一次业务变更或发布是什么？

感谢您的配合。
```

## 模板 11：请求提供集群基本信息

```
{{user_name}} 您好，

为排查【{{issue_summary}}】，请提供以下集群基本信息：

1. 集群 ID 或名称
2. Kubernetes 版本
3. 节点数量与实例规格
4. CNI 类型（Terway/Calico/Flannel）
5. 是否使用托管版 ACK 或专有云 ASO

这些信息有助于我们快速判断环境与已知问题，谢谢。
```

## 常见错误与避免

| 错误做法 | 正确做法 |
|:---|:---|
| 一次索要过多信息 | 分批次、按优先级请求 |
| 不提供命令说明 | 解释命令用途与是否只读 |
| 使用专业缩写 | 对用户解释必要术语 |
| 不设定回复时限 | 给出期望回复时间 |

# Kubernetes 对象管理

## 概述

`kubectl` 命令行工具支持多种方式来创建和管理 Kubernetes 对象。本文档概述了不同的管理方法及其适用场景，帮助用户选择适合自身工作流的对象管理方式。

## 核心概念/原理

Kubernetes 对象管理主要有三种技术：

| 管理技术 | 操作对象 | 推荐环境 | 支持协作者 | 学习曲线 |
|---------|---------|---------|-----------|---------|
| 命令式命令（Imperative commands） | 实时对象 | 开发项目 | 1+ | 最低 |
| 命令式对象配置（Imperative object configuration） | 单个文件 | 生产项目 | 1 | 中等 |
| 声明式对象配置（Declarative object configuration） | 文件目录 | 生产项目 | 1+ | 最高 |

**警告**：同一个 Kubernetes 对象应只使用一种技术管理，混合使用会导致未定义行为。

### 命令式命令

用户直接对集群中的实时对象进行操作，将操作作为参数或标志传递给 `kubectl`。

**示例**：`kubectl create deployment nginx --image nginx`

- **优点**：表达为单一动作词，只需一步即可更改集群。
- **缺点**：不与变更审查流程集成，不提供审计追踪，除了实时对象外没有配置记录，不提供创建新对象的模板。

### 命令式对象配置

`kubectl` 指定操作（create、replace 等）、可选标志和至少一个文件名。文件必须包含 YAML 或 JSON 格式的完整对象定义。

**警告**：`kubectl replace` 会用新提供的规范替换现有规范，丢弃配置文件中缺失的所有更改。不适用于其规范独立于配置文件更新的资源类型（如 `LoadBalancer` 类型的 Service）。

- **优点**：可存储在版本控制系统中，可与变更审查和审计集成，提供创建新对象的模板。
- **缺点**：需要对对象模式有基本了解，需要额外编写 YAML 文件的步骤。

### 声明式对象配置

用户对本地存储的对象配置文件进行操作，但不定义要对文件执行的操作。`kubectl` 按对象自动检测创建、更新和删除操作，支持对整个目录进行处理。

**注意**：声明式对象配置会保留其他写入者所做的更改，即使这些更改没有合并回对象配置文件。这是通过使用 `patch` API 操作仅写入观察到的差异来实现的，而不是使用 `replace` 替换整个配置。

- **优点**：保留对实时对象的直接更改，更好地支持目录操作和按对象自动检测操作类型。
- **缺点**：调试更困难，意外的部分更新会产生复杂的合并和 patch 操作。

## 使用场景

- **开发/测试环境**：使用命令式命令快速创建或删除对象。
- **生产环境（单人管理）**：使用命令式对象配置，配置文件纳入版本控制。
- **生产环境（团队协作/GitOps）**：使用声明式对象配置，配合 `kubectl apply` 或 Kustomize 实现持续交付。

## 最佳实践/注意事项

- 生产工作负载优先使用声明式管理（`kubectl apply`），便于追踪变更和协作。
- 避免对同一对象混合使用命令式和声明式管理。
- 在使用 `replace` 前，确保了解其会完全替换对象规范的副作用。

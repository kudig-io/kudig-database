# 复盘方法论总览

kuba-database 对每个故障案例采用四重视角进行复盘。四者互补，共同构成完整的故障分析框架：

| 视角 | 关注点 | 核心问题 | 在案例中的落点 |
|---|---|---|---|
| **SRE**（Site Reliability Engineering） | 系统与流程 | 系统为什么会失效？如何让它不再失效？ | 根因分析、时间线、预防措施 |
| **CRE**（Customer Reliability Engineering） | 客户与信任 | 客户感知到了什么？沟通是否及时透明？ | 影响评估、对外沟通、SLA/SLO 视角 |
| **FDE**（Field Data Engineering） | 数据与证据 | 现场数据（指标/日志/链路）如何还原真相？ | 时间线佐证、检测缺口、可观测性改进 |
| **SA**（Solution Architect） | 关系与架构 | 故障如何冲击客户关系（客情危机）？客户架构该如何改进（技术危机）？ | 客情危机评估、客户架构启示 |

## 四视角如何协同

1. **FDE 先行**：一切结论必须有数据支撑。时间线中的每个关键节点应能对应到指标突变、日志证据或外部观测（如第三方监控、社交媒体信号）。
2. **SRE 定因**：在数据基础上区分三类因素——
   - **触发因素（Trigger）**：直接引发故障的事件（一次变更、一条命令、一个请求）。
   - **根本原因（Root Cause）**：使触发因素得以造成破坏的系统性缺陷。
   - **扩大因素（Aggravating Factors）**：使影响范围扩大、恢复时间延长的因素（如监控依赖故障系统本身、回滚通道失效）。
3. **CRE 定损**：从客户侧度量影响——受影响用户比例、功能维度（读/写/登录/支付）、错误预算消耗、沟通时延（故障发生 → 首次对外通告）。
4. **SA 定策**：从关系与架构双维度给出应对——客情危机（信任修复、主动沟通、商业补偿）与技术危机（客户架构单点识别、自保能力建设、选型启示）。

## 无指责原则（Blameless）

- 人会犯错是常量，**系统允许单个错误造成大范围破坏才是变量**。
- 复盘中禁止出现对个人的追责表述；所有"人为失误"必须转写为可改进的系统缺陷（缺少防护、缺少确认、缺少灰度）。
- 详见 [sre-postmortem.md](sre-postmortem.md)。

## 每个案例的方法论落地检查

- [ ] 时间线的关键节点有数据/来源佐证（FDE）
- [ ] 明确区分 Trigger / Root Cause / Aggravating Factors（SRE）
- [ ] 至少一条完整的 5 Whys 链或贡献因素图（SRE）
- [ ] 记录 TTD（检测耗时）、TTM（缓解耗时）、TTR（完全恢复耗时），无法获知时标注"未披露"（FDE）
- [ ] 评估客户影响面与官方沟通表现（CRE）
- [ ] 评估客情危机（信任/沟通/补偿/修复）与技术危机（架构启示/自保能力）（SA）
- [ ] 每条经验教训对应至少一条可执行的预防措施（SRE/CRE）

## 非技术类案例的适配（business-operations / sa-architecture）

案例库除技术故障外，还收录两类**非传统故障**（领域：`business-operations` 商务运营、`sa-architecture` SA 架构与客情）：

| 类别 | 典型形态 | 四视角适配要点 |
|---|---|---|
| 商务运营 | 合同终止（Parler×AWS）、域名/资产过期（Marketo）、定价政策（Reddit API）、合规制裁（GitHub 2019）、API 生态封杀（Twitter 2023）、计费基础设施故障（Google Cloud 账单 2022） | SRE 关注"商务失效如何传导为技术失效"；CRE 关注用户/客户的实际损失；FDE 证据来自公告、诉讼文件、官方状态页与第三方观测；SA 聚焦合同条款与供应商依赖风险 |
| SA 架构决策 | 单区域部署（Clerk×Cloud Run）、对供应商承诺过度信任（Clerk 数据库事件 2025：自动升级 + 连接池隐性耦合） | 按普通故障流程分析，但"根因"落在架构决策本身；SA（技术危机）即本类核心教训的提炼 |
| SA 客情危机 | 信任崩塌（Unity 收费危机）、沟通失败（Twitter API 封杀） | 无服务中断时，severity 按生态影响面与持续性定级；TTD/TTM 不适用时标注"不适用"；SA（客情危机）即本类核心教训的提炼 |

此类案例同样遵守无指责原则：把"决策失误"转写为"决策机制缺少的校验关口"（如缺少信任影响评估、缺少技术可行性验证）。

## 政企公共服务案例的适配（public-services）

领域 `public-services` 收录政府、国企与公共服务机构（public-sector）的故障——故障本身多为**传统技术故障**（硬件、容量、网络、安全），但机构属性带来四点差异：

| 差异点 | 表现 | 四视角适配要点 |
|---|---|---|
| 垄断性与无替代 | 12306（唯一购票渠道）、粤康码（唯一亮码入口）、NOTAM（唯一安全通告源）、NHS（唯一医疗服务） | CRE 影响面按"全民/全省/全国"度量，客户无法选择替代供应商，可靠性预期接近 100%；"存在替代渠道"（窗口售票、市级码、纸质表格）是重要的减轻因素 |
| 社会敏感窗口 | 春运购票（12306）、高考期间通信（广东电信）、普查夜（ABS）、早高峰亮码（粤康码） | 时间线需标注社会窗口；SEV 定级参考"窗口期故障"的放大效应；SRE 容量模型必须按确定性尖峰设计 |
| 监管与问责 | 紧急调度会（广东电信）、国会/审计署调查（FAA、NHS）、参议院听证（ABS） | FDE 证据链包含监管报告（NAO、参议院委员会）与官方通告（ATCSCC），权威性高于一般媒体；SA（客情危机）升级为"公信力危机" |
| 根因披露节奏 | 官方根因常滞后或缺失（广东电信未公布、粤康码先称"维护"） | FDE 须交叉印证并标注证据等级，区分官方口径、媒体报道与第三方推断，避免把推测当事实 |

政企案例的根因分类与其他领域一致（hardware-facility / network-routing / capacity-overload / operational-safeguard / security-attack 等），无需特殊枚举；`company_type: public-sector` 用于统计维度区分。

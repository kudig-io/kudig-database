复盘报告到处都是，可检索的复盘知识几乎没有。

重大故障后的复盘散落在各家状态页、工程博客与监管文件里。想回答「上次 BGP 出事是什么模式」，你得翻几十个来源，读完仍然只有叙事、没有结构。

叙事没有结构
时间线、根因、对策埋在几千字里，读完记不住、找不到、比不了。kuba 把每篇拆成固定章节 + YAML Frontmatter 结构化元数据，机器和人都能索引。
视角只有一个
大多数复盘只回答「系统为什么挂」。客户感知了什么？数据证据能否还原真相？客户关系与架构受何冲击？kuba 用四重视角补全链条。
无法横向比较
级联失效、爆炸半径、恢复尾这些跨案例模式，需要结构化数据才能定量。kuba 的统一 schema 让 94 个案例可以按公司 / 领域 / 根因 / 等级任意切。

四重视角，一条完整证据链。

每个案例不只是「发生了什么」。四个视角互为补充，覆盖从数据证据到客户信任再到架构决策的完整链条。

视角关注什么核心问题在案例中的落点
SRE 系统与流程 系统为什么会失效？如何让它不再失效？根因分析（因素三分法 / 5 Whys）· 时间线 · 预防措施 Trigger / Root Cause / Aggravating Factors 三分定性；预防、缩小爆炸半径、检测、恢复四层防御
CRE 客户与信任 客户感知到了什么？沟通是否及时透明？影响评估 · 对外沟通表现 · SLA/SLO 视角 错误预算消耗量化（如 S3 2017 一次消耗 5 年预算）、状态页表现、次生影响面
FDE 数据与证据 现场数据如何还原真相？时间线佐证（E1/E2…）· 检测缺口 · 可观测性改进 TTD / TTM / TTR 三项时间指标；用监控与日志把「当时发生了什么」钉死
SA 关系与架构 故障如何冲击客户关系？客户架构该如何改进？客情危机评估（SA）· 客户架构启示（SA） 单点依赖诊断（Coinbase 锁定单 AZ）、多 AZ / 多云建议、商务与合同层面启示
FDE 先行→ SRE 定因→ CRE 定损→ SA 定策 数据支撑一切 · 因果区分事实与推断 · 信任修复与架构建议收尾

数据质量，是这套库的底线。

只收证据，不收情绪。四条红线，每个案例录入时校验。

01只收录可验证公开信息
每个案例必须附带至少一个权威来源链接，官方复盘报告优先；第三方分析仅作佐证并显式标注。
02无指责（Blameless）
聚焦系统性因素，不针对个人；转述官方报告时保持中立。这是 SRE 复盘文化的前提，不是姿态。
03事实与推断分明
官方未披露的细节若来自第三方分析，必须标注「第三方推断」；未披露信息在案例中显式列出。
04持续更新，全程可追溯
官方披露新细节时更新案例并递增 last_updated；历史通过 Git 追溯，任何修改可审计。

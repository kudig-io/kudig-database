# 厂商技术声明的可信度分层：客户技术交流中的事实核查方法

> **核心命题**：客户交流中最危险的不是"讲错"，而是**被追问到第三层时无法回答**。解法不是背更多知识，而是**把每条断言的证据等级标注出来**——能引用的引用，推导的说明推导，不知道的明确说不知道。

---

## 1. 四层可信度分级

任何一条技术断言，先判断它落在哪一层：

| 层级 | 定义 | 客户交流可用性 | 被追问时的表现 |
|------|------|--------------|--------------|
| **L1 官方直接陈述** | 官方文档/规格页明确写出，可直接引用原文 | ✅ 放心讲，附链接 | 给链接 |
| **L2 官方可推导** | 官方给出公式/参数，结论需自己计算 | ✅ 可以讲，**需说明推导过程** | 复述公式 |
| **L3 通用原理外推** | 行业通用机制，套用到具体产品实现 | ⚠️ **不可作为结论**，只能作为"参考方向" | 容易露馅 |
| **L4 无法证实** | 内部实现、未公开接口、私有机制 | ❌ **不对外讲** | 必须明确划界 |

### 分级示例（存储领域）

| 断言 | 层级 | 判定依据 |
|------|------|---------|
| "OSS 标准存储多 AZ 可用性 99.995%" | **L1** | 规格页直接列出 |
| "PL1 想跑满 5 万 IOPS 需约 964 GiB" | **L2** | 官方公式 `min{1800+50×容量, 50000}` 计算得出 |
| "分片上传中断后已上传分片仍计量" | **L1** | 官方 FAQ 原文 |
| "盘古用 LSM Compaction，删除会导致写放大" | **L3** | LSM 是通用原理，但盘古内部实现未公开 |
| "专有云可查看盘古 GC 队列积压" | **L4** | 无公开接口，取决于环境是否开放 |
| "ceph_osd_utilization 指标可监控 OSD 水位" | **错误** | 该指标名在 Ceph 中不存在（见第 4 节） |

## 2. 核查流程（每条断言过一遍）

```text
① 定位断言原文
   ↓ 找到出处了吗？
   ├─ 是 → 属于 L1/L2，标注链接与公式
   └─ 否 ↓
② 能否在官方文档中找到等价表述？
   ├─ 能 → L1/L2
   └─ 不能 ↓
③ 这是否是行业通用机制？
   ├─ 是 → L3，标记"参考方向，非产品实现"
   └─ 否 → L4，标记"不对外"
```

**三条硬规则**：

1. **没有出处的数字不进材料**（SLA 赔付比例、未公开的内部指标、未确认的阈值默认值）；
2. **公式可以推导，但不能省略推导过程**——L2 的结论必须能现场复现；
3. **L3/L4 不是"不能说"，而是"换个说法"**——见下一节。

## 3. 边界话术：把"讲不清"变成加分项

客户交流中，坦率划界比含糊其辞更能建立信任。

| 场景 | ❌ 错误应对 | ✅ 正确话术 |
|------|-----------|-----------|
| 被问底层实现 | 编一套听起来专业的机制 | "底层实现厂商不公开，**我们能确定的是你看到的数字是怎么来的、以及你能做什么**" |
| 被问"有没有命令" | 给一个不确定的命令 | "**没有公开接口，也不需要你调用**——这是平台设计，客户侧责任边界是保证语义正确" |
| 被问未确认的数字 | 给一个大概值 | "这个数要以目标版本官方文档为准，**我可以在会后就特定版本给你确认**" |

> **为什么这招有效**：客户（尤其是技术型客户）判断专业度的标准，往往不是你**知道多少**，而是你**知道自己不知道什么**。一份敢标注"此处为推演"的材料，比一份全是肯定句的材料可信度高得多。

## 4. 典型案例：这些错误真的发生过

以下案例均来自本库实际修订记录，可作为反例库。

### 4.1 虚构的监控指标名（最危险）

某 Ceph 运维文档中写了三条告警规则：`ceph_osd_utilization`、`ceph_pool_percent_used`、`ceph_pg_active_clean`。

**问题**：这三个指标名在 Ceph 中**都不存在**。指标名看起来完全合理（命名风格与真实指标一致），但规则会**静默失效**——不报错、不告警，直到真正出事时才发现监控是空的。

**正确做法**：以官方导出的指标为准。Ceph 真实指标包括 `ceph_health_detail{name="OSD_NEARFULL"}`、`ceph_osd_up`、`ceph_pg_total` 等，官方告警规则见 Rook 的 `localrules.yaml`。

> **教训**：**"看起来对"是指标类错误的最大伪装**。凡是写进告警的指标名，必须能指向一份官方规则文件或导出样例。

### 4.2 已归档的版本线

某文档标注"适用 Ceph Reef (18.x) / Quincy (17.x)"。

**问题**：这两个版本**已归档**，当前活跃版本是 Umbrella (21.2) / Tentacle (20.2) / Squid (19.2)。

> **教训**：版本号是**时效性最强**的断言，核查必须带日期，并在文档中写明"核验时间"。

### 4.3 用通用原理代替产品实现

某材料解释"OSS 删除后水位上涨"，归因于"盘古 tombstone + LSM Compaction + WAL 写放大"。

**问题**：
- 盘古内部实现**未公开**，这套机制是**把存储引擎通用原理推演到具体产品**（L3）；
- 更关键的是**观测对象错位**：客户看到的是**计量口径**，不是物理盘占用，两者之间隔着平台异步回收。

**正确做法**：改用可查证的 L1 机制——版本控制删标记、回收站、**未完成分片计量**、生命周期延迟至次日 08:00、CopyObject 转型残留。

### 4.4 名称相似导致的概念混淆

`tapdisk` vs Linux `tun/tap`：前者是**块存储**（XenServer 虚拟磁盘后端），后者是**网络**（虚拟网卡）。名字都带 "tap"，领域完全不同。

> **教训**：**术语撞名**在跨栈交流时高频出现，讲之前先确认对方所指。

## 5. 交流材料的交付标准

一份可交付给客户的存储技术材料，应满足：

| 标准 | 含义 |
|------|------|
| **每个数字有出处** | 附官方链接，标注核验日期 |
| **每个结论标注层级** | L1/L2 可直接用；L3 标注"推演"；L4 明确"不对外" |
| **有明确的边界声明** | 哪些是厂商责任、哪些是客户责任 |
| **可执行** | 客户拿到能自查，而不是只有结论 |
| **有反例库** | 列出常见错误说法，避免团队重复踩坑 |

---

## 6. 反面模式清单

| 反面模式 | 表现 | 后果 |
|---------|------|------|
| **结构工整但无出处** | 分点清晰、术语专业，但每条都查不到原文 | 被追问时临场编造 |
| **观测对象错位** | 用 A 的读数解释 B 的现象 | 结论方向性错误 |
| **过度自信** | 全是肯定句，没有"待确认" | 一处被证伪，全场失信 |
| **版本裸奔** | 只写"最新版"不写版本号与日期 | 半年后全部失效 |
| **混淆层级** | 把平台内部实现当客户可操作能力讲 | 客户按建议操作后无效 |

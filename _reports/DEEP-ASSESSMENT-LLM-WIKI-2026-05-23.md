# KUDIG 语料库深度评估报告

> 评估维度：**LLM-Wiki 语料质量**（预训练/微调适用性） × **人类专家直接阅读体验**
> 关键前提：**不进入 RAG 工作流** — 评估重点为「知识内化」（LLM 权重记忆）+「专家翻阅参考」
> 评估时间：2026-05-23
> 语料规模：5,389 Markdown / 80.3M 字符 / ~64.3M tokens

---

## 一、执行摘要

| 维度 | 评分 | 说明 |
|:---|:---:|:---|
| **LLM-Wiki 语料质量** | **3.9/5** | 代码密度极高（57.9%），命令模式学习条件优越；但 prose 密度低（31.1%），自然语言推理链薄弱 |
| **人类专家阅读体验** | **4.0/5** | 信息层级清晰、命令可执行性强；但 Skill 偏薄、段落碎片化、重复 title 干扰导航 |
| **综合评分** | **~4.0/5** | 达到「专家参考级」水准，距离「LLM 微调黄金语料」（4.5+）需补齐 prose 密度和 Skill 深度 |

**关键缺口**：
1. **Prose 密度仅 31.1%** — 代码块占 57.9%，自然语言推理知识密度不足，LLM 学到的「理解」少于「记忆」
2. **Skill 平均 122 行** — 作为专家 runbook 太薄，作为微调语料难以让 LLM 建立完整诊断-修复模式
3. **命令多样性 8.2%** — LLM 容易过拟合到常见命令模板，场景化推理能力受限

## 二、LLM-Wiki 语料质量评估

### 2.1 语料规模与 token 效率（4.2/5）

**规模**
- 总字符：80.3M → ~64.3M tokens（按 0.8 token/char 估算）
- 排除 domain-19（CNCF Landscape 简介）后：~48.2M tokens
- 这是一个**中型预训练/微调语料**，规模介于 CodeAlpaca（~20M）和 SlimPajama（~600B）之间

**Token 效率分析**

| 内容类型 | 占比 | 对 LLM 的价值 | 评估 |
|:---|:---:|:---|:---|
| **Code blocks** | 57.9% | ⭐⭐⭐ 命令模式、配置模板、脚本逻辑 | 极高 — 教 LLM 学会「执行」 |
| **Prose** | 31.1% | ⭐⭐⭐ 推理逻辑、根因分析、决策依据 | 偏低 — 教 LLM 学会「思考」 |
| **Tables** | 7.4% | ⭐⭐ 结构化对照、参数矩阵 | 适中 — 辅助模式识别 |
| **Frontmatter** | 3.7% | ⭐ 元数据、标签、意图查询 | 低 — 对权重学习几乎无贡献 |

**核心发现**：
> 这是一份**「执行导向」**语料，而非**「推理导向」**语料。LLM 从中能学到大量 kubectl/helm/yaml 命令模式，但难以建立「症状→根因→修复」的深层因果推理链。

**对比参考**：
- 理想微调语料（如 MetaMath）的 prose:code 比例约为 7:3
- KUDIG 的 prose:code 比例为 3:6（倒置）

### 2.2 结构化程度与模板一致性（4.3/5）

**优势**
- **Frontmatter 标准化 87.7%**：title/category/tags/intent_queries/trigger_keywords/prerequisites 六元组覆盖率高
- **QA 语料格式统一**：5,159 对 QA 严格遵循 `io_pair_id → skill_ref → command → output_pattern → diagnosis → action` 六段式结构
- **Skill 模板一致**：每个 Skill 含「何时使用→快速分级→诊断步骤→修复动作→验证」标准流程
- **FTA 推理骨架**：44 个组件问题树，统一使用 Mermaid 语法，布尔门（AND/OR）结构清晰

**劣势**
- **948 个重复 title**：训练时可能导致 LLM 对同名文档的注意力分散
- **Skill frontmatter 不完整**：仅 5/17 个 Skill 标注 `agent_execution_mode: L2-semi-auto`，执行风险分级未普及
- **QA YAML 解析不稳定**：含 YAML anchor（`&id001`），部分解析器不支持

### 2.3 知识密度与去噪（3.5/5）

**去噪分析**

| 噪声源 | 占比 | 影响 | 建议 |
|:---|:---:|:---|:---|
| domain-19 CNCF Landscape | 21% | 大量一句话项目简介，稀释核心领域密度 | 预训练时排除或降采样 |
| Frontmatter 意图查询 | 3.7% | "K8s Node NotReady 诊断与修复 是什么" 等自指语句 | 对权重学习无贡献，可裁剪 |
| Wikilink 标记 | ~5% | `[[Kubernetes|Kubernetes]]` 双括号语法 | LLM 不理解 Obsidian 链接，视为噪声 |
| 空/模板化段落 | ~8% | "<typical output lines...>" 等占位符 | 需填充真实输出 |

**有效知识密度**：排除上述噪声后，有效 token 约 **35-40M**，实际可用率 55-60%。

### 2.4 推理链完整性（3.8/5）

**优势**
- **FTA → Skill → Case Study 三层推理链已建立**：
  - FTA（44 个）：「顶事件 → 中间事件 → 底事件 → 诊断命令」布尔推理
  - Skill（17 个）：「症状识别 → 快速分级 → 分步诊断 → 修复动作 → 验证」流程推理
  - Case Study（23 个）：「问题现象 → 时间线诊断 → 根因 → 修复 → 复盘」叙事推理
- **Synthesis 跨域连接**：52 个合成页面建立「A × B」跨域推理，帮助 LLM 建立概念间关联

**劣势**
- **Skill 深度不足**：平均 122 行，远不及专家级 runbook（通常 500-1000 行）。LLM 从 122 行中学到的是「检查清单」而非「完整推理」
- **Case Study 与 Skill 连接松散**：Case Study 中的 `skill-ref` 链接密度低，LLM 难以建立「这个案例对应哪个 Skill」的映射
- **缺乏负面样本**：QA 中无「这个命令不该在这种情况下使用」的反面教材，LLM 容易产生幻觉
- **Critical severity 仅 0.4%**：高危场景训练不足，LLM 对 P0 问题的推理能力弱

### 2.5 指令跟随格式（4.0/5）

**优势**
- **QA 语料天然适合 SFT（监督微调）**：`command` + `output_pattern` → `diagnosis` + `action` 的输入-输出对可直接用于训练
- **表格指令清晰**：大量「参数 → 说明 → 阈值」的三列表格，适合 LLM 学习结构化响应
- **Mermaid 图指令**：2,530 个 Mermaid 图提供可视化推理指令

**劣势**
- **命令多样性 8.2%**：5,159 条命令中仅 425 条唯一，`kubectl get nodes` 重复 77 次。LLM 微调后容易生成同质化响应
- **Action 字段空缺**：大量 `action: []`，LLM 学到的是「诊断无修复」
- **缺乏 CoT（Chain-of-Thought）标注**：无 "Let me think step by step" 风格的推理过程标注，不利于思维链微调

## 三、人类专家阅读体验评估

### 3.1 信息架构与导航（4.3/5）

**优势**
- **三层目录清晰**：Domain → Topic → 文档，专家可快速定位到目标领域
- **418 个 MOC/README**：入口导航丰富，domain-10 的问题诊断有完整的索引体系
- **Wikilink 密度 10.8/文件**：专家可跟随链接跳转至相关概念、Skill、FTA
- **Intent queries 字段**：frontmatter 中的「用户可能怎么问」帮助专家预判使用场景

**劣势**
- **948 个重复 title**：大量 "Day X:"、"Domain Y:" 的重复命名，专家在全局搜索时难以区分
- **domain-19 干扰**：21% 的体积是 CNCF 项目一句话简介，专家翻阅时会遇到大量低价值内容
- **缺乏「专家速览」模式**：无「只看命令」或「只看根因」的折叠视图

### 3.2 内容深度与可执行性（3.7/5）

**优势**
- **命令可直接复制**：11,861 个 bash 代码块，专家可直接复制粘贴执行
- **FTA 深度优秀**：平均 991 行，含完整布尔门、诊断命令、预期输出模式
- **Case Study 真实感强**：平均 286 行，含具体时间线、Prometheus 告警、kubectl 输出
- **表格密度高**：19.9 个表格/文件，参数对照清晰

**劣势**
- **Skill 偏薄——核心痛点**：
  | 文档类型 | 平均行数 | 专家预期 | 差距 |
  |:---|:---:|:---:|:---|
  | FTA | 991 | 500-1500 | ✅ 符合预期 |
  | Case Study | 286 | 200-400 | ✅ 符合预期 |
  | **Skill** | **122** | **400-800** | 🔴 **仅为预期的 15-30%** |
  | Training | 525 | 300-800 | ✅ 符合预期 |
  
  **专家视角**：一个 122 行的 Skill 只能覆盖「检查清单」级别，无法覆盖「遇到 X 情况时，先检查 A，如果 A 正常则检查 B，如果 B 异常则执行 C，否则执行 D」的完整决策树。

- **段落碎片化**：中位数 115 字符（约 20-30 个中文字），大量短列表项打断阅读流
- **验证环节薄弱**：Skill 中 `verify-*.sh` 脚本覆盖率低，专家修复后缺乏自动化验证手段

### 3.3 可视化与决策支持（4.2/5）

**优势**
- **Mermaid 图 2,530 个**：FTA 树、架构图、流程图丰富，帮助专家建立视觉记忆
- **快速分级表格**：Skill 开头含「症状 → 检测方法 → 置信度」三列表格，专家可 30 秒内判断优先级
- **决策树嵌入**：问题排查文档中大量 `ConfigMap 问题 → Pod 启动失败？ → not found / key not defined` 树形结构

**劣势**
- **缺乏交互式决策树**：静态 Markdown 无法根据用户选择展开分支，专家需手动滚动查找
- **Mermaid 渲染依赖**：部分环境（如终端阅读）不支持 Mermaid 渲染，图变成纯文本

### 3.4 更新与维护（3.5/5）

**优势**
- **K8s 版本标注**：frontmatter 含 `k8s_versions: [1.28.x, 1.29.x, 1.30.x, 1.31.x, 1.32.x]`，专家可判断时效性
- **last_updated 字段**：大部分文档含更新日期

**劣势**
- **缺乏版本差异标注**：无 "v1.28 vs v1.32 的变化" 段落，专家难以判断命令是否适用于当前集群版本
- **无变更日志追踪**：Skill/FTA 的修改历史未在文档内体现，专家不知道「这个修复方法是最新的还是 3 个月前的」

## 四、关键发现矩阵

| 发现 | 对 LLM 微调的影响 | 对专家阅读的影响 | 紧急度 | 建议 |
|:---|:---|:---|:---:|:---|
| **Prose 仅 31.1%，Code 57.9%** | LLM 学会「执行」但学不会「推理」 | 专家获得命令但缺乏决策上下文 | 🔴 高 | 为每个 Skill 补充 200-400 行「为什么这样做」的 prose 解释 |
| **Skill 平均 122 行** | 难以建立完整诊断-修复模式 | runbook 太薄，专家需自行脑补 | 🔴 高 | 将 Skill 扩充至 400-600 行，增加分支决策和边界条件 |
| **命令多样性 8.2%** | 同质化响应，场景适配差 | 不同问题给出相同命令 | 🔴 高 | 引入参数化模板，同一场景生成 3-5 个变体命令 |
| **948 个重复 title** | 注意力分散，训练噪声 | 搜索困难，难以区分 | 🟠 中 | 去重或添加唯一标识后缀 |
| **Action 字段空缺** | LLM 学到「诊断无修复」 | 专家找到根因后无下一步 | 🟠 中 | 批量填充 action 至 80%+ |
| **Critical 0.4%** | P0 问题推理能力弱 | 缺乏高危场景参考 | 🟠 中 | 补充 20+ critical QA/Case Study |
| **缺乏 CoT 标注** | 不利于思维链微调 | 专家看不到推理过程 | 🟡 低 | 在关键 Skill 中添加 "思考过程" 段落 |
| **缺乏负面样本** | 容易产生幻觉 | 专家可能误用命令 | 🟡 低 | 补充「常见错误」和「禁忌操作」段落 |

## 五、LLM-Wiki vs 专家阅读 对比

| 评估项 | LLM-Wiki 角度 | 专家阅读角度 | 差距 |
|:---|:---:|:---:|:---|
| 代码密度（57.9%） | ⭐⭐⭐ 命令学习条件优越 | ⭐⭐⭐ 可直接复制执行 | 双赢 |
| Prose 密度（31.1%） | ⭐⭐ 推理知识不足 | ⭐⭐ 决策上下文缺失 | 共同短板 |
| Skill 深度（122 行） | ⭐⭐ 模式不完整 | ⭐⭐ runbook 太薄 | 共同短板 |
| 表格密度（19.9/文件） | ⭐⭐⭐ 结构化学习好 | ⭐⭐⭐ 参数对照清晰 | 双赢 |
| FTA 深度（991 行） | ⭐⭐⭐ 推理骨架完整 | ⭐⭐⭐ 问题树可视化强 | 双赢 |
| 重复 title（948） | ⭐⭐ 训练噪声 | ⭐⭐ 导航干扰 | 共同短板 |
| 段落碎片化（中位数 115） | ⭐⭐⭐ 适合 tokenization | ⭐⭐ 阅读节奏打断 | LLM 受益，专家受损 |

**核心洞察**：
> KUDIG 的**代码密度和结构化程度**对 LLM 和专家是**双赢资产**；但**prose 密度和 Skill 深度**是**共同短板**——补齐 prose 和 Skill 深度将同时提升 LLM 推理能力和专家阅读体验。
>
> 一个意外的发现：**段落碎片化**（中位数 115 字符）对 LLM 是优势（短序列更适合 transformer 的局部注意力），但对专家是劣势（阅读节奏被打断）。这揭示了「LLM 友好」和「人类友好」之间并非总是正相关。

## 六、改进路线图

### 阶段 3.5（2-3 天）— 共同短板补齐

1. **Skill 深度扩充**（17 个 Skill，每个 +200-400 行）
   - 增加「边界条件」段落：「如果 A 正常但 B 异常，则…」
   - 增加「常见错误」段落：「不要这样做，因为…」
   - 增加「版本差异」段落：「v1.28 和 v1.32 的区别是…」

2. **Prose 解释补充**
   - 为每个代码块前添加 2-3 行「为什么执行这个命令」的解释
   - 目标：prose 比例从 31.1% 提升至 40%+

3. **Action 批量填充**
   - 基于 skill_ref 和 command 推断修复命令，填充至 80%+ 覆盖率

### 阶段 4（1-2 周）— LLM 微调优化

4. **命令多样性提升**
   - 引入参数化模板，同一场景生成 3-5 个变体
   - 目标：多样性从 8.2% 提升至 25%+

5. **CoT 标注**
   - 在 50 个核心 Skill/FTA 中添加 "Let me think step by step" 风格的推理过程

6. **负面样本补充**
   - 每个 Skill 添加「常见错误」和「禁忌操作」段落

### 阶段 5（2-4 周）— 专家体验优化

7. **去重与导航**
   - 处理 948 个重复 title，添加唯一标识
   - 为 domain-19 建立独立 profile，核心语料中降采样

8. **版本差异标注**
   - 所有命令添加 K8s 版本兼容性注释

9. **验证脚本补充**
   - 每个 Skill 补充 verify-*.sh，覆盖率 100%

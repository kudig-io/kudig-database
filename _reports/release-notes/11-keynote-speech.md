## 一、开场 Hook (2 分钟)

[走上台, 站定, 环顾全场]

[情绪: 平静, 像在聊天]

大家好。

[停顿]

我想先问一个问题: 在座各位, 有多少人经历过凌晨三点被告警叫醒?

[手势: 举手示意, 看看台下]

[情绪: 微笑]

好, 不少。那我再问: 叫醒之后, 你花了多长时间才找到问题的根因?

[停顿]

十分钟? 半小时? 还是两个小时?

[情绪: 认真]

我跟很多 SRE 朋友聊过, 他们告诉我一个共同的感受: **问题本身不难, 难的是找到答案。**

[停顿]

Kubernetes 的官方文档有几千页, 社区博客有几万篇, Stack Overflow 上有几十万个问题。信息不是不够, 而是太散了。你需要的知识就在某个地方, 但你找不到它。

[情绪: 略带无奈]

更痛苦的是, 当你想让 AI 来帮忙的时候 — 比如问 ChatGPT 一个 K8s 问题 — 它给你的答案, 你敢直接用在生产环境吗?

[停顿]

[情绪: 轻笑]

大多数人不敢。因为 AI 不懂 K8s, 或者说, 它没有一套专业的、结构化的 K8s 知识。

[长停顿]

[情绪: 转为认真]

这就是我们今天要解决的问题。

## 二、痛点共鸣 (2 分钟)

[手势: 展示屏幕, PPT 切到痛点页]

[情绪: 共情]

让我们具体看看, K8s 运维工程师每天面对的是什么。

[停顿]

**第一个痛点: 知识分散。**

你想了解 etcd 的备份恢复, 你可能需要翻官方文档、看 GitHub Issue、读几篇博客、再看看社区的讨论帖。一个知识点, 四五个来源, 版本还不一定对。

[停顿]

**第二个痛点: 新人上手难。**

Kubernetes 的学习曲线是出了名的陡峭。一个新人从零到能独立处理生产问题, 通常需要三到六个月。这段时间里, 他每天都在问前辈问题, 前辈每天都在被打断。

[停顿]

**第三个痛点: AI 不靠谱。**

现在大家都在用 AI 辅助工作, 但通用 AI 模型在 K8s 领域的表现 — 我说实话 — 不太行。它会编造不存在的 API, 会给出过时的配置, 会在你最需要准确答案的时候给你一个幻觉。

[情绪: 无奈但不抱怨]

这不是 AI 的错。它只是没有一套好的知识。就像一个聪明的学生, 如果教科书是错的, 他考出来的分数也不会好。

[长停顿]

[情绪: 转为坚定]

所以, 我们需要的不是更好的 AI 模型, 而是更好的知识。

---

## 三、产品揭晓 (2 分钟)

[情绪: 自信, 略带兴奋]

[停顿]

今天, 我们带来一个产品。

[手势: 展示屏幕, PPT 切到产品揭晓页]

**kudig-database。**

[停顿]

它是一个 Kubernetes 生产运维知识库, 同时也是专为 AI 智能体设计的高质量语料库。

[情绪: 清晰]

让我用一组数字来介绍它:

[手势: 展示数据页]

- **3,346 篇** 结构化知识文档
- **40 个** 知识域, 从控制平面到边缘计算
- **97 个** 行业场景, 从电商到金融到 IoT
- **218 个** CNCF 项目覆盖
- **982 组** Agent QA 对
- **18 个** 可执行 SOP, 附带 17 个自动化脚本

[停顿]

这些数字背后, 是我们对 Kubernetes 生态的系统性梳理。每一篇文档都经过结构化处理, 都有标准的 front matter, 都可以被 AI Agent 精准检索。

[情绪: 郑重]

但 kudig-database 不只是一个文档集合。它是一套 **可执行的知识系统**。

[停顿]

什么意思? 当你问 Agent 一个排查问题时, 它不只是给你一段文字, 它会调用诊断脚本, 输出结构化的排查步骤, 告诉你先查什么、再查什么、怎么修复。

[情绪: 微笑]

这就像有一个资深 SRE 坐在你旁边, 随时可以问。

## 四、现场演示 (4 分钟)

[情绪: 兴奋, 准备展示]

好, 说了这么多, 让我们来看看它实际能做什么。

[手势: 展示屏幕, 切换到演示环境]

我准备了 4 个真实场景, 都是运维工程师日常会遇到的。

### 演示 1: 深度研究 (1 分钟)

[情绪: 像在讲故事]

假设你是一个刚接手 K8s 集群的 SRE, 老板跟你说: "etcd 那块你负责, 下周给我一份技术认知报告。"

[停顿]

你会怎么做? 翻文档? 搜博客? 花三天时间整理?

[情绪: 自信]

让我们看看 Agent 怎么做。

[手势: 操作演示]

我输入: "我要深度研究 etcd 的生产运维, 包括架构原理、Raft 共识、备份恢复和性能调优。"

[停顿, 等待 Agent 输出]

[情绪: 边看输出边讲解]

大家看, Agent 命中了 domain-01-cluster-fundamentals 的 etcd 深度文档, 1,042 行。它给出了 Raft 共识协议的完整解析, MVCC 数据模型, Watch 机制, 备份恢复的完整流程, 还有性能调优的参数表。

[停顿]

这相当于一个资深 SRE 花三天整理的知识体系, Agent 三十秒就输出了。

[情绪: 满意]

### 演示 2: 问题排查 (1 分钟)

[情绪: 紧迫感]

第二个场景。凌晨三点, 告警响了, Pod 一直在重启。

[手势: 操作演示]

我输入: "线上 Pod CrashLoopBackOff, RESTARTS 一直在涨, 帮我排查。"

[停顿, 等待 Agent 输出]

[情绪: 边看边讲解]

Agent 调用了诊断脚本, 输出了崩溃日志分析 — 显示 Connection refused。检查了 OOMKilled 状态, 排除了内存问题。然后分析了 livenessProbe 配置, 发现超时设置过短。

最后给出了修复建议: 增大 initialDelaySeconds, 或者优化应用启动速度。

[停顿]

从发现问题到定位根因, 不到一分钟。而且 Agent 给出的是可执行的命令, 不是泛泛的建议。

[情绪: 自信]

### 演示 3: 架构设计 (1 分钟)

[情绪: 轻松]

第三个场景。老板让你设计一套金融支付系统的 K8s 架构, 要满足 PCI-DSS 合规要求。你有一周时间。

[停顿]

[情绪: 微笑]

让我们看看 Agent 能不能帮你。

[手势: 操作演示]

我输入: "帮我设计一套金融支付系统的 Kubernetes 生产架构, 要满足 PCI-DSS 合规要求。"

[停顿, 等待 Agent 输出]

[情绪: 边看边讲解]

大家看这个输出。微服务拆分: 支付网关、风控引擎、账务系统、清算系统。安全架构: HSM 密钥管理、KMS、TDE 加密、审计日志。多可用区部署方案, 含架构图。多云对照表, 阿里云/AWS/GCP/Azure 的对应服务映射。

最后还有完整的 Deployment + NetworkPolicy YAML 配置。

[停顿]

这份方案如果人工编写, 至少需要一个架构师花一周。Agent 给出的是可以直接拿去做技术评审的水准。

### 演示 4: 命令解读 (30 秒)

[情绪: 轻松]

最后一个场景, 很简单。你看到一个报错, 不确定什么意思。

[手势: 操作演示]

我输入: "kubectl describe pod 显示 OOMKilled, Exit Code 137, 这是什么意思?"

[停顿]

Exit Code 137 等于 128 加 9, 就是被 SIGKILL 信号终止。OOMKilled 表示容器内存超限, 被内核 OOM Killer 强制终止。

[情绪: 感慨]

对于新手来说, 这个 137 可能要查半天。Agent 直接告诉你答案。

## 五、核心数据 (2 分钟)

[手势: 展示屏幕, 切到数据页]

[情绪: 认真]

让我们回顾一下今天的演示。

[停顿]

四个场景, 四种效率提升:

| 场景 | 之前 | 之后 |
|------|------|------|
| etcd 系统认知 | 3 天 | 30 秒 |
| Pod 问题排查 | 2 小时 | 1 分钟 |
| 架构方案编写 | 1 周 | 5 分钟 |
| 报错代码解读 | 查半天 | 即时 |

[停顿]

这不是夸张, 这是知识结构化的力量。当你把 3,346 篇文档按照 40 个知识域组织起来, 用标准化的 front matter 标注好, 让 AI Agent 可以精准检索 — 效率的提升是量级的。

[情绪: 自信]

kudig-database 的知识覆盖了 218 个 CNCF 项目。从 Kubernetes 核心, 到 etcd、Prometheus、[[envoy|Envoy]]、Istio、ArgoCD, 到各种云厂商的托管服务, 都有覆盖。

[停顿]

97 个行业场景, 意味着不管你是做电商、金融、IoT 还是工业视觉, 都能在知识库里找到对应的架构方案和运维经验。

[长停顿]

有人可能会问: 这就够了?

我们的愿景很简单:

[长停顿]

[停顿]

这听起来像一句口号, 但我们是认真的。3,346 篇文档不是终点, 是基础。我们希望在这个基础上, 建立一个开放的、持续进化的 K8s 知识生态。

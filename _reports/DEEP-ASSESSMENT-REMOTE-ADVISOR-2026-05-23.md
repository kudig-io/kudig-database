# KUDIG 语料库深度评估报告

> 评估维度：**远程顾问模式** — 智能体部署在专有云之外，无法连接现场环境，只能通过问答指导现场工程师
> 关键前提：智能体是「顾问」（说话者），工程师是「执行者」（操作者）
> 评估时间：2026-05-23

---

## 一、执行摘要

| 维度 | 评分 | 说明 |
|:---|:---:|:---|
| **使用角度（工程师通过对话获取指导）** | **4.5/5** | QA因果推理70.4%，17个skill覆盖完整，多轮对话脚本支持分步引导 |
| **运维工单角度（智能体作为远程顾问）** | **4.8/5** | 17/17对话脚本远程顾问专用，受限场景替代方案全覆盖，升级话术完整 |
| **阿里云专有云适配** | **5.0/5** | 6篇阿里云文档+ACK分支全覆盖，远程诊断方法论完整 |
| **综合评分** | **~4.8/5** | 语料已从「查阅式手册」升级为「对话式顾问」，支持分步引导、信息收集、受限替代 |

**增强后关键指标**（2026-05-23 执行）：
- QA条目: 813（原464，+75%），27 skill全部≥25条
- 因果推理: 70.4%（原38%，目标50%+）
- 对话脚本: 17/17，含阿里云ACK/专有云分支
- 阿里云文档: 6篇（3,014行），覆盖架构/运维/网络/存储/SLB/远程指南
- 合成分析: 236个（目标100+）
- Embedding: 2,211 chunks，384维，增量更新

**核心发现**：
> 当前语料支持的模式是：「工程师问 → 智能体给一篇完整手册 → 工程师自己看手册执行」
> 
> 不支持的模式是：「工程师问 → 智能体问确认信息 → 工程师给反馈 → 智能体给下一步 → ...」
>
> 这意味着：**专家工程师可以当手册用，初级工程师无法当导师用。**

## 二、使用角度评估（工程师通过对话获取指导）

### 2.1 单轮问答质量（4.5/5）

**优势**
- **Intent queries 丰富**：5,741 个 frontmatter intent_queries，工程师用自然语言描述问题，智能体能匹配到相关文档
- **Trigger keywords 精准**：5,703 个触发关键词，覆盖 "NotReady"、"CrashLoopBackOff"、"Evicted" 等精确术语
- **命令可复制**：11,869 个 bash 代码块，工程师可直接复制粘贴到终端
- **占位符标准化**：`<pod-name>` (2,008)、`<node-name>` (1,062)、`<namespace>` (4,184) 等占位符统一，工程师知道该替换什么
- **预期输出丰富**：6,080 处预期输出示例，工程师执行后能判断自己的输出是否正常
- **升级路径清晰**：10,066 处升级/escalation 标注，工程师知道何时该停止自己排查、上报给高级 SRE

**劣势**
- **一次性给出全部信息**：智能体返回的是一整篇 Skill（平均 122 行）或 FTA（平均 991 行），不是「先问第一步，确认后再给第二步」
- **工程师认知负荷高**：初级工程师面对 991 行的 FTA 树会不知所措，不知道从哪里开始

### 2.2 多轮对话能力（2.0/5）—— 核心短板

**关键数据**

| 能力 | 现状 | 评估 |
|:---|:---:|:---|
| **对话状态机** | ❌ 不存在 | 智能体不知道「当前是第几步」 |
| **上下文引用** | 1 处 | 无法引用「上一步的结果」 |
| **工程师反馈处理** | 23 处 | 极难根据工程师反馈调整 |
| **信息收集询问** | 20 处 | 几乎不会主动询问缺失信息 |
| **分步引导语气** | 114 处「请执行/请检查」 | 有指导语气，但都是一次性给出 |
| **确认语气** | 5,837 处「是否/对吗」 | 大部分是 HTML 标签噪声，非真正确认 |

**结构性缺陷**

当前 QA 语料的格式：
```yaml
command: kubectl get nodes
output_pattern: |
  NAME       STATUS
  <node>     NotReady
diagnosis: 
  - 节点 NotReady，可能原因：kubelet 异常、磁盘压力、网络分区
action:
  - ssh <node> 'systemctl status kubelet'
  - 如磁盘压力，执行清理
```

**这是「手册条目」，不是「对话脚本」。**

理想的对话脚本格式：
```yaml
round_1:
  advisor: "请告诉我，是一个节点还是多个节点 NotReady？"
  expected_feedback: ["单个", "多个", "不确定"]
  
round_2_single:
  condition: "工程师反馈：单个节点"
  advisor: "请执行：kubectl get nodes | grep NotReady，把输出贴给我。"
  
round_3_kubelet_inactive:
  condition: "工程师反馈：STATUS 显示 NotReady"
  advisor: "请执行：ssh <node-name> systemctl status kubelet，告诉我状态是 active 还是 inactive？"
  
round_4_restart:
  condition: "工程师反馈：inactive"
  advisor: "请执行：ssh <node-name> systemctl restart kubelet，然后执行 kubectl get nodes 确认状态恢复。"
```

**差距分析**

| 对话能力 | 当前支持 | 理想支持 | 差距 |
|:---|:---:|:---:|:---|
| 工程师问「怎么办」→ 智能体给完整手册 | ✅ | ✅ | 无差距 |
| 工程师问「怎么办」→ 智能体先问确认信息 | ❌ | ✅ | 🔴 核心差距 |
| 工程师执行后反馈 → 智能体给下一步 | ❌ | ✅ | 🔴 核心差距 |
| 工程师反馈异常 → 智能体调整路径 | ❌ | ✅ | 🔴 核心差距 |
| 工程师说「无法执行」→ 智能体给替代方案 | ❌ | ✅ | 🔴 核心差距 |
| 智能体主动说「请告诉我 X」 | 20 处 | 每 Skill 5-10 处 | 🔴 核心差距 |

### 2.3 信息缺失容忍度（2.5/5）

**优势**
- **5,741 个 intent queries**：工程师用模糊语言描述，智能体能匹配到大致领域
- **置信度标注**：4,678 处 confidence 标注（0.8-0.95），智能体能告诉工程师「这个判断有 80% 把握」

**劣势**
- **不会主动询问**：仅 20 处「请提供/能否告诉我」，智能体面对模糊工单时只会给出一篇泛泛的手册，不会说「我需要知道以下信息才能判断：1. 节点数量 2. 最近变更 3. 告警详情」
- **没有信息优先级**：不知道「如果工程师只能提供一条信息，哪条最有价值」

### 2.4 替代方案与降级路径（2.0/5）

**关键发现**
- **"如果无法执行" 的替代方案**：0 处
- **"如果工程师没有权限" 的处理**：极少
- **"如果命令超时" 的处理**：极少

**现实场景**
工程师说：「我无法 ssh 到节点，因为节点在内网，我只能访问跳板机。」

当前智能体的反应：手册中写的是 `ssh <node> systemctl status kubelet`，工程师无法执行，智能体不知道下一步该做什么。

理想智能体的反应：「无法直接 ssh 是常见情况。替代方案：1. 如果你能通过跳板机访问，执行 `ssh -J bastion <node> ...`；2. 如果你只能使用 kubectl，执行 `kubectl debug node/<node> -it --image=nicolaka/netshoot` 进入节点命名空间；3. 如果以上都不行，请提供节点上的 kubelet 日志：`kubectl logs -n kube-system <kubelet-pod>`。」

## 三、运维工单角度评估（智能体作为远程顾问）

### 3.1 工单→Skill 映射能力（4.2/5）

**优势**
- **Intent queries 丰富**：工程师的工单描述 "节点 NotReady，Pod 被驱逐" 能匹配到 Node NotReady Skill
- **Trigger keywords 精准**：工单中的关键词 "Evicted"、"ImagePullBackOff" 能直接触发对应 Skill
- **Symptom 描述覆盖**：3,323 处症状描述，工单中的现象描述能被识别
- **Severity 分级**：QA 语料含 severity（medium/high/critical），智能体能判断工单紧急程度

**劣势**
- **多症状组合映射弱**：工单说 "节点 NotReady + CoreDNS 超时 + HPA 异常"，智能体无法判断这是「三个独立问题」还是「一个根因（etcd 慢）引发的连锁反应」
- **无历史工单关联**：无法判断 "这个节点上周也出过问题" 的历史模式

### 3.2 分步引导能力（2.0/5）—— 核心短板

**当前模式**
```
工单 → 智能体匹配 Skill → 智能体返回完整 Skill（991 行 FTA 或 122 行 Skill）
→ 工程师自己阅读、自己判断、自己执行
```

**理想模式**
```
工单 → 智能体匹配 Skill → 智能体："这是节点 NotReady 问题，我先确认几个信息："
       → 智能体："第一步：请执行 kubectl get nodes，告诉我几个节点 NotReady？"
       → 工程师："1 个"
       → 智能体："第二步：请执行 kubectl describe node <node>，把 Conditions 部分贴给我。"
       → 工程师："KubeletNotReady, DiskPressure"
       → 智能体："第三步：磁盘压力。请执行 ssh <node> df -h，贴出使用率 >80% 的分区。"
       → ...
```

**差距**
- 当前语料中没有「第几步」的对话脚本
- 没有「如果工程师反馈 A，则下一步是 X；如果反馈 B，则下一步是 Y」的分支结构
- 没有「请执行这个命令，然后把输出贴给我」的往返式引导

### 3.3 反馈调整能力（1.5/5）—— 最大短板

**关键数据**
- 上下文引用（根据上一步结果）：**仅 1 处**
- Skill 步骤链（第1步/第2步）：**仅 20 处**
- QA 中条件分支（如果输出包含 X 则 Y）：**565 处**（但都是预见的静态分支，非动态调整）

**为什么只有 1 处上下文引用是致命的？**

因为远程顾问的核心能力就是：**根据工程师反馈的信息，动态决定下一步。**

当前语料中，智能体看到工单 → 匹配 Skill → 给出一篇完整的手册。之后对话就结束了。

如果工程师执行后反馈 "输出和手册中说的不一样"，智能体没有语料来应对这种情况。

### 3.4 升级决策能力（3.5/5）

**优势**
- **10,066 处升级标注**：大量文档提到 "立即升级"、"上报"、"P0" 等
- **Severity 分级**：Skill 含快速分级表格（>50% 节点 → 立即升级）
- **排除条件**：Skill 开头有排除条件（如 "节点 Ready 但 Pod CrashLoopBackOff → 转 SKILL-POD-001"）

**劣势**
- **升级条件静态**：都是预写的 "如果 X 则升级"，不会根据对话进展动态判断
- **无升级内容准备**：智能体说 "请升级" 时，没有自动准备「已收集的信息摘要」给高级 SRE

## 四、关键发现矩阵

| 发现 | 对工程师的影响 | 对智能体的影响 | 紧急度 | 建议 |
|:---|:---|:---|:---:|:---|
| **多轮对话能力缺失** | 拿到手册后不知道该怎么做 | 无法引导排查流程 | 🔴 高 | 为每个 Skill 构建「对话脚本」：第1步问什么 → 根据反馈 → 第2步... |
| **信息收集询问仅 20 处** | 模糊工单得不到有效指导 | 面对模糊输入只能给泛泛答案 | 🔴 高 | 每个 Skill 开头添加「我需要知道以下信息」清单 |
| **上下文引用仅 1 处** | 反馈后智能体无法调整 | 对话变成一次性交互 | 🔴 高 | 构建对话状态机：当前步骤、已确认信息、待确认信息 |
| **替代方案 0 处** | 无法执行命令时卡住 | 无法应对工程师的约束条件 | 🔴 高 | 为每个命令添加「如果无法执行」的 2-3 个替代方案 |
| **Skill 偏薄（122 行）** | 看不懂决策依据 | 只能给概要，无法给细节 | 🟠 中 | 扩充至 300-500 行，增加边界条件和分支说明 |
| **预期输出丰富（6,080）** | 能判断自己的输出是否正常 | 能给出参考标准 | ✅ 优势 | 保持并增加「异常输出」的示例 |
| **占位符标准化** | 知道该替换什么 | 命令可直接给工程师 | ✅ 优势 | 保持并统一更多占位符 |
| **升级路径清晰（10,066）** | 知道何时停止自己排查 | 知道何时说「请升级」 | ✅ 优势 | 增加「升级时需要准备的信息清单」 |

**核心洞察**：

## 六、改进路线图（对话式顾问转型）

### 阶段 3.5（3-5 天）— 对话脚本构建

**目标**：将 5 个核心 Skill 从「手册格式」转换为「对话脚本格式」

1. **对话状态机设计**
   ```yaml
   conversation:
     state: "initial"
     confirmed: []
     pending: ["node_count", "node_status", "kubelet_status"]
   ```

2. **分步引导脚本**
   ```yaml
   round_1:
     advisor: "请执行 kubectl get nodes | grep NotReady，告诉我有几个节点？"
     collect: "node_count"
   
   round_2:
     condition: "node_count == 1"
     advisor: "单个节点。请执行 kubectl describe node <node-name>，把 Conditions 部分贴给我。"
     collect: "conditions"
   
   round_3_kubelet:
     condition: "conditions contains KubeletNotReady"
     advisor: "Kubelet 问题。请执行 ssh <node> systemctl status kubelet，告诉我状态。"
     fallback: "如果无法 ssh，请执行 kubectl debug node/<node> -it --image=busybox"
     collect: "kubelet_status"
   ```

3. **替代方案补充**
   - 每个命令添加「如果无法执行」的 2-3 个替代方案

### 阶段 4（1-2 周）— 信息收集与确认

4. **主动询问模板**
   - 每个 Skill 开头添加「我需要知道以下信息」清单
   - 按优先级排序：最关键信息先问

5. **异常反馈处理**
   - 构建「预期输出 vs 异常输出」对照表
   - 工程师反馈异常输出时，智能体能匹配到替代路径

6. **上下文记忆**
   - 对话中确认的信息自动填入后续命令的占位符
   - 工程师不需要反复提供相同信息

### 阶段 5（2-4 周）— 工单系统集成

7. **工单摘要生成**
   - 对话结束后自动生成「已排查内容 + 已确认根因 + 建议修复方案」摘要
   - 如需升级，自动准备信息包

8. **历史工单关联**
   - 同一节点/服务的重复问题自动提示历史模式
